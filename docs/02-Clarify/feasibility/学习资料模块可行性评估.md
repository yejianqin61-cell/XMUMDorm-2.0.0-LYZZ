> 关联：`docs/00-Constitution/principles/技术约束.md`、`docs/00-Constitution/policies/安全策略.md`

## 一、结论先行

| 子能力 | 可行性 | 说明 |
|--------|--------|------|
| 另建 GitHub 库存学习资料 | ✅ 完全可行 | 纯 Git，零成本 |
| 网页直接读库、不经过服务器 | ✅ 可行（有前提） | 必须库为 **public**，否则浏览器拿不到内容 |
| Markdown 渲染 | ✅ 可行 | 项目**已有** `react-markdown` + `remark-gfm`（`HandbookArticleDetail.jsx` 在用） |
| PDF 用 iframe 显示 | ⚠️ 有条件可行 | **不能用 `raw.githubusercontent.com`**，必须换 CDN（已验证，见 §2.2） |
| 网页允许下载 | ✅ 可行 | 用 CDN 地址 + `?download=` / `download` 属性 |
| 隐藏 GitHub 账号提 PR | ✅ 可行 | 需 fine-grained PAT，**只能放服务端** |
| 自动 merge | ⚠️ 有条件可行 | 依赖仓库开启 Allow auto-merge + **必须有分支保护规则（状态检查或必须评论）** |
| 「不使用服务器资源」 | ⚠️ **部分不成立** | 文件流量确实零服务器成本；但写操作（PR）**必须**经过服务端，见 §4.1 |

**总评：方案整体可行，而且和本项目现状契合度很高。但有三处必须调整原设计：**
1. **PDF 链接源必须换**（raw 的 Content-Type 是 `application/octet-stream`，iframe 里会直接触发下载而不是预览）——实测已证。
2. **写操作不能纯前端**。「隐藏 GitHub 账号」的 token 若下发到浏览器，等于把整个资料库（乃至该账号）的写权限公开，违反 `安全策略.md` 第 43 行「禁止在代码中硬编码密钥/密码/Token」。**这不算「使用服务器资源」——后端本来就在跑**，只多了一个路由，不占额外数据库/存储。
3. **「PR + 自动 merge」的实际收益需要重新认识**：同一个 bot 账号无法 approve 自己的 PR，所以这个 PR **不是真正的代码评审**，它的价值是「审计留痕 + 一键回滚」。如果要真正的评审，必须由真人 admin 点 merge，那就没有「自动」了。

## 二、关键技术点实测验证

以下不是推测，是在本机对真实线上端点实测的结果。

### 2.1 GitHub API 速率（实测 `/rate_limit`）

| 场景 | 额度 |
|------|------|
| 未认证（浏览器直连 api.github.com） | **60 次/小时/IP** |
| 已认证（服务端带 PAT） | **5000 次/小时** |

> 校园网是 NAT 共用出口 IP。**前端直连 GitHub API 列目录会被 60/小时打死**，这是必须在服务端做缓存 + 代理的硬理由。

### 2.2 文件分发端点对比（实测响应头）

| 端点 | Markdown | PDF | CORS | 缓存 |
|------|----------|-----|------|------|
| `raw.githubusercontent.com` | `text/plain` ✅ | ❌ **`application/octet-stream`** | `*` ✅ | `max-age=300` |
| `cdn.jsdelivr.net/gh/…` | `text/markdown` ✅ | ✅ **`application/pdf`** | `*` ✅ | `max-age=604800`（7 天） |

实测细节：
- `raw.githubusercontent.com` 返回的 PDF 还带 `X-Content-Type-Options: nosniff`，浏览器**不会**嗅探成 PDF，iframe 里必然是下载行为。
- jsDelivr 实测返回魔数 `%PDF-`、`Content-Type: application/pdf`，且 `Cross-Origin-Resource-Policy: cross-origin`，**iframe 内联预览可用**。
- Markdown 内容用 raw 或 jsDelivr 都行（纯文本，客户端 `react-markdown` 渲染）。

**结论：分发统一走 `cdn.jsdelivr.net/gh/<owner>/<repo>@<ref>/<path>`。**

### 2.3 PDF 预览的三条备选链路

| 方案 | 可行性 | 代价 |
|------|--------|------|
| **A. jsDelivr 直链 + `<iframe>`** | ✅ 首选 | 依赖第三方 CDN；有单文件体积上限（jsDelivr 对 GitHub 源普遍限制在 **20MB**，需上线前实测确认） |
| **B. GitHub Pages（`<owner>.github.io/<repo>/<path>`）** | ✅ 实测可用 | 见 §2.6 专项评估 |
| C. `docs.google.com/viewer?url=…&embedded=true` | ✅ 实测 200 | 文件 URL 会被 Google 抓取，隐私差；偶发限流 |
| D. `mozilla.github.io/pdf.js/web/viewer.html?file=…` | ✅ 实测 200 | 同样是第三方；适合 jsDelivr 拒收的超大 PDF 兜底 |
| ~~E. raw.githubusercontent 直链~~ | ❌ | Content-Type 错误，见 §2.2 |


### 2.4 GitHub 侧硬限制（官方文档）

- **单文件**：超过告警阈值会有 warning；**超过上限直接拒绝推送**，超出必须用 Git LFS。浏览器方式加文件另有更小的上限。
- **仓库体积**：官方建议 **< 1GB**，**强烈建议 < 5GB**。学习资料库塞满 PDF 会很快逼近。
- **自动 merge**：官方文档明确——**「Allow auto-merge」只有在仓库配置了分支保护规则（要求评论 或 要求状态检查）时才有效**。也就是说 **必须为资料库配一个 required status check（GitHub Actions）或 required review**，否则 auto-merge 根本不会出现。
- **Contents API**：用 base64 提交的写接口有较小的请求体上限（约 1MB 级别，编码后膨胀 ~1.33 倍），大文件要走 Git Data API（blob）或直接从 CI 侧提交。

## 2.6 专项：用 GitHub Pages（`github.io`）做分发？

### 2.6.1 实测结果（`mozilla.github.io` 等 Pages 站点）

| 文件 | Content-Type | `Access-Control-Allow-Origin` | `Cache-Control` | `nosniff` |
|------|--------------|-------------------------------|-----------------|-----------|
| `.pdf` | ✅ `application/pdf` | `*` | `max-age=600` | 无 |
| `.html` | `text/html` | `*` | `max-age=600` | 无 |
| `.mjs` | `text/javascript` | `*` | `max-age=600` | 无 |

Pages 底层是 **Fastly**（与 jsDelivr 同源网络），返回 `Accept-Ranges: bytes`，并**实测不存在 `X-Frame-Options` / CSP**，所以 iframe 内联可用。

### 2.6.2 相对 jsDelivr 的优劣

| 维度 | jsDelivr | GitHub Pages |
|------|----------|--------------|
| PDF Content-Type | ✅ 正确 | ✅ 正确 |
| **中文文件名** | ⚠️ 未实测 | ✅ 原生支持（我们的路径一定含中文） |
| **单文件体积上限** | ⚠️ 约 20MB（未文档化） | ✅ 无此限制（受仓库 100MB 上限约束） |
| 缓存 | 7 天（长） | **10 分钟（短）** |
| **能否锁定 commit sha** | ✅ `@<sha>` 不可变 | ❌ 只能跟分支，**无不可变 pin** |
| 第三方依赖 | jsDelivr 公司 | GitHub 自家（更可靠） |
| CDN purge | 有工具 | 无（靠 10 分钟 TTL 自然过期） |
| 国内可达性 | 有中国优化 | 无明确中国优化 |

### 2.6.3 ⚠️ Pages 的致命安全约束（**这是决定性因素**）

**GitHub Pages 的公开仓库没有「只发布某个子目录之外的例外」机制，且无法自定义响应头。** 实测确认 Pages 不发送 `X-Content-Type-Options: nosniff`。

后果：**任何被交付为 `text/html` 或 `image/svg+xml` 的文件都会在 `*.github.io` 源上执行 JavaScript**。提交 `.html` / `.htm` / `.shtml` / `.xhtml` / `.svg` 文件，即可获得一个**同源托管页面**——这是典型的存储型 XSS，且发生在 GitHub 的域名上，我们**既无法加 CSP 也无法加 nosniff 来缓解**。

在「允许学生上传」的场景下这是**不可接受**的攻击面。若采用 Pages，必须：

1. 上传白名单**硬排除** `.html` `.htm` `.shtml` `.xhtml` `.svg` `.js` `.mjs` `.xml` `.xsl` `.xhtml` 及 `_config.yml` / `_headers`
2. Actions 二次校验兜底（防止绕过）
3. 且必须接受「仓库内容整体可被索引、可被当作网站访问」

### 2.6.4 建议结论

| 结论 | 说明 |
|------|------|
| **一期不启用 Pages** | 将分发复杂度与攻击面控制在最低；jsDelivr 已满足 PDF 预览 |
| **把 Pages 列为已验证的 Plan B** | 一旦实测发现 jsDelivr 的 20MB 上限或中文路径不可用，可**按目录**启用 Pages 承接 PDF，其余仍走 jsDelivr |
| 若启用，**必须同时** | 白名单排除 HTML/SVG 类扩展名 + Actions 校验 + `CONTRIBUTING.md` 明示 |

> 混合模式（PDF 走 Pages，MD 走 jsDelivr `@sha`）是可行的：Pages 无 commit pin，但 **PDF 变更频率低且单文件自包含，不需要 pin**；Markdown 需要 pin 来规避 7 天缓存，正好 jsDelivr 提供。

```
┌─────────────────────────────────────────────────────────────┐
│  学习资料库（新建 public GitHub repo，例：XMUM-Study-Materials）│
│                                                              │
│  main 分支（唯一对外可见的真相源）                             │
│    index.json          ← Actions 自动生成的清单（标题/大小/哈希）│
│    cs/ Data-Structures/notes.md, slides.pdf …                │
│    .github/workflows/validate.yml                             │
│                                                              │
│  bot 用 PAT 提交到 upload/<timestamp>-<user> 分支             │
│        └─> 开 PR ──> Actions 校验（体积/类型/敏感词/命名）      │
│                └─> 通过则 auto-merge（squash）──> main        │
└─────────────────────────────────────────────────────────────┘
        ▲ 写（唯一需要服务端的部分）              │ 读（浏览器直连，零服务器流量）
        │                                        ▼
┌───────────────────┐                  ┌──────────────────────────────┐
│ 现有 Express 后端  │                  │  Web 前端                     │
│ POST /api/materials│                 │  - 列表：从 jsDelivr 拉        │
│  · authenticateToken│                │    index.json（CDN 缓存）      │
│  · multer 收文件    │                 │  - MD：fetch 原文 + ReactMarkdown│
│  · 调 GitHub API    │                 │  - PDF：<iframe src="jsDelivr">│
│  · PAT 只在 .env    │                 │  - 下载：<a download>          │
└───────────────────┘                  └──────────────────────────────┘
```

**读路径完全不经过服务器** —— 这一半的「不使用服务器资源」是成立的。
**写路径必须经过服务器** —— 但只是复用已在运行的 Express，不新增数据库表、不新增对象存储消费（若走纯 GitHub 方案）。

## 四、必须正视的风险

### 4.1 与项目铁律的冲突

| 冲突点 | 铁律出处 | 处置建议 |
|--------|----------|----------|
| Token 不得下发前端 | `安全策略.md` ❌3 | 写操作走服务端，PAT 只进 `.env`（`.gitignore` 已覆盖） |
| ~~「图片存储 = 本地存储，非云存储」~~ | `技术约束.md:14` | ✅ **已修复**：原文与代码不符——实际图片早已走 **Cloudflare R2** 对象存储（`services/objectStorage.js` + `utils/assets.js`，本地 `uploads/` 仅作未配置时的回退且当前为空目录）。已在 `技术约束.md` 更正该行，并新增 **「存储形态（权威口径）」** 一节统一登记资产存储位置 |
| 可能需要新表记录上传者/状态 | `数据库变更铁律.md` | 若做审核队列，必须走 `migrations/` 增量迁移 |
| 新增路由需测试 | `测试铁律.md` | `POST /api/materials` 等必须有 `__tests__/` 用例 |
| **流程本身** | `CLAUDE.md` 10 阶段 | 本模块目前只到「Clarify」阶段，正式开工前需补 Requirement → Module → Task 文档 |

### 4.2 运营与法律风险（**这一条最容易被忽略，但后果最重**）

1. **版权 / 盗版教材**：学生上传扫描教材是最典型的场景，也最容易触发 GitHub DMCA。后果是**整个账号或仓库被封**。如果资料库挂在社团/项目账号下，会连带影响主项目。
2. **内容一旦 merge 就永久公开且可被索引**：`raw.` 和 jsDelivr 都是公网直链，任何人都能访问，**没有登录墙**。删掉文件后，jsDelivr 官方明确宣称「即使文件从 GitHub 删除也会继续永久缓存」——**下架能力天生是残缺的**。
3. **未合并的 PR 分支内容同样可被公网直链访问**。所以「先 PR 后 merge」**不构成**内容隔离。真正的内容隔离只能靠：
   - Actions 校验阶段就拦截（关键词/体积/类型白名单），且
   - 敏感内容只进**私有**仓库（但私有仓库浏览器读不到，方案整体崩塌）。
4. **无审核的自动 merge = 无审核发布**。若要保留「自动」，就必须接受「违规内容自动上线，事后人肉删除」的运营模型。

### 4.3 工程风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| PAT 过期（fine-grained 最长 1 年） | 上传全挂 | 轮换计划 + 后端健康检查告警 |
| 大文件超限 | 上传失败 | 前端预校验 + 后端硬限（建议 **PDF ≤ 10MB**，超限拒绝并提示） |
| Actions 队列/失败 | PR 卡住不 merge | 失败时前端提示「已提交，待处理」，不能假装成功 |
| jsDelivr 不可用或限流 | PDF 打不开 | 兜底 raw 直链（转为下载）+ pdf.js viewer 备用 |
| jsDelivr 缓存 7 天 | 更新后看不到新版本 | 用 `@<commit-sha>` 而非 `@main`；列表用短 TTL 缓存 |
| 仓库超 1GB | GitHub 警告/限流 | 定期清理 + 体积看板；大文件走 R2 |
| RN 端无法渲染 | 移动端功能不一致 | 一期明确「Web 专属」，移动端只给「下载/浏览器打开」 |
