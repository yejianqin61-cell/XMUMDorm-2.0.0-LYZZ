## 第 1 条 设计方向（不可协商）

三条来源，各有明确边界与量化上限：

| 来源 | 取什么 | 明确不取什么 |
|---|---|---|
| **苹果的舒适感** | 留白与呼吸感、层级分明的字阶、连续圆角、物理化动效、内容优先、克制的色彩 | **不做 iOS 克隆**。这是**质感标准**：Android 按 Material 3 语言实现同一质感，两端各自像本机 App |
| **Discord 的社区感** | 暗色**分层表面**、社区信息密度、成员/在线/未读语义、单一强调色、分组列表与分隔线 | 不搬侧栏/频道隐喻（移动端用 Tab + 分段控件承载）；不做无层次的密集堆叠 |
| **Neo-Brutalism（一点点）** | **仅限 CTA / Badge / 分区标题**：2px 描边 + 硬偏移阴影 + 高对比色块 + 较重字重 | 不用于内容表面、正文段落、列表行、导航壳、弹层容器、表单控件 |

**1.1 Neo-Brutalism 越界判定（硬边界）**
任何**第 4 类**元素使用描边+硬阴影+高对比色块手法，即判定越界，**应由 lint 或 review 阻断**。

**1.2 吉祥物**
品牌吉祥物**仅允许出现在 App 图标与启动页**。界面内任何位置（含空态、错误页、成就、等级、引导）**不得出现**。

**1.3 禁止项（红线）**
1. ❌ 以**模糊 / 玻璃拟态**作为视觉身份或层级手段 —— 层级由**表面色**表达。
2. ❌ 「App 1:1 复刻 Web UI」。
3. ❌ 在组件或屏内书写 `#hex` 与 `fontSize` 字面量。
4. ❌ 打包或加载**自有字体文件**（见 2.5）。
5. ❌ **任何渐变背景** —— `LinearGradient` / `MeshGradient` / CSS `linear-gradient` / 用图片模拟渐变，全部禁止。层级与情绪一律由**纯色表面 + 排版**表达。
   依据：所有者 2026-10-01 决定；与红线条 1 同源 —— 渐变是"用观感代替结构"的另一种形式。
6. ❌ **Emoji 作为界面图标**（含 ✅ / ⚠️ / 🔥 这类符号），也**不得**用 Unicode 符号字符（`★` `✓` `▸`）冒充图标。图标一律走第 16 条的两层方案。
   依据：所有者 2026-10-01 决定；且 Web 侧**实测 346 个 JSX 文件中 emoji 出现 0 次、且没有任何图标库** —— 本条是**恢复既有纪律**，不是新增负担。

**1.4 全局组件化：一改全部改（所有者 2026-10-01 裁决 —— 本宪法的设计哲学主线）**
1. **界面视觉只能有两个来源：令牌，或消费令牌的组件。** 不存在第三种（不得屏内自造样式、不得局部覆盖令牌）。
2. **改一处必须全局生效**：改令牌 → 全部屏变化；改组件 → 全部用它的屏变化。做不到的写法即违规。
3. **组件的接口稳定性优先于功能丰富度** —— 因为改基座在 App 上的代价是商店发版（3.4／11.4）。
4. 三条可执行推论：**组件不得嵌套套壳**（9.14）、**令牌必须单一来源且可整体重生成**（2.1）、**新需求先声明原型、不许先写页面**（9.1）。

**依据**：所有者 2026-09-30 与 2026-10-01 决定（[提案 §四/§九](../../03-Architecture/app-design/App设计哲学提案.md)）；红线条 1 另据 Material 官方 "M3: Using color instead of shadows to communicate elevation" 与旧 App「Android 玻璃从不生效」的机制级根因。

## 第 2 条 令牌是唯一事实源

**2.1 令牌是唯一来源，以「csstoken + 构建期生成」落地（所有者 2026-10-01 裁决）**
- 三层结构：`Foundation → Semantic → Component`。业务代码**只允许**消费 Semantic 层；Component 层默认不建。
- **令牌的创作源是一个 CSS 自定义属性文件**：`tokens/design-tokens.css`。这既是所有者要求的「csstoken」，也是"改一处、全局变"的物理载体。
- ⚠️ **React Native 运行期没有 CSS 自定义属性**。因此落地方式是**单一创作源 + 构建期生成**：

| 产物 | 消费者 | 是否手写 |
|---|---|---|
| `tokens/design-tokens.css` | Web 直接消费 | ✅ **唯一事实源** |
| `tokens/generated/native-tokens.ts`（含对比度元数据） | App 消费 | ❌ 生成 |
| `tokens/generated/tokens.json` | 两把尺子消费 | ❌ 生成 |

→ **改品牌色 = 改这一个 CSS 文件 + 跑 `node scripts/gen-tokens.js`。**
⛔ **禁止在生成产物上手工修改**；⛔ **禁止引入样式引擎**（`nativewind` / `restyle` / `unistyles` / `tamagui`）来"实现 CSS 变量"（见 9.11.2）——生成方案已满足同一目的，且不引入构建期依赖。

**2.1.1 品牌色（所有者 2026-10-01 裁决：厦大蓝 + 美团黄）**

| 角色 | 锚点 | 来源 | 关键实测 |
|---|---|---|---|
| **主色 = 厦大蓝** | **`#173874`** | 【实测官方资产】`www.xmu.edu.cn/images/logo2.png`，OKLCH **H=261.2°** | 白字 on 它 **11.33:1** ✅、它作文字 on 白 **11.33:1** ✅、**它 on 暗色 canvas 仅 1.63:1** ❌ |
| **辅色 = 美团黄** | **`#ffc300`** | 【实测官方资产】`www.meituan.com/favicon.ico`，OKLCH **H=86.1°** | 黑字 on 它 **13.06:1** ✅、它 on 暗底 **11.45:1** ✅、白字 on 它 **1.61:1** ❌、它作文字 on 白 **1.61:1** ❌ |

**由实测直接推出的三条硬约束**：
1. **暗色主题必须为厦大蓝配同色相提亮档** —— 锚点在暗底只有 1.63:1，而本项目暗色优先（2.2）。亮色用 `#173874` 本体，暗色用同色相（H=261.2°）的提亮档。
2. **美团黄永远不能作亮色主题的文字** —— 它作文字 on 白只有 1.61:1。它的合法角色只有两个：**填充（必须配黑字）** 与 **暗色主题下的强调**。
3. **警告色相由 73.3° 移到 55°** —— 使主色/辅色/三个状态色**两两满足 2.3 的 25° 门**（对美团黄 31.1°、对危险 32.7°、对厦大蓝 153.8°）。→ **本条不需要任何"例外"，规则保持为硬规则。**

完整色阶、角色映射与**每个令牌的实测对比度**见 [App 设计令牌规范](../../03-Architecture/app-design/App设计令牌规范.md)。

**2.2** 两套主题（dark / light）**各自完整成套**，暗色为一等公民。暗色**先定义**，亮色派生。

**2.3 每个颜色令牌必须携带完整元数据**：`value` / `usage`（surface|fill|text|icon|border）/ `textSafe` / `contrastOn` / `contrastRatio` / `theme`。
- `textSafe = true` 的令牌，其 `contrastRatio` **必须 ≥ 4.5:1**（正文）或 **≥ 3:1**（大字/非文本）。
- ⛔ **`textSafe` 不得按档位推断。**
  v1.0 曾写「品牌色 400/500 档位一律 `textSafe = false`」——**那是从 Web 调色板反推的外推，不是通则**。实测：本项目自建色阶中 `brand-400` 在暗色底上 **7.69:1**（可作文字），而 `brand-600` 在亮色底上才是可作文字的档位（**5.10:1**）。
  **正确规则**：`textSafe` 只能由**该令牌对声明背景（`contrastOn`）的实测对比度**决定。同一个 400 在暗色下 `textSafe=true`、在亮色下 `textSafe=false` 是正常的。
- ⛔ **主色不得承载未达 4.5:1 的白字。** Web 品牌蓝 `#4da7ff` 作文字 on 白与承载白字**都是 2.53:1**，两端都不达标 —— 这是"不能照搬 Web"的机械依据（[品牌主色提案](../../03-Architecture/app-design/App品牌主色提案.md) §1.1）。
- ⛔ **主色与状态色必须各自独占色相，间距 ≥25°。** Web 调色板把辅助色与状态色放在同一色相（薄荷 167.2° vs 成功 161.9° = **5.3°**；杏 66.6° vs 警告 73.3° = **6.7°**；粉 1.4° vs 危险 22.3° = **21.1°**）—— 这是它承载不了语义的结构性根因，**不得继承**。

**2.4 禁止项**
1. ❌ 组件/屏内出现 `#hex` 与 `fontSize` 字面量。
2. ❌ 语义令牌跨用途挪用（分隔线色当文字色、次级文字色当背景色等）。
3. ❌ 用**模糊**表达层级。
4. ❌ 混用 M2 的 overlay 与 M3 的 surface container 数值。
5. ❌ 暗色使用纯黑大底。
6. ❌ 装饰/辅助色复用**状态色的色相**（间距 <25°）。

**2.5 字体：只用系统字体（所有者 2026-10-01 裁决）**
1. ⛔ **禁止打包任何字体文件**，禁止用 `expo-font` 加载自定义字族。禁止使用 Web 的 `Source Han Serif SC`（衬线，Android 退化）与 `PingFang SC`（Android 不存在）。
2. ⛔ **禁止在 Android 上书写 `fontFamily`。** RN 的 `ReactFontManager.createAssetTypeface`（Android）在字体名不匹配时**静默回退系统字体、不打印任何日志**；iOS 才会打印 `Unrecognized font family`。→ **在 Android 上把字体名拼错是不可见的 bug**（[RN #58750](https://github.com/facebook/react-native/issues/58750)，2026-09-29 提交、至今 open，影响 RN 0.87.1）。
3. `system-ui` / `ui-sans-serif` / `ui-serif` / `ui-monospace` / `ui-rounded` **只在 iOS 受支持**（RN 官方 `fontFamily` 文档原文），**不得在 Android 依赖**。
4. **字阶按平台角色各自生成**：iOS 用**系统文字样式**（从而获得 Dynamic Type），Android 用 **M3 字阶角色**。**语义命名两端一致，取值分端生成** —— 依据：Android 的字体度量在 target 35→36 之间已经变过一次（`elegantTextHeight` 在 target 36 被忽略）。
5. **字重只用 `normal` / `bold` + 系统确实存在的档位**。RN 官方："Not all fonts have a variant for each of the numeric values, in that case the closest one is chosen." → 不得假设 `500` 与 `600` 必然可区分。
6. **数字对齐用 `fontVariant: ['tabular-nums']`**，不为此换字体（课表 / 排行榜 / 计时 / 价格）。
7. **系统字号放大必须支持**：`allowFontScaling` 保持开启，为关键布局设 `maxFontSizeMultiplier` 上限，**不得靠关掉缩放解决**。

**依据**：旧 v1 实测 1437 / 645 处；[调研-06](../../06-Analyze/ui-research/App设计调研-06-无障碍与对比度实测.md)；[品牌主色提案](../../03-Architecture/app-design/App品牌主色提案.md)；[调研-02 §C8](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md)；RN 官方 Text Style Props；M3 色角色体系；Apple HIG「Avoid hard-coded color values」「Avoid redefining the semantic meanings」「Soften the color of white backgrounds」。

**验证**：`node scripts/contrast-check.js --fail`；`node scripts/brand-ramp.js --hue <已选定色相> --fail`；`node scripts/design-debt-report.js --path <app>/src --fail-on-zero`。
（注意：**不得把 `--compare --fail` 当门** —— `--compare` 的候选清单故意含未过门项，脚本会直接拒绝该组合并退出码 2。）

## 第 3 条 技术栈（硬约束）

**3.1 版本基线**
- **Expo SDK 57**（`expo@57.0.26`）+ **React Native 0.86.3** + **React 19.2.3**（SDK 57 官方配对，GA 2026-06-30）。
- **一律使用 `npx expo install`**，**禁止**手工指定原生库版本 —— 官方模板与 npm `latest` 已在 gesture-handler 等包上脱节（模板锁 `~2.32.0`，npm latest 3.3.0），且两者 peerDeps **无版本上界**，装错不会在安装期报错、只会在运行时炸。
- **Node.js ≥ 22.13.x**；TypeScript 锁 SDK 模板版本（`~6.0.3`），**禁止**用 npm latest。

**3.2 SDK 线（依据排期收敛为锁 57）**
所有者 2026-10-01 给定排期口径：**无硬性上限，尽量 1 个月内**。据此 **SDK 58 起步方案不再成立**：
- SDK 58 GA 预计 **2026-10-06 ~ 10-13**，等待会吃掉 1 个月预算的 **25%~45%**；
- 现有**全部版本矩阵都是对 SDK 57 实测的**（expo 57.0.26 / RN 0.86.3 / React 19.2.3 / gesture-handler `~2.32.0` / expo-router 57.0.24 / `@expo/ui` 57.0.21），换 58 等于让这套核对作废重做；
- 58 同时吃进三处迁移面：expo-router 核心重构（官方原文 "remove a large portion of the forked react-navigation API surface"）、iOS 27 scene lifecycle、RN Strict TypeScript API。

→ **锁 SDK 57 起步；SDK 58 升级列为独立、非阻塞的后续任务。** 详见[设计阶段计划 §7.2](../../05-Tasks/App设计阶段/设计阶段工作计划与验收门.md)。

**3.3 禁止项**
1. ❌ 使用 `expo@next` / `next` 标签 / `canary` 版本。
2. ❌ 配置中保留 `newArchEnabled`（SDK 55+ 起新架构**强制且无法关闭**，保留会造成误判）。
3. ❌ 引入任何不支持新架构的库（interop 仅作过渡手段，须在 PR 说明）。

**3.4 依赖准入**
引入任何第三方库前，**必须**在 PR 中给出五项：**许可证 / 是否含原生代码 / OTA 影响判定 / 最后发布时间 / 是否强加视觉身份**（第 5 项依据 9.8 与 9.11）。
- 实测：`FlashList` 与 `LegendList` **零原生代码**（OTA 友好）；`expo-image`、`reanimated`、`worklets`、`gesture-handler`、`@expo/ui`、`screens`、`safe-area-context`、`svg` **均含原生代码**。
- 因此 OTA 纪律**必须按依赖逐个登记**，不得一刀切。
- ⚠️ **npm 元数据不可全信**：实测 `tamagui` 的 npm `license` 字段为空，其仓库才是 MIT → 许可证必须**回源核实**。

**依据**：[基座事实核对](../../06-Analyze/tech-research/App基座事实核对-版本线与上架门槛.md)（Lead 独立核实 @2026-09-30）、[基座调研](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md) §2/§3/§6/§9.1。

## 第 4 条 导航与信息架构

**4.1 一级导航（所有者 2026-10-01 裁决，取代同日早前的「广场/树洞/食堂/我的」）**：**四格**

| Tab | 内容（所有者指定） | 定位 |
|---|---|---|
| **广场** | 食堂 · 社团 · 二手 · 跑腿 · 新生指南 | **服务聚合**（去哪吃 / 去哪办事 / 买什么） |
| **工具** | 课程表 · 待办 · 放假日 · **校方系统快速打开（AC 系统 / Moodle / 签到）** | **本 App 的最主要功能入口**（所有者原话） |
| **校园里** | **万能墙 + 树洞**（合并） | 内容社区 |
| **我的** | 个人身份、个人内容、设置 | 个人 |

**发布走 FAB**，**信箱走全局顶栏动作**（4.7），两者都不占 Tab。
→ **本条的定位后果**：本 App 首先是**学生事务与校方系统的工具**，其次才是社区。工具 Tab 的可用性是第一优先。

**4.1.1 「校园里」的合并边界（必须先立规矩，否则会破坏后端不变量）**
所有者要求万能墙与树洞合并。**合并只允许发生在导航层，不允许发生在数据层或信息流层**：
- **后端事实**（[调研-03 §5-Q3](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)）：**树洞非匿名**（`routes/posts.js:130-135` 返回作者昵称/头像/等级）；**万能墙强制匿名**，且匿名是写死在 `routes/confessions.js:6-10` 的**不得破坏的核心不变量**。
- ✅ **允许**：一个 Tab 内用**分段控件**切换两个**互斥**子视图（「树洞」/「万能墙」），各自保留自己的分页、排序与载荷。
- ⛔ **禁止**把两者**混排进同一条信息流**；⛔ 禁止万能墙条目携带任何作者身份；⛔ 禁止为"统一"而给万能墙加作者、或把树洞匿名化 —— **那是后端事实性变更，需另立需求**。
- 两个子视图**各自的返回栈与滚动位置独立**。

**4.1.2 工具 Tab 的「校方系统快速打开与会话记忆」（所有者指定为本 App 最主要功能）**
这是**App 独有、Web 没有**的能力，必须在此立技术边界：
1. **形态**：内嵌 WebView 打开校方系统（AC 系统 / Moodle / 签到），**记住会话**，免去每次重新登录。
2. **会话凭据必须进系统级凭据存储**：token / cookie 走 `expo-secure-store`。⛔ **禁止**写入 AsyncStorage 明文或自建文件。
3. ⛔ **凭据不出设备、不上传**：本项目后端**不得**接收、存储或转发校方系统凭据。**安全红线。**
4. ⛔ **不得自动化"签到"或任何代替用户完成的校方动作**：只提供"打开 + 保持会话"，**不做**自动打卡、模拟点击、批量提交。
5. ⚠️ **商店合规风险（必须知情）**：App Store 审核指南 **4.2（Minimum Functionality）** 会拒"只是网页封装的 App"。因此 ① 工具 Tab 不得在感知上等同于浏览器；② 该能力必须与**原生**课表/待办/放假日同屏同层呈现，而不是一个孤立 WebView 入口；③ 上架前做一次专项自评。
6. **待脚手架期实测（不得当已成立）**：iOS `WKWebView` 第三方 cookie 持久化、Android `CookieManager` 跨会话保持、目标校方系统是否允许被 WebView 内嵌。

**4.2 收纳纪律（取代原「两个收纳器」表述）**
工具已被提升为一级，故收纳结构改为**三处，不得新增第四处**：
1. **广场** —— 服务与内容的**入口聚合**（所有者指定的五类之外，低频**内容/服务**类入口只能落这里）；
2. **工具** —— 学生事务与校方系统的**能力聚合**；
3. **我的** —— 个人身份、个人内容与设置。
- 信箱**不属于任何收纳处** —— 它是全局顶栏动作（4.7），**只此一处**。
- ⛔ **"禁止把低频功能塞到顶栏图标堆里"仍然有效**：顶栏只允许一个动作（信箱）。

**4.2.1 待归位清单（所有者指定的四格内容未覆盖这些能力，以下是【建议】，须确认后才可作为排期依据）**

| 能力 | 建议归宿 | 依据 |
|---|---|---|
| 热搜 / 校园此刻 | **广场**顶部内容条 | 后端 `square/home-summary` 已聚合 `hot_*` |
| 活动 | **广场 → 社团** | 活动属 `clubs.js` |

**4.2.2 明确不对齐项（所有者 2026-10-01 裁决）**
1. ⛔ **M10 学习资料（materials）不做 App 端对齐**（即「除了学习笔记，其他都要和 Web 对齐」中的排除项）→ App **不建**资料上传 / 阅读 / PDF 视图。若将来要做，**单独立项**。
2. ⛔ **M06 管理员后台不对齐**（29 端点 / 11 页 / 桌面表格形态）。
3. ⛔ **商家端不对齐**（14 端点 / 7 页 / 重表单与上传）。
4. ✅ **其余面向学生/用户的能力全部与 Web 对齐** —— 这是本轮的**范围决定**，取代原调研-03 §五中与此冲突的建议（其 Q1/Q2 原建议"不进"被采纳，Q5 的"学习资料做 v1"被改为"不做"）。

**4.3 导航壳必须交给原生容器**：Tab 栏、Header、Sheet、返回手势一律使用平台原生实现。
⛔ **「自绘导航壳 + 贴玻璃」是禁止模式** —— 材质行为（滚动边缘效果、tab 滚动最小化、search tab 分离、sidebar 自适应、随 Reduce Transparency 自动降级）**绑定在系统组件上**，自绘只能拿到静态观感。
⚠️ **SDK 57 上的原生 Tab 实现路径必须在脚手架首周定案**（`expo-router` 的原生 Tab 在 54–57 只有 `unstable-native-tabs`）；三条候选与取舍见[设计阶段计划 §7.3](../../05-Tasks/App设计阶段/设计阶段工作计划与验收门.md)。**无论选哪条，都不得退回自绘 Tab 栏。**

**4.4 返回与深链（铁律）**
1. **每个 Tab 各自独立维护返回栈**；深链落到具体内容时返回栈必须合理（不是空栈）。
2. 返回是**系统级行为**：使用平台 Back API，**不得劫持** `KEYCODE_BACK`。
3. 配置变更（旋转/分屏）后 UI 状态不丢；进程被杀后返回至少**输入不丢**。
4. 同时不叠两个模态；任何时刻不同时显示两个 alert；关闭模态会丢内容时**先解释再给解决方式**。

**4.5 ⚠️ 阻塞级前置验证（不得跳过）**
Android target API 36 上存在 **RN 返回事件失效、系统判定退出 Activity、App 直接关闭**的风险（社区实测与 RN 官方说法相反，上游 `expo/expo#39092` 仍 open）。
**必须在脚手架第一周完成真机 spike**；结论可能形成 ADR。**在该结论出来前，不得锁定返回栈的实现方案。**

**4.6 Tab 过渡用淡入淡出**，禁止横向位移动画与横向滑动切 Tab（Android 左右边缘与 iOS 左边缘都是系统返回手势区）。

**4.7 信箱入口（所有者 2026-10-01 裁决，取代调研-03 的方案 B）**

信箱是**本项目在旧 Web 移动端完全失去入口的一项能力**（[调研-03 §1.2 事实 2](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)：`TopBar.jsx` 全仓库 0 引用）。因此本条的每一条都是**防止该缺陷复发**的约束：

1. **形态**：信箱是一个**贯穿全局的顶栏动作**，位于**四个一级 Tab 的顶栏右上角**；图标、位置、点击区、角标语义**四屏完全一致**。
2. **归属**：它**不是 Tab**，**不进两个收纳器**，也**不是模态** —— 它是**推入式全屏目的地**（进入后隐藏 Tab 栏）。
3. **常态可见**：不允许出现"只在某一屏才有信箱入口"。**这是本条的验收核心。**
4. **角标**：未读角标是该图标的**唯一职责**，必须常驻；角标口径与"我的"里的次要入口**必须同源**，不得两套计数。
5. **返回语义**：从任一 Tab 进入信箱后返回，**回到进入前的 Tab 与滚动位置**。深层内容（如从信箱点进帖子）再返回应回到信箱，而不是跳过它。
6. **深链**：从系统推送进入 `/mailbox` 时，**栈底必须回退到广场**，不得出现空栈（依据 4.4.1）。
7. ⚠️ **诚实记录的代价**：顶栏右上角是**单手可达性最差**的位置（Tab 栏最好）。所有者以这一可达性损失换取"释放第 5 格 + 四格标签更宽裕"。**因此第 4 项（角标）与系统推送承担了"不漏消息"的全部责任** —— 它们是本条不可删减的部分，不是可选优化。
8. 顺带收益（记录以免日后被当作偶然）：一级 Tab 由 5 降为 4，**启动时 eager 渲染的页面树减少一个**，且 Tab 标签弹性压力**下降一整档**（提案 §6.1／§6.3）。

**依据**：[调研-03](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md) §1.2／§4.1／§4.4（顶部横幅已登记取代关系）、[调研-02](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md)、[调研-01 §8.1-A7~A20/B1~B8](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md)。

## 第 5 条 平台边界（双端各自最优）

**5.1 必须两端一致**：信息架构、业务行为、术语、数据契约、**品牌标志**、**文案语气**。
⚠️ **品牌调色板不再属于"必须一致"项** —— 所有者 2026-10-01 裁决 App 自建色阶（[品牌主色提案](../../03-Architecture/app-design/App品牌主色提案.md)）。品牌色是否反向统一 Web 单独立项，**不阻塞 App**。

**5.2 必须各按各的平台规范做**：导航壳形态、返回语义、弹层与 Sheet 形态、动效曲线、系统材质、图标语言、触感反馈、**字阶取值**。

**5.3 平台硬约束（不可协商）**
| 平台 | 约束 |
|---|---|
| Android | **edge-to-edge 不可退出**（target 36 起 `windowOptOutEdgeToEdgeEnforcement` 被禁用）→ **每屏必须自行处理 insets** |
| Android | **`sw≥600dp` 上方向/可调整性限制被忽略**，且该退出口在 API 37 取消 → **大屏/折叠屏自适应是首发要求，不是"以后再说"** |
| Android | 层级由**表面色**表达（tonal surface），不是模糊 |
| iOS | **2026-04-28 起必须用 iOS 26 SDK 或更新构建**才能提交 |
| iOS | `UIDesignRequiresCompatibility` **在 iOS 27+ SDK 构建时被系统忽略** → Liquid Glass 无法长期退出 |

**5.4 已登记的平台差异项（显式记录，不取交集）**
1. 应用内是否提供外观开关：Apple HIG **反对**应用自建外观设置 vs Discord 官方提供五档主题 → 本项目**默认不提供外观档位**，只跟随系统；如需例外须 ADR。
2. Tab 栏能否承载动作：Apple HIG 明文"tab bar 支持导航、**不提供动作**" → 本项目**发布不做 Tab**（见 4.1）。**"底栏中间放发布"零官方背书，禁止采用。**
3. 触控目标尺寸：**iOS ≥44×44pt / Android ≥48×48dp**（各自平台官方值，**不取交集**）。
4. 字阶取值：iOS 用系统文字样式（Dynamic Type），Android 用 M3 字阶角色；**语义命名一致、数值分端生成**（见 2.5.4）。

## 第 6 条 双语与本地化

**6.1 集中词条层，禁止内联三元**
- ⛔ **禁止** `isZh ? '中文' : 'English'` 这类内联三元（Web 侧实测 **1701 处**，无法审计完整性、无法统一长度）。
- ✅ 全部面向用户的字符串走**集中词条层**（key-based），每个 key 必须同时具备 `zh` 与 `en`。
- 旧 App 的"双语"是空壳（139 个文件里仅 **4 个**真正双语），**不得重演**。

**6.2 布局按英文长度定尺寸**
- 实测：英文长度中位数是中文的 **2.50×**，75 分位 **3.00×**，90 分位 3.75×，最大 6.00×；**75.9%** 的文案英文 ≥ 中文 2 倍。
- 规则：所有定宽元素按**英文**定尺寸；中文**不得填满**容器；按钮 / Tab / Badge 需 **≥3× 弹性**或明确截断策略；影响关键操作的文案不得静默截断。
- **语言切换不得引发布局跳动**（弹性在令牌层预留）。

**6.3 Tab 标签策略（四格后压力下降，策略放松一档）**：4.7 的裁决使每格可用宽度增加 **25%** → 由"图标优先 + 仅激活项显示文字"放宽为"**图标 + 常态短标签**"。仍须按英文定宽；`Tree Hole` 这类两词标签的最终处理（缩短 / 两行）归风格体系阶段定稿。

**6.4 语言集合与默认语言（待定）**：是否预留马来语（`ms`）；是否跟随系统语言（Web 默认 `zh`）。

**依据**：[调研-05](../../06-Analyze/ui-research/App设计调研-05-双语与文本弹性实测.md)。

**验证**：`design-debt-report.js` 的「内联双语三元必须为 0」「`t('key')` ≥1」两项。

## 第 7 条 无障碍（每屏验收，不是"尽量"）

**7.1 硬数字**：触控目标 **iOS ≥44×44pt / Android ≥48×48dp**（视觉可更小，命中区必须补足）；字号**默认 17pt / 最小 11pt**；对比度 **≥4.5:1**（正文，≤17pt）/ **≥3:1**（18pt 或加粗）。

**7.2 必须支持**：系统字号放大后布局不崩；TalkBack（Android）与 VoiceOver（iOS）可完整朗读；纯图标按钮必须有可读标签；图片必须有替代文本；自绘控件必须暴露正确角色与状态。

**7.3 动效降级**：**每条动效都必须声明并实现 reduced-motion 降级**（参照 Web 侧仅覆盖 8 处的反例）。

**7.4 自绘即自负**：标准系统组件会自动适配 Reduce Motion / Reduce Transparency；**自绘的部分必须自己实现全部旁路**。

**依据**：Apple HIG Accessibility、Android 官方触控目标 48dp、W3C WCAG 2.2 SC 1.4.3、[调研-06](../../06-Analyze/ui-research/App设计调研-06-无障碍与对比度实测.md)。

## 第 8 条 动效

**8.1** 动效规格**由本项目自建**并明确声明为近似 —— 依据：**M3 动效物理在 React Native 上没有官方实现**（官方实现对照表 Compose=Available、Flutter=Unavailable、RN 无条目），且 spring 数值官方未公开。**不得声称"M3 合规动效"。**

**8.2 准许清单制**：每个动效必须能回答"它在表达**方向 / 反馈 / 寻路**中的哪一种"，答不上就删。

**8.3** **高频交互默认不动**（Apple HIG 官方口径）。

**8.4** 位移类可有回弹，**颜色/透明度类不得回弹**；时长随覆盖面积缩放；手势驱动动画必须在 **UI 线程**执行。

**8.5** 动效库（Reanimated / Gesture Handler）**只在本条清单落地后才允许引入** —— 旧 App 装了却 0 引用的根因正是"没有动效规范，因此没有'该在哪里动'的依据"。

**依据**：[调研-02](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) 附录 B、[调研-01 §6](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md)。

## 第 9 条 组件与原型纪律

**9.1 原型库 = 8 核心 + 9 扩展**（覆盖 103 页）。每个新需求**必须先声明所属原型**；不属于任何一个时，先评审"是否新增原型"，**不许先写页面**。

**9.2** 表单与列表是两个最大的桶（合计 **37.9%**），**优先做成参数化框架**。

**9.3** 万能墙（一屏一篇翻页）与二手私信（对话）**各只有 1 页也必须单独立原型**，不允许塞进列表/详情降级实现。

**9.4** **纯转发原型禁止新增**；现存 4 个纯转发页应删除。

**9.5 组件库必须被消费**：**第一个纵向切片必须真正消费组件库与令牌**，通过后才允许模块铺开。
反例：旧 App 组件库 0 引用；Web 侧 9 个模板中 `FormPageLayout` **0 页使用**。

**9.6 App 组件必须重写，不复用 `shared/components/`** —— 该目录含 `.jsx` + `.css`，为 Web 专属。可与 App 共用的只有 `shared/{api,constants,utils,config,query}`。

**9.7** 建议把 `shared/` 物理拆为 `shared/core/`（跨端纯逻辑）与 `shared/web/`（Web 专属）——物理边界比约定可靠（**待定项**）。

**9.8 组件层三层边界（所有者 2026-10-01 裁决 —— 回答"用现成的还是自己写"）**

| 层 | 做法 | 判据 |
|---|---|---|
| **① 平台 / 运行时原语** | **用现成** | 它承担的是**平台行为**，不是视觉决定 |
| **② 设计系统层**（令牌 → 主题 → 原子 → 组合 → 原型） | **自研** | 它是**视觉决定**或本项目独有的约束 |
| **③ 完整设计系统 / UI kit** | **不作基座** | 采用即接受它的色值与字阶 |

**9.9 第①层采用清单（**不得重造**）**：系统容器（`react-native-screens` + 原生 Tab 实现〔4.3〕+ `expo-router`）、手势与动效（`gesture-handler` + `reanimated`/`worklets`）、**原生控件优先 `@expo/ui`**、列表虚拟化（`FlashList` **或** `LegendList`，二者择一）、`expo-image` / `expo-haptics` / `expo-symbols`、`safe-area-context` / `svg`。
⛔ **禁止重造**手势、动效、列表虚拟化与物理 —— 这是平台工程，不是设计工作。
⚠️ **上列版本一律由 `npx expo install` 决定**（见 3.1）。**权威 pin 快照见[组件层调研 §4.6](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)** —— 实测 `expo@57.0.26` 的 `bundledNativeModules.json` 把 reanimated 钉在 **4.5.1**（npm latest 4.7.0）、worklets **0.10.1**（0.13.0）、gesture-handler **`~2.32.0`**（3.3.0，**差一个大版本**）、screens **`~4.26.0`**、flash-list **2.0.2**、svg **15.15.4**。**"数值取自 npm latest"是本项目最容易立刻出事的一类错误。**

**9.10 能换成官方实现的，优先换掉第三方原生依赖**：`@expo/ui` 自带 **8 个 drop-in 替代**（`@gorhom/bottom-sheet`、`@react-native-community/datetimepicker`、`@react-native-masked-view/masked-view`、`@react-native-menu/menu`、`react-native-pager-view`、`@react-native-picker/picker`、`@react-native-segmented-control/segmented-control`、`@react-native-community/slider`）→ 优先用官方实现替换社区库，以降低 11.4 的 OTA 负担。

**9.11 第③层禁止作基座**
1. ⛔ 禁止把**自带完整调色板与字阶**的 UI kit 作为组件基座（`react-native-paper`、`tamagui`、`react-native-ui-lib`、`@ui-kitten/components`、`react-native-magnus`、`react-native-elements`、`@rneui/themed` 等）。
2. ⛔ 禁止引入**样式引擎**（`nativewind` / `@shopify/restyle` / `react-native-unistyles` / `tamagui` 的 styling 部分）：RN 的 `StyleSheet` + 令牌层已足够。本项目的问题不是"样式写得麻烦"，而是"**没有唯一令牌来源**"。
3. **判据必须是"默认渲染"，不是"脚本是否变绿"**（v1.1 修正，这一点极易被误用）：
   `design-debt-report.js` **只扫我们的 `src/`**，`node_modules` 里的硬编码色值**不会被计数、但运行时照样生效** —— 因此"两把尺子全绿"**不等于**"视觉自主"。
   **唯一有效的判据**：**装上该库、不改它的主题，渲染一个 `Button`，得到的是不是我们的 CTA？**
   实测（解包逐文件正则统计，口径与偏差见[组件层调研 §6.1](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)）：`react-native-paper@5.15.3` **1072 处色值 / 99 处 `fontSize` 字面量**且自带 M3 token 文件；`tamagui/themes` 1910 处色值；`react-native-magnus` 279 处；`react-native-elements` 148 处。
   ⚠️ **反例警告**：`@rneui/themed` 实测 **0 色值 0 字号**，但默认 theme 仍是外来视觉 —— **"字面量为 0"既不充分也不必要**。

**9.12 ⛔ 禁止把"运行期才确定的颜色"作为令牌层取值**（含 M3 Dynamic Colors / Material You）
- 若开启动态取色，表面/强调色的实际取值由**用户壁纸**决定 → **`contrastRatio` 无法在构建期预先算定** → 违反 2.3 条。**因此系统动态色不得作为本项目令牌的取值来源。**
- ⚠️ **这不等于不能用 `@expo/ui`（v1.1 精确化）**。三条不冲突的用法：① 给 `Host` 传 **`seedColor` = 本项目品牌主色**，把系统控件锚定到我们的色而不是壁纸；② 用 `colorScheme` **显式 lock** 到 light/dark，不用 `'unspecified'`；③ 把 `@expo/ui` 原生控件当"**平台控件**"，我们自己的令牌层只管自绘组件，两者通过同一 `seedColor` 对齐。
- **待脚手架期实测**（不得当已成立）：`seedColor` 是否在所有 M3 组件上完全覆盖动态取色；`getMaterialColors` 返回的 8 位 `#RRGGBBAA` 能否直接进入 `contrast-check.js` 的解析路径。

**9.13 依赖"最后发布时间"是准入项**：3.4 的依赖准入必须包含**最后一次发布时间的实测值**。
- ⚠️ **取值方法**：必须读 **`npm view <pkg> time --json` 里该版本自己的时间戳**。**不得用 `time.modified`** —— 它是"元数据最后被修改的时间"，会被 dist-tag 变更或新版本发布污染（实测：`react-native-paper` 的 `time.modified` = 2026-06-16，那是 **alpha 版**发布的时刻，而 `latest` 版 `5.15.3` 实际发布于 **2026-05-26**）。
- 各候选的实测发布日与维护信号见[组件层调研 §2.1](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)，**本宪法不复述具体日期**（避免二次转述失真）。

**9.14 ⛔ 禁止组件嵌套套壳（所有者 2026-10-01 裁决）**
「全局组件化」（1.4）的反面是"一层套一层的壳"。以下四类**一律禁止**：
1. ⛔ **透传壳**：组件存在的唯一作用是转发 props 或渲染**恰好一个**子组件（`XxxContainer` / `XxxWrapper` / `XxxBox` 式包装；真正的 Context Provider 除外）。
2. ⛔ **同语义多层**：一个语义单元被拆成 **≥3 层**视觉嵌套容器（如 `Card > CardBody > CardContent`）。**同一语义单元至多 2 层**（容器 + 内容）。
3. ⛔ **为复用而抽象**：只有 **1 处**使用的"通用"组件。**一处使用 = 就地写；两处出现才抽组件。** 这同时消灭了"组件库写了 0 引用"的反面——写出来就必然有人用。
4. ⛔ **样式壳**：一个组件只为了给另一个组件加 margin / 背景。应当直接应用**间距与表面令牌**，而不是多包一层。
**判据（可 review，一句话）**：*删掉这个组件、把它的内容上提一层，是否丢失任何行为？* 不丢失就是壳，**必须删**。
**依据**：所有者 2026-10-01 决定；与 1.4 同源 —— 每多一层壳，一次全局改动就要多穿一层。

**依据**：[调研-03 §6](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)、[基座调研 §9.6](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)、[App组件层调研](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)（含 `@expo/ui` 官方原文、`react-native-paper` 官方 README、各包 npm 一手实测）、旧 v1 实测。

## 第 10 条 四态与离线（数据层要求）

**10.1 四态是屏级交付物**：每屏都必须定义**加载 / 空 / 错误 / 无网**四态。

**10.2 空态分三类**（首次无数据 / 用户动作无结果 / 错误管理型），各自动作不同；空态**替换掉**组件本体；一个空态只给一个最重要动作；空间有限时只用文字不塞插画。

**10.3 加载先给东西看**（骨架/占位），不是先给空白；知道时长用确定性指示器；**不配"loading…"这类无信息量文字**；分页必须有明确状态机（`refresh/append/prepend × NotLoading/Loading/Error`，错误带 retry）。

**10.4 错误提示必须具体到「可感知 / 可理解 / 可改正」（所有者 2026-10-01 裁决）**
⛔ **禁止笼统措辞**：「出错了」「操作失败」「网络错误」「请稍后重试」「系统繁忙」—— **这些一律视为未完成**。
每条错误必须同时给出三件事：

| 要素 | 要求 | 反例 → 正例 |
|---|---|---|
| **可感知** | 指明**具体对象**（哪个字段 / 哪条内容 / 哪个操作） | 「操作失败」→「食堂评价提交失败」 |
| **可理解** | 说明**真实原因**，可归因，不甩锅给"系统" | 「网络错误」→「图片 3.2 MB，超过 2 MB 上限」 |
| **可改正** | 给**一个可执行动作**，动词开头，用户立刻能做 | 「请稍后重试」→「换一张小于 2 MB 的图片」 |

- **技术细节不得外泄**：不显示 HTTP 状态码、堆栈、SQL、内部错误码原文；但**也不得**用"未知错误"掩盖已知原因。
- **一个错误只给一个主行动**；有次行动时降级为文字链接。
- **网络类必须区分三种**：「无网络」/「服务不可达」/「超时」—— 因为用户能做的事不同。
- 校验类错误**就近显示在字段旁**，摘要置顶并把焦点移过去。
- 用户预期会成功的操作**不弹成功提示**；预期内的删除**不警告**。

**10.5 文案纪律：杜绝说明性文字（所有者 2026-10-01 裁决）**
1. ⛔ **禁止说明性 / 解释性段落** —— 不出现"这个功能是用来…"、"你可以在这里…"、"注意：…"这类旁白。
2. ⛔ **禁止用文案弥补设计缺陷**：一个操作如果需要一段话解释，**改设计，不是加文案**。
3. ✅ **文案必须简短**：按钮 / 标签 **≤6 个汉字**（英文 ≤2 词）；标题 ≤12 个汉字；正文说明（仅错误与合规场景允许存在）≤30 个汉字。
4. ✅ **只留三类文字**：**标识**（这是哪里 / 这是什么）、**动作**（按了会发生什么）、**状态**（现在怎么了）。不属于这三类的，删。
5. ⛔ **禁止占位废话**：`加载中…`、`暂无数据`（空态必须给动作，见 10.2）、`请稍候`。
6. **错误与合规文案是唯一允许超出上述长度的例外**（10.4 要求具体、条款要求完整），但**仍须先短后详**：一句话结论 + 可展开细节。

> **与 10.4 的关系**：**"简洁"不等于"含糊"。** 具体指**信息量**，简洁指**字数**。两者不冲突；冲突时**以 10.4 为先**。

**10.6 离线优先是数据层架构，不是一张提示图**
- **本地是唯一数据源**：UI 只读本地，网络只由 repository 写入本地；
- **Cache then network 优于 Network falling back to cache**；
- 高频且变化不快的内容（食堂 / 课表 / 树洞列表）应"**先给本地、再刷新**"。

**依据**：Android 官方 offline-first、web.dev offline cookbook、Carbon 三类空态、Apple HIG Loading、GOV.UK 错误规范（均见 [调研-01 §7](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md)）。

## 第 11 条 构建 / OTA / 发布纪律

**11.1** 采用 **CNG + `npx expo prebuild`**；`android/` 与 `ios/` **保持 gitignored 不提交**。

**11.2** 构建与提交统一走 **EAS Build / EAS Submit**；CI 用 `EXPO_TOKEN` 非交互认证。

**11.3** `runtimeVersion` 采用 **`fingerprint`**（优先保证不漏 bump 原生变更）**待定项**。

**11.4** **依赖清单中标注"原生依赖=有"的任何变更 → 必须重新构建并走商店审核**；只有纯 JS / 资源变更才可走 OTA。

**11.5** OTA 发布**必须支持渐进（rollout）与回滚**；生产前先在 preview channel 验证。

**11.6 签名铁律**：upload key 与 app signing key **分离**；upload key **不入库**，交由 EAS credentials / CI secret 管理；使用 **Play App Signing**，并把 **Google 侧 app signing key 指纹**登记给所有依赖签名的第三方。

**11.7 原生代码写法**：原生 Swift **优先写成本地 Expo Module 放在 `modules/`**，**不放进 `ios/`**（`prebuild --clean` 会抹掉手改）；必须改 prebuild 产物时应写成 **config plugin**。

**11.8 iOS 混编边界**：**凡 `@expo/ui` 已提供的原生组件，不允许自写原生实现**（iOS 用 `@expo/ui/swift-ui`，Android 用 `@expo/ui/jetpack-compose`，跨端用 `@expo/ui/universal`）。任何"为 iOS 单独写原生"的决定**必须附 ADR** 并说明为何 `@expo/ui` 不可用。
- ⚠️ **必须配一条兜底（v1.1 修正）**：`swift-ui` 与 `jetpack-compose` 两个入口**互不相通**（同一份 UI 不能两端跑），`universal` 入口的组件面明显更窄（缺 Card / Chip / Tab 等）。→ **表现层组件（消费本项目令牌的那一层）仍然必须自研**。`@expo/ui` 的真实角色是「**原生控件地基 + 逃生舱 + 官方 drop-in 替代来源**」，不是表现层组件库。
- ⚠️ **布局约束的准确范围（勿扩大，v1.1 修正）**：官方原文是 *"Flexbox styles apply to the `Host` component itself. **Once you are inside the native context**, Yoga is not available."* —— **限制只存在于原生 context 内**：`swift-ui` / `jetpack-compose` 入口内须用 `HStack`/`VStack` / `Row`/`Column` 并包在 `Host` 内；而 **`universal` 入口本身走 RN 的 `View` + Flexbox**（实测 `universal/Row` 即 `{flexDirection:'row'}`，见[组件层调研 §4.4.3](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)）。
  ⛔ **不得把本条写成"`@expo/ui` 不能当跨端布局基座"** —— 那会误杀 `universal` 路线。
- Nitro Modules **仅在有明确性能测量证据时**引入（当前 0.37.x，<1.0，未声明 production-ready）。

**依据**：[基座调研 §7/§9.3/§9.4](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)。

## 第 16 条 图标体系（两层，所有者 2026-10-01 裁决）

**16.1 两层归属（判据唯一）**

| 层级 | 适用范围 | 来源 |
|---|---|---|
| **第 1 层：品牌位 / 自绘位置** | 我们自己绘制在任何内容里的图标：顶栏动作（信箱）、列表与卡片内的语义图标、功能区图标、空态/错误态、发布 FAB | **Lucide**（`lucide-react-native`） |
| **第 2 层：系统控件位** | 由系统容器**自己提供**图标的位置：原生 Tab 栏、原生导航栏的返回/设置项、原生菜单、ActionSheet、日期选择器、分享面板、系统对话框 | **平台原生**：iOS 用 SF Symbols（`expo-symbols`）；Android 用 Material Symbols（`@expo/ui` 的 `Icon` 或原生容器自带） |

**判据（一句话）**：**这个图标是我们画在内容里的，还是系统容器自己提供的？** 前者 Lucide，后者平台原生。
⛔ **禁止任意混用**：不得在品牌位用 SF Symbols，也不得往系统控件位塞 Lucide 图标。

**16.2 禁止项**
1. ⛔ Emoji 与 Unicode 符号字符（1.3.6）。
2. ⛔ 为单个图标引入**第二个**图标库。
3. ⛔ 让第 1 层的描边风格与第 2 层的光学重量明显打架（两层之间允许不同，但同一层内必须一致）。
4. ⛔ **图标不得承担唯一语义**：纯图标按钮**必须有可读标签**（7.2）。

**16.3 尺寸与光学重量**
- 图标尺寸**从字阶令牌派生**（与相邻文字成比例），**不得在屏内写魔法数字**；**stroke 宽度全局统一**，不逐处调整。
- 同一含义在全局**只能有一个图标** —— 这是 1.4「一改全部改」在图标上的落地。
- 【提案】具体档位与 stroke 值**须在脚手架期用真机定稿**，不得当已验证规格使用。

**16.4 无障碍**
- 承载语义的图标必须给**可读标签**；纯装饰图标必须**从无障碍树中隐藏**。
- TalkBack / VoiceOver 下逐个核对（13.1）。

**16.5 第 1 层的实现纪律（`lucide-react-native`）**
1. ⛔ **禁止 barrel 导入** —— 必须逐图标子路径导入：`import X from 'lucide-react-native/icons/<kebab-name>'`。
   依据：Lucide 官方 RN 文档原文 —— *"In practice this tree-shaking does **not** currently work reliably for `lucide-react-native` barrel imports"*。逐图标导入同时绕开 Expo 的两个**实验性**开关（`EXPO_UNSTABLE_TREE_SHAKING` / `EXPO_UNSTABLE_METRO_OPTIMIZE_GRAPH`）。**这是性能红线，不是风格偏好。**
2. **`strokeWidth` 全局统一取 2，只在 Provider 设一次**；⛔ 禁止在任何调用点传 `strokeWidth`。（实测 1857 个图标全部按 24×24 网格 / stroke 2 设计，无一处例外。）
3. ⚠️ **许可证必须登记为双许可**：`ISC` **＋** 约 140 个 Feather 派生图标（含 `check` / `search` / `upload` / `x` / `arrow-left` / `log-in` 等常用项）为 **MIT（© Cole Bemis）**。依据：包内 `LICENSE` 文件原文 —— **`npm view` 只报 ISC，是不完整的**。
4. ✅ **实测 0 个原生文件**（9619 个文件扫描）→ **可走 OTA，不占原生发版窗口**（与 `@expo/ui` 的 231 个原生源文件形成对照，见 3.4）。
5. **图标名以实测名单为准，不得凭记忆写。** Lucide 1.x 已重命名/移除若干"肌肉记忆"名：`filter`→`list-filter`、`more-horizontal`→`ellipsis`、`alert-circle`→`circle-alert`、`trash-2`→`trash`。**写错的表现是不透明的模块解析失败，不会提示"已重命名"。** 全部 20 条替换见[图标方案调研](../../06-Analyze/tech-research/App图标方案-Lucide与平台图标.md) 的缺口清单。**不允许在未经核实的情况下新增图标名。**

**16.6 第 2 层的实现纪律**
1. ⛔ **Web 端必须另择来源**：`@expo/ui` 的 `Icon` **在 Web 上什么都不渲染**（官方加粗原文：*"Note: `Icon` does not render on web."*）→ Web 走 `expo-symbols` 的 `web` 槽位。
2. ⚠️ **更正仓库既有表述**：`expo-symbols` **不是 iOS-only** —— SDK 57 官方 front-matter 为 `platforms: ['android','ios','tvos','web','expo-go']`，Android / Web 走 **Material Symbols**。
3. **Tab 图标属于平台资产**：原生 Tab 栏由系统绘制（4.3 禁止自绘），因此 Tab 图标以**平台图标名**传给原生 API（Material Symbols 名 / SF Symbol 名），⛔ **不是 Lucide 组件**。四个 Tab 的 Material Symbols 名已逐个核实存在；**SF Symbol 名属【提案】**，须用 Apple 官方 app 核对（SF Symbols 名单不在任何 npm 包中，无法离线核实）。

**16.7 第 2 层的无障碍兜底（否则 16.4 的验收必然失败）**
- `@expo/ui` 的 `Icon`：`accessibilityLabel` **仅 Android 生效**（官方原文：*"iOS accessibility is not yet wired up."*）。
- `expo-symbols` 的 `SymbolView`：**根本没有 `accessibilityLabel` prop**。
- → ⛔ **不得寄望图标组件自带标签**：第 2 层图标**必须由包装层在可聚焦父级上补标签**。
- ⚠️ 实测陷阱：**不得用 `aria-hidden` 隐藏第 1 层图标** —— `hasA11yProp` 把 `aria-*` 一律判为"有语义"，反而会把它暴露给读屏。装饰性图标用第 1 层自己的隐藏手段。

**16.8 「屏蔽」的语义分叉（一个图标不得承载两个含义）**
16.3 的正向要求是"同一含义只有一个图标"；**反向同样成立**。"屏蔽"在本项目有两个**不同功能**：

| 功能 | 图标 | 依据 |
|---|---|---|
| **屏蔽某个用户**（Play 合规必需） | `user-x` | 宪法第 12 条表第 5 项 |
| 屏蔽某类内容 / 筛选（若将来要做） | `shield-ban` | 需**另立需求**，不得复用上行的图标 |

**依据**：所有者 2026-10-01 决定；Web 侧实测 346 个 JSX 文件 **emoji 0 次且无图标库**；平台原生图标能力见 [基座事实核对](../../06-Analyze/tech-research/App基座事实核对-版本线与上架门槛.md)；**图标名清单、20 条缺口替换、14 条首周真机验证清单**见 [App 图标方案调研](../../06-Analyze/tech-research/App图标方案-Lucide与平台图标.md)。
