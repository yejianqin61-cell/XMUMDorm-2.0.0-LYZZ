## 2. 发生了什么

用户发帖时收到以下错误：

```json
{
  "status": -1,
  "code": "TERMS_CHECK_FAILED",
  "message": "服务器错误，请稍后重试"
}
```

服务端的实际调用链是：

```text
POST /api/posts
  -> requireCurrentTerms
  -> SELECT user_terms_acceptances
  -> 目标库缺少表
  -> TERMS_CHECK_FAILED
  -> HTTP 500
```

迁移 070 创建 `user_terms_acceptances`，保存 `user_id`、`terms_version` 和 `accepted_at`。

迁移 076 为 `posts` 增加 `content_origin` 和 `repost_source`，它与条款门禁不是同一条依赖链。

因此，只执行 076 不能使发帖链路完整。PR 中 mock 了 `requireCurrentTerms`，所以路由测试通过，却没有暴露目标库缺表的问题。

本轮没有替用户自动写入接受记录。用户必须在 Web 界面确认当前版本，服务端仍然是最终门禁。

## 3. 以后怎么查

### 迁移检查

线上或本地需要按顺序执行完整的增量迁移入口：

```text
node scripts/run-incremental-migrations.js
```

不要只凭 PR 标题、最后一个文件名或“看起来相关”的迁移文件判断数据库是否就绪。

迁移后先检查表：

```sql
SELECT TABLE_NAME
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN ('user_terms_acceptances', 'posts');
```

再检查帖子字段：

```sql
SELECT COLUMN_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'posts'
  AND COLUMN_NAME IN ('content_origin', 'repost_source');
```

最后检查真实业务查询，而不是只检查迁移命令的退出码。条款查询失败时，应保留明确的数据库错误信息，并在接口层转换为可定位的服务错误。

### 功能交付检查

服务端条款门禁和 Web 条款 UI 是一个完整功能的两个部分：

```text
登录用户
  -> GET /api/users/me/terms
  -> 未接受当前版本：显示 TermsAcceptanceGate
  -> POST /api/users/me/terms/accept
  -> 接受成功：解锁发帖表单
  -> 服务端再次校验当前版本
```

前端测试可以 mock 服务端门禁，但至少还要有一条真实数据库查询链路的检查。否则测试只证明代码分支存在，不能证明目标环境具备运行条件。

## 4. 复盘后的工作方式

- 数据库变更先确认目标库，再执行完整增量迁移入口。
- 执行后同时检查表、字段和实际业务查询。
- PR 描述列出所有迁移依赖，不把“本次主要迁移”当成“全部必需迁移”。
- 条款接受必须是用户明确操作，不能为了绕过门禁替用户写记录。
- 涉及用户可见状态的服务端门禁，要同步交付对应的 Web 状态界面。
- 运行 mock 测试后，再补一条连接目标配置的最小真实链路验证。
