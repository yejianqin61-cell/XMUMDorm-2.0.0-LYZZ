## 1. 为什么先做这条

契约要求「戊先修正管理端点并写一条真实结构的接口测试，再接 App 管理页」。未修正前，管理端课程测评列表读的是不存在的列，接口必然 500 或返回空，App 管理页无从接入。

## 2. 事实与证据

- 真实表结构：`course_reviews` 有 `course_name`、`teacher`、`rating`、`difficulty`、`comment`、`created_by`、`deleted_at`（`migrations/017_handbook.sql:148-161`、`migrations/018_course_reviews_comment.sql:8-9`）。
- 管理配置读的却是不存在的列：`cr.title`、`cr.content`（`routes/admin.js:1240-1248`）。
- 列表默认过滤 `deleted_at IS NULL`（`routes/admin.js:1277-1279`），软删后无法在列表中找到目标，而恢复接口存在（`:1389-1394`）→ 恢复入口不可达。
- 现有 `__tests__/routes/admin.test.js` 全量 mock `query`，只校验调用次数，不校验列名，所以测试全绿也发现不了该缺口。

## 3. 改动范围

- `routes/admin.js`：修正 `course-review` 模块配置；列表接口支持 `includeDeleted=1`。
- `__tests__/routes/admin.courseReview.test.js`：新增，从迁移文件解析真实列集，校验配置引用的列、接口返回结构、软删可见与恢复。

不涉及：数据库迁移、App 路由（归甲）、前端页面。

## 4. 验收

- [x] `cr.*` 引用的每一列都存在于迁移定义的 `course_reviews` 中
- [x] 列表返回 `title`=课程名、`content`=测评正文，含教师与评分
- [x] `?includeDeleted=1` 能看到软删记录，默认看不到
- [x] 详情可打开已软删记录，恢复后 `deleted_at` 清空
- [x] `npx jest __tests__/routes/admin` 通过

## 5. 风险与未验证

- 【已定】测试用「迁移文件解析出的列集」当结构真源，不连接 MySQL；能抓住列名错误，抓不住权限与真实执行计划。
- 【提案】后续可在有 MySQL 的环境加一条 opt-in 集成测试（沿用 `shopCoupons.integration.test.js` 的模式）。
