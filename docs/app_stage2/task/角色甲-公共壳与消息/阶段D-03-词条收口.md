## 2. 开发者需要知道的

**先读**

- `app/src/__tests__/p0-03-i18n.test.ts:56-111,225-263` — 门禁四件：中英键集合相等、禁用词 0 命中、字数约束、⛔ 无内联 `isZh ?`。

- `app/src/i18n/en.ts:441-473` — 英文对照（⛔ 必须逐个同步，不许只改中文）。
- `docs/app_stage2/task/角色甲-公共壳与消息/阶段A-03-保存词条入字典.md` — 阶段 A 新增 5 条保存词条的登记方式。

**已定**

- 词条表是**平坦 key → string**，命名空间收敛在已知前缀里（`mailbox.` 已登记）；⛔ 不新增命名空间。
- 中英必须同键同数；⛔ 页面里不出现内联双语三元（门禁 7A 扫描 `app/src`）。
- 宪法 10.5：按钮/标签中文 ≤6 汉字、标题 ≤12 汉字（`mailbox.*` 不在长度门里，但也不写说明性旁白）。

**边界与接缝**

- 只改 `zh.ts` / `en.ts` 的文案值，⛔ 不改 key 名、不动其他角色文件。
- 接缝：`p0-03-i18n` 门禁用例（既有，不新增接缝）。

**运行**

- `cd app && npx jest src/__tests__/p0-03-i18n --ci`
- `cd app && npm run typecheck`

**未知**

- 阶段 A–C 的词条是否有「只加了一边」的漏项：门禁 1A 会直接红；若红，补齐而不是删 key。
- `mailbox.empty.*` 位于通知分类的空态里，改文案时要保证英文不出现被禁词（`Please try again later` 一类）。

## 3. 工作流

1. 读四个入口并一句话复述：本任务只改词条值与核对，不改行为。
2. 先跑一遍 `p0-03-i18n`，记录改动前基线。
3. 改 `mailbox.empty.description` 中英各一条：交易分类已改为会话列表，通知空态不再包括交易。
4. 反查阶段 A–C 新增的 9 条词条（保存 5 条、二手 3 条、提醒说明 1 条）中英是否都在。
5. 再跑门禁 + typecheck；若发现只加了一边，补齐后再跑。
6. 提交。
