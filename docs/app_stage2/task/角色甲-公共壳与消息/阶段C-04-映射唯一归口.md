# 阶段C-04 · 通知/提醒映射的唯一归口（R-3，D-3＝进）

## 1. 本任务的位置

- **阶段 C 提醒与通知归口**。本任务把「本地提醒载荷 → 路由」并进甲的目标映射文件，避免两套映射。
- **前置**：C-02 的宿主已存在（可同批）。**后置**：无。

## 2. 开发者需要知道的

**先读**

- `app/src/features/mailbox/targets.ts` — 甲的唯一目标映射（服务端 target → 路由/说明）。
- `app/src/features/tools/reminders/navigation.ts:14-48` — 乙的本地载荷解析（三态）。
- `app/src/features/mailbox/MailboxScreen.tsx` — 唯一消费 `resolveTarget` 的地方。
- `docs/app_stage2/task/甲-.../开发设计文档-甲-四角色接线整合.md` R-3 — 两类输入共享同一种结果类型。

**已定**

- **D-3 团队领导决定：本地提醒载荷也进同一处映射**（`targets.ts`），页面/宿主不再自行拼路由。
- 两类输入产出**同一种**结果类型（route / unavailable / ignore），服务端 target 的语义不搬进本地适配器。
- ⛔ 不把本地载荷塞进服务端通知响应结构。

**边界与接缝**

- 在 `targets.ts` 增加"本地提醒载荷 → 结果"的唯一入口；C-02 的宿主改为调它；不动服务端。
- 接缝：目标映射文件的纯函数出口（表驱动）。

**运行**

- `cd app && npx jest src/__tests__/s2-30-notification-mapping src/__tests__/s2-09-notification-targets --ci`
- `cd app && npm run typecheck`

**未知**

- 本地载荷归属其他账号时返回 ignore 还是 unavailable：按"不跳转且不解释"处理，用例写清。

## 3. 工作流

1. 读四个入口并一句话复述。
2. 写用例 1（本账号可用载荷 → route 带 week/course），红。
3. 在 `targets.ts` 加唯一入口并让 C-02 宿主调用，绿。
4. 补用例 2（非本账号 → ignore）、用例 3（缺目标 → unavailable）。
5. 加源码断言：页面层不再出现第二处通知/提醒载荷解析。
6. 跑用例 + typecheck，提交。
