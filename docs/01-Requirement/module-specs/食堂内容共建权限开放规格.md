# 食堂内容共建权限开放规格

**Status:** ready-for-agent

## Problem Statement

食堂信息的实际来源是校园用户整理的商铺、菜单、价格与图片，而当前产品仍沿用“商家后台”模式：只有商家角色或管理员能创建商铺，且商铺、菜品、分类的大部分编辑与删除又要求操作者必须是原店主。一个账户已创建过商铺后，也不能继续补充其他分区的商铺。

这使普通学生即使发现菜单缺失、价格变化或分类错误，也不能在正在浏览的分区或商铺内补全信息；现有维护入口还集中在与浏览路径割裂的旧商家页面。食堂模块的内容共建定位与实际权限、入口不一致。

## Solution

将食堂商铺、菜品和分类改为“所有登录用户共同维护”的内容：学生、商家和管理员在同一套浏览页面中，都可创建和编辑这些内容；商铺与菜品的删除仅管理员可执行；未登录用户仍只能浏览。

维护入口应贴近信息所在位置：在分区商铺列表提供添加商铺入口，在商铺详情/菜单页提供编辑商铺、增删改分类、添加及管理菜品的入口。现有商家专用管理流程不再是唯一途径，可在兼容期内保留，但其权限能力与共建入口一致。

不新增一套内容接口或角色体系。现有商铺、分类、菜品 CRUD 接口继续承担职责，仅将业务授权从“商家角色/店主/管理员”收束为“有效登录用户”，并保留所有安全和数据完整性约束。

## User Stories

### US-001：普通用户新增分区商铺

作为已登录用户，我可以在任一食堂分区的商铺列表中发起“添加商铺”，填写名称并选择当前分区，以便补充尚未收录的商铺。

### US-002：连续补充多个商铺

作为已登录用户，我可以在不同分区或同一分区继续新增商铺，不会因自己此前创建过一间商铺而被阻止。

### US-003：未登录用户的创建引导

作为未登录用户，当我尝试任意食堂内容维护操作时，我会被引导登录；服务端也必须拒绝没有有效身份凭证的写请求。

### US-004：所有登录角色使用同一权限

作为学生、商家或管理员，我都能对任意未删除商铺执行创建与编辑操作；商家身份和最初创建者不再是这些共建操作的授权门槛。

### US-005：编辑已有商铺

作为已登录用户，我可以从商铺页面进入编辑，修正店名、营业时间和店铺图片等已有字段；保存后，当前页面和分区列表能反映最新信息。

### US-006：删除商铺

作为管理员，我可以删除错误、重复或已撤销的商铺；系统在执行前要求明确确认，删除后商铺不再出现在正常浏览和搜索结果中。普通登录用户不显示、也不能调用该操作。

### US-007：创建分类

作为已登录用户，我可以在任意商铺菜单内新增分类，例如“主食”“饮品”，以便为菜品归类。

### US-008：维护分类

作为已登录用户，我可以修改分类名称和排序，也可以删除分类。删除分类时，原分类下仍存在的菜品被保留并变为未分类，不被连带删除。

### US-009：新增菜品

作为已登录用户，我可以在任意商铺的有效分类下添加菜品，填写名称、描述、价格并按现有能力上传图片。

### US-010：维护已有菜品

作为已登录用户，我可以从菜品或商铺菜单的维护入口编辑菜品资料、所属分类、价格和图片。菜品删除仅由管理员在确认后执行。

### US-011：空商铺也可共建

作为已登录用户，进入没有分类或没有菜品的商铺时，仍能看到添加分类、添加菜品所需的入口，不会因空状态而失去维护路径。

### US-012：维护后即时一致

作为操作用户，创建、编辑或删除成功后，我会回到合理的上下文；相关商铺列表、菜单、分类、菜品详情和排名数据会刷新，不显示旧内容。

### US-013：保留创建者追溯

作为运营者，商铺仍保留最初创建者关联用于历史追溯，但该关联不再限制其他登录用户的新增和编辑操作，也不替代管理员删除权限。

### US-014：保持现有内容质量约束

作为平台用户，我提交的店名、分类、菜品字段及图片仍须经过现有的必填、类型、长度、敏感词和文件格式/大小/数量校验；开放共建不降低这些标准。

### US-015：处理目标已变化的情况

作为已登录用户，若我保存或删除时目标已被他人删除或无效，系统向我展示明确失败信息并刷新当前数据，而不是显示错误的成功状态。

### US-016：旧商家入口兼容

作为既有商家用户，我仍可使用已有的商家管理路径完成食堂信息维护；该路径不能继续要求商家角色或仅限本人店铺，也不能成为普通用户无法到达的唯一功能。

## Implementation Decisions

1. “所有用户”在本规格中定义为所有已登录且身份凭证有效的用户；不开放匿名写入。所有食堂写请求继续经过现有登录鉴权。
2. 商铺、分类、菜品的读取范围维持现状；创建和编辑向所有登录用户开放。商铺与菜品删除仅管理员可执行；分类删除维持全体登录用户可执行的共建范围。
3. 服务端移除商家角色和店主归属对商铺、分类、菜品创建与编辑操作的业务拒绝；商铺和菜品删除保留管理员角色校验。无论哪类操作，均不移除身份认证、中间件、输入校验、敏感词过滤、上传校验或参数化查询。
4. 商铺创建不再执行“一名用户只能有一个未删除商铺”的限制。商铺的创建者关联继续写入，作为归属历史和可追溯信息，不作为以后修改或删除的权限条件。
5. 不因本次开放权限而删除或重定义 `merchant`、`admin` 等账户角色；它们在食堂内容维护之外的既有职责保持不变。
6. 延续现有软删除语义：删除商铺、分类、菜品不直接物理删除；其中商铺和菜品仅管理员可删除。正常查询、搜索和列表不再返回已删除记录。分类删除时，其菜品取消分类关联的既有行为保持。
7. 复用既有商铺、分类、菜品 CRUD 能力，不新增平行接口。客户端将旧“商家管理”页面逐步改造成可从指定商铺上下文进入的共建维护界面，避免依赖“我的店铺”才能工作。
8. 分区页的“添加商铺”入口对所有登录用户可见；未登录状态可显示同一入口但进入登录流程。创建表单预设当前分区，允许按已有表单规则调整分区。
9. 商铺页面必须提供清晰但不干扰浏览的维护入口，至少涵盖编辑商铺、管理分类、添加菜品和管理已有菜品。菜单为空时也必须保留相应入口。
10. 删除商铺、分类、菜品均需二次确认；商铺与菜品删除入口仅向管理员展示，且服务端必须再次校验管理员身份。确认文案说明其直接影响。任何失败不得在客户端乐观移除内容后静默吞错。
11. 成功写入后按受影响资源刷新缓存：分区商铺列表、商铺详情、分类列表、菜单/菜品列表、菜品详情，以及依赖这些数据的搜索与排名结果。
12. 现有“我的店铺”查询和旧路由可保留作兼容，但不应用于决定是否展示或允许共建维护操作。后续可在使用迁移完成后单独清理旧商家后台叙事。

## Testing Decisions

1. 覆盖服务端写接口的身份矩阵：普通学生、商家、管理员均能对自己与他人创建的有效商铺、分类、菜品完成创建与编辑；商铺、菜品删除仅管理员成功，学生与商家均收到拒绝；无凭证、过期或无效凭证均被拒绝。
2. 覆盖商铺创建：三种登录角色均可在任意有效分区创建商铺；同一用户创建第二间商铺成功；无效分区或空名称仍失败。
3. 覆盖商铺编辑和删除：非创建者可成功更新；仅管理员可软删除。删除后详情、分区列表、搜索及正常查询不再显示该商铺。
4. 覆盖分类创建、编辑、排序和删除：非创建者可维护；删除分类后其下菜品仍存在且为未分类。
5. 覆盖菜品创建、编辑和删除：非创建者可在目标商铺的有效分类下创建及编辑；仅管理员可删除；已删除或不存在的分类、商铺、菜品返回正确失败结果。
6. 保留并回归验证现有字段、敏感词、图片 MIME 类型、文件大小、图片数量及 multipart/JSON 更新校验。
7. 覆盖前端路径：从分区页新增商铺；从非本人创建的商铺进入维护并新增/编辑分类、菜品；确认商铺和菜品删除入口只对管理员展示；空商铺场景；未登录点击后的登录与回跳。
8. 覆盖写入后的刷新与导航，确保不需要手动重载即可看到创建、编辑、删除结果；失败时不丢失可恢复的表单输入。
9. 在 App 目标窄屏宽度下检查维护入口、表单、确认对话与错误提示的可操作性，并验证中英文文案不溢出。

## Out of Scope

- 匿名用户新增或编辑食堂内容。
- 新建内容审核、众包评分、举报流、版本历史、回滚、冲突合并或审批工作流。
- 更改账户角色管理、管理员后台权限或食堂以外模块的商家权限。
- 新增数据库表、改变现有食堂数据模型，或迁移历史创建者数据。
- 排名算法、点评/回复、收藏、订单、支付及食堂首页视觉改版。
- 因开放共建而自动合并重复商铺；重复治理可作为后续独立能力。

## Further Notes

- 当前实现中，写接口确实存在商家角色、店主归属和管理员条件，并非只需在前端展示按钮；本改动需要前后端同时遵守同一授权契约。
- 内容共建会增加信息质量风险，但本轮不以新审批机制阻塞用户已明确要求的开放权限；既有校验、软删除和创建者关联是本轮最低限度的可控边界。
- 运行态浏览器会话当前未连接，本规格基于路由、接口和页面实现通览形成；上线前应按本规格的端到端路径由人工验收。
