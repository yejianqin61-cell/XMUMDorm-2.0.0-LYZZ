# 通知系统性能与信箱体验治理规格

**Status:** ready-for-agent

**汇总跟踪：** GitHub Issue #17

**关联问题：** GitHub Issue #12、#13

**范围：** Capacitor App 信箱页面、共享通知 API 与通知查询所需数据库索引。Web 端继续兼容共享 API，但本轮不重做 Web 信箱界面。

## Problem Statement

用户首次打开信箱或切换通知类别时，需要等待通知列表和未读汇总两个请求。当前 App 首屏一次请求 50 条通知，查询还需要关联帖子和发送者；远程 Railway 数据库的单次往返和慢 SQL 会被直接放大为可感知的等待。切换类别会重复获取未读汇总，点击同一帖子聚合出的未读消息时又逐条调用已读接口，进一步制造不必要的 HTTP 和数据库请求。

信箱的信息架构和内容表达也不够克制。“全部”与三个业务类别并列，类别标题后附带数字徽标，使顶部区域拥挤；无标题通知会额外显示“（无标题）/ (Untitled)”；公告卡片同时显示公告类别和公告标题，可能出现两行重复的“公告”；同一帖子的点赞和评论虽然已按目标初步合并，但聚合范围只覆盖当前已加载的数据，点击后直接跳转帖子，用户无法在信箱内展开查看互动明细。接口已经返回是否还有下一页，页面却没有继续加载入口，超过首批上限的通知不可见。

## Solution

将信箱收束为“互动、事务、系统”三个稳定类别，默认进入互动类别，移除“全部”入口及类别标题后的未读数字。未读状态继续通过信箱全局入口和列表项的轻量视觉状态表达，不在每个类别标题旁重复计数。

通知首屏改为小批量渐进加载。列表响应同时提供当前用户的未读类别汇总，App 首次进入和类别切换只发起一个列表请求；客户端按类别缓存已加载结果，在有效期内返回已访问类别时立即复用。页面必须提供继续加载能力，直到服务端明确没有下一页。

同一帖子的点赞和评论合并为一个互动组。组标题区域负责展开或收起，展开后按时间展示该帖子的互动明细，并支持继续加载该组的完整历史；“查看帖子”作为组内独立操作进入帖子详情。展开或进入帖子时，使用已有批量已读能力一次确认该组的未读通知，不得逐条请求。

没有真实标题的通知不渲染标题占位行，正文直接承担主要信息。公告卡片不再显示额外的“公告 / Announcement”类别标签，只显示真实标题、正文、发送者和时间；真实标题为空时直接展示正文，不生成第二行“公告”占位文本。

服务端查询在生产结构上执行 `EXPLAIN` 和冷请求基线测试。优先通过减少客户端请求、降低首屏条数、复用批量接口和调整查询形状解决问题；只有现有索引不能覆盖实际过滤与排序时，才新增最小复合索引，并通过独立迁移及初始化结构同步交付。

## User Stories

1. 作为打开信箱的学生，我希望首批通知尽快出现，以便不用面对长时间骨架屏。
2. 作为网络条件一般的学生，我希望进入信箱只产生完成首屏所需的最少请求，以便减少远程数据库延迟对体验的放大。
3. 作为经常切换通知类别的学生，我希望返回刚刚查看过的类别时立即看到已有内容，以便不必重复等待。
4. 作为查看互动的学生，我希望默认直接进入互动类别，以便优先处理最常见的点赞和评论。
5. 作为信箱用户，我希望顶部只保留互动、事务和系统三个明确类别，以便快速判断消息归属。
6. 作为信箱用户，我希望类别标题后不再堆叠未读数字，以便顶部保持安静、易扫读。
7. 作为有未读消息的学生，我希望仍能从信箱入口和列表项状态判断是否有新消息，以便移除类别数字后不会失去必要反馈。
8. 作为收到多次互动的帖子作者，我希望同一帖子的点赞和评论收束为一个通知组，以便列表不会被同一内容反复占满。
9. 作为查看互动组的帖子作者，我希望点击组标题能原位展开详情，以便不离开信箱就能知道谁做了什么。
10. 作为查看互动组的帖子作者，我希望展开内容按时间展示点赞、评论人、评论摘要和发生时间，以便理解互动上下文。
11. 作为互动较多的帖子作者，我希望能继续加载该帖子的完整互动历史，以便展开结果不受信箱首屏分页限制。
12. 作为准备回复互动的帖子作者，我希望从展开区域使用明确的“查看帖子”入口进入详情，以便展开和导航不会争用同一次点击。
13. 作为处理聚合通知的学生，我希望一次操作即可将该组未读消息全部标记为已读，以便状态及时一致且不会产生多次请求。
14. 作为收到无标题通知的学生，我希望页面直接展示有意义的通知正文，以便不看到“无标题”这类无效占位文字。
15. 作为收到系统公告的学生，我希望公告只出现一次真实标题，以便不会看到两行重复的“公告”。
16. 作为收到无标题公告的学生，我希望直接看到公告正文，以便系统不凭空生成重复标题。
17. 作为历史通知超过首批上限的学生，我希望能够继续加载下一页，以便所有通知最终都可访问。
18. 作为清理信箱的学生，我希望清理操作只作用于当前类别，以便移除“全部”类别后操作范围仍然明确。
19. 作为中文用户，我希望通知类别、互动动作、公告、空状态和错误状态全部使用中文，以便页面不出现中英混杂。
20. 作为英文用户，我希望同一组内容使用完整英文文案，以便语言切换后不残留中文占位。
21. 作为维护者，我希望列表响应具有稳定的分页、目标、互动类型和未读汇总契约，以便 App 与 Web 共用后端时不会各自猜测数据含义。
22. 作为维护者，我希望性能改动有相同环境下的前后基线，以便确认优化来自请求和查询治理，而不是偶然的网络波动。
23. 作为维护者，我希望索引调整通过可重复执行的迁移交付，以便 Railway 和全新数据库保持一致。

## Implementation Decisions

- 本轮只治理当前 Capacitor App 使用的信箱体验与共享后端，不修改已弃用的 React Native 客户端。
- 信箱类别固定为 `interaction`、`transaction`、`system`，默认类别为 `interaction`；客户端不再请求或展示 `all` 类别。
- 类别 Tab 不显示数量徽标。全局未读总数仍可供信箱入口使用，列表项使用轻量未读状态，不新增说明性文案。
- 列表首批页大小从 50 收束为 20。后续页面沿用服务端 `hasMore` 契约，以明确的继续加载或触底加载方式追加，不覆盖已加载内容。
- `GET /api/notifications` 保持现有鉴权和类别过滤，并在响应中加入未读类别汇总；未读汇总与通知列表在服务端并发获取，客户端首屏不再额外请求未读汇总接口。既有独立未读汇总接口暂时保留，供其他调用方兼容使用。
- App 使用项目已经安装的服务端状态查询能力按“用户 + 类别”缓存列表，设置短暂新鲜时间并保留旧数据；不新增状态管理依赖，不引入 Redis。
- 普通帖子互动以稳定的帖子目标键聚合，点赞和评论属于同一组。公告、事务和无法定位目标的通知继续使用各自稳定目标键，不错误并入帖子互动组。
- 帖子互动组的摘要只负责聚合展示。组标题点击切换展开状态；导航帖子必须使用组内独立操作，避免一次点击同时展开和跳转。
- 展开互动组时，列表接口支持按帖子目标过滤互动通知，并继续使用分页契约。展开结果必须来自服务端完整目标范围，不能声称当前首屏中偶然聚合的项目就是全部互动。
- 互动明细至少包含通知 ID、动作类型、发送者、评论摘要、评论 ID、发生时间、未读状态和帖子目标。点赞不伪造评论摘要；已删除或不可访问的帖子显示不可用状态，不跳转到空白页面。
- 展开或进入帖子时，客户端收集该组未读通知 ID，去重后一次调用已有批量已读接口。批量接口只接受正整数 ID、去重、限制单批数量，并始终用当前用户 ID 约束更新范围。
- 没有真实标题时不渲染标题 DOM。正文生成逻辑继续使用“你的帖子 / your post”等自然宾语，不显示“（无标题）/ (Untitled)”。
- 公告卡片移除类别标签，只保留真实标题、正文、发送者和时间。真实标题为空时省略标题行；公告正文为空时才显示本地化空正文状态。
- 移除“全部”后，清理按钮只清理当前类别。系统公告继续遵循既有公告保留策略，不因普通清理操作被物理删除；已读状态与删除是两个不同动作。
- 通知列表排序使用稳定的“创建时间倒序 + ID 倒序”，避免相同时间戳在分页边界重复或遗漏。若继续使用偏移分页，必须通过回归测试锁定稳定顺序；本轮不强制迁移为游标分页。
- 性能验收先记录同一环境、同一用户、相同数据量下至少 10 次冷请求的中位数与 P95。优化后首次信箱列表的客户端请求数必须从 2 降为 1，中位耗时至少降低 40%，且不再出现由逐条已读造成的 N 次请求。
- 使用生产结构执行通知列表、类别列表、未读汇总和按帖子展开查询的 `EXPLAIN`。只有执行计划表明确显示现有索引无法覆盖用户过滤和时间排序时，才增加复合索引；禁止凭猜测叠加索引。
- 如需索引变更，必须新增下一编号迁移、同步全新数据库初始化结构，并记录回退方式；不得修改已经部署的旧迁移或在应用启动时执行 DDL。
- 保持现有通知类型、模块映射和写入入口，不在本轮重做全站通知生产链路。

## Testing Decisions

- 以通知 HTTP 路由作为后端最高契约测试边界，继续使用现有 Jest 与 Supertest 模式；测试可见响应、鉴权、过滤、分页和已读行为，不把具体 SQL 文本当作主要业务断言。
- 列表契约测试覆盖：默认分页、三个类别过滤、稳定排序、`hasMore`、响应内未读汇总、无标题目标、公告目标、已删除目标和数据库失败。
- 同帖互动测试覆盖：点赞与评论使用同一帖子目标、不同帖子不得合并、按帖子展开可跨页读取、评论摘要与动作类型正确、不可访问帖子不产生无效跳转。
- 批量已读测试覆盖：同组多个 ID 只进行一次更新、重复 ID 去重、非法 ID 拒绝、超出单批限制拒绝、其他用户的通知不能被修改、公告缓存按既有规则失效。
- 前端以信箱页面作为最高行为边界，覆盖默认互动 Tab、无 All Tab、无 Tab 数字、类别切换缓存、加载更多、同帖展开/收起、独立查看帖子操作、无标题省略和公告标题不重复。
- 当前 App 尚无既有前端自动化测试文件。本轮不为通知治理引入新的测试框架；优先使用项目现有浏览器验收能力验证页面行为，并将可纯化的通知分组逻辑放在现有测试工具能够覆盖的共享边界。若项目随后统一接入前端测试框架，再补页面自动化回归。
- 性能测试使用同一生产或生产等价 Railway 数据库、固定测试账号和相近通知数量，记录优化前后至少 10 次冷请求；不得使用命中客户端缓存或服务端缓存的结果冒充冷请求改进。
- Capacitor 实机验收覆盖弱网首次进入、类别切换、返回已访问类别、展开大量互动、批量已读、继续加载、中文模式和英文模式。

## Out of Scope

- 不申请 Android 或 iOS 系统级通知权限，不接入 JPush、FCM、HMS Push 或 Web Push。
- 不修改通知的全站生产规则，不新增点赞、评论、社团、食堂、二手或跑腿业务埋点。
- 不增加通知偏好、免打扰、声音、震动、推送时间段或用户订阅设置。
- 不重做 Web 端信箱视觉界面；仅保证共享 API 兼容。
- 不修改公告弹窗的内容、按钮和展示时机；本规格只处理信箱内公告卡片。
- 不引入 Redis、消息队列、搜索引擎或新的前端状态管理依赖。
- 不将通知表改造成事件溯源系统，不清洗全部历史通知数据。
- 不修改已弃用的 `mobile/` React Native 前端。

## Further Notes

- Issue #12 作为性能问题来源；Issue #13 第 5 项与其重复，实施时只维护一套性能验收数据。
- Issue #13 的同帖互动聚合当前已有客户端雏形，但只覆盖首批已加载通知，且整张卡片直接导航。本规格保留已有目标键资产，补齐服务端完整范围、原位展开和独立导航。
- 现有数据库已经有面向用户、类型、已读状态和时间的复合索引，但它不一定适合不指定类型和已读状态的时间流查询。是否新增索引必须由实际执行计划决定。
- 现有批量已读接口已经具备用户约束，本轮应复用并补充输入边界，不再维护逐条请求路径。
- `#12`、`#13` 在本规格实施和验收完成前保持开放；汇总规格 issue 用于承载统一开发与验收边界。
