## 一、已由所有者拍板的方向（不可在后续工作中擅自变更）

| 决策 | 内容 |
|---|---|
| 技术形态 | **真原生 App**（不是 WebView 套壳）；**以 React Native 为主**，**iOS 侧允许并预期混入原生代码** |
| 首发平台 | **Android 优先** |

## 二、为什么必须先立宪、后写码

旧 App v1 的失败已被实测证实为**约束缺失**，而非技术选型错误。实测数据（见 [`../../06-Analyze/ui-research/App设计调研-00-旧App设计债实测基线.md`](../../06-Analyze/ui-research/App设计调研-00-旧App设计债实测基线.md)）：

| 指标 | 旧 App v1 实测 |
|---|---|
| 硬编码色值 `#hex` | **1437 处 / 79 个文件** |
| `fontSize` 字面量 | **645 处** |
| 引用自有 UI 组件 | **0 次**（组件库写了 7 个，一屏未用） |
| `src/theme/` 令牌体系 | **不存在**（只有一个 469 B 的局部文件） |
| 暗色/外观 API | **0 次** |
| Reanimated / gesture-handler | 已安装，**0 引用** |

**推论**：旧 App 的问题不是"用了 Web 写法"，而是**每一屏都在自由发挥**。因此本阶段的成功判据不是"设计文档写得多漂亮"，而是**产出的约束能否被脚本验证**。

## 四、协作纪律（写入宪法候选条款）

1. **一个模块 = 一个写作用域 = 一个负责人**；令牌与原型组件由单一所有者维护，其他人只读。
2. **禁止并行修改** `tokens`、根布局、导航壳、原型组件。
3. **首个纵向切片必须先消费组件库与令牌**，通过后才允许模块铺开（旧 App 的组件库 0 引用就是这样发生的）。
4. **每完成一个模块立即过验收**，不留"最后统一验"。
5. **不得据已删除的旧文档写任何 App 代码**——旧设计材料只作历史参考，归档于 `app-legacy-v1`。

### 5.4 ⚠️ 阻塞级风险（必须在脚手架首周验证，不能等功能做完）

| 风险 | 内容 | 处置 |
|---|---|---|
| **R1：Android 上返回键可能直接退出 App** | target API 36 + Android 16 设备上，系统不再派发 `onBackPressed` / `KEYCODE_BACK`。RN 0.81 官方博客称 `BackHandler` 照常工作，但社区在 `react-native-screens` Discussion #2540 实测相反：RN 收不到事件 → 系统判定退出 Activity → **App 直接关闭**。上游 issue `expo/expo#39092` **至今 open**（标签指向 React Native Screens）。逃生舱 `android:enableOnBackInvokedCallback="false"`（官方支持、社区验证有效），**代价是没有系统返回预览动画 = 本机感有损** | **脚手架第一周做真机 spike**，结论决定导航架构；可能是 ADR。**在结论出来前，不锁返回栈的实现方案** |

> 该风险直接冲击「五格导航 + 各 Tab 返回栈」的设计，且它**没有纯 JS 解法**——属"必须先验证"的架构级未知项。
