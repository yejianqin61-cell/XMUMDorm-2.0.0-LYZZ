# 04 — 聚合通知批量已读闭环

**What to build：** 用户展开互动组或进入关联帖子时，一次性将该组当前可确认的未读通知标记为已读，并立即同步主列表、明细和全局未读状态，不再逐条发送请求。

**Blocked by：** 03 — 同帖互动组原位展开

**Status：** ready-for-agent

## 交付行为

- 展开互动组时收集该组未读通知 ID，去重后调用一次批量已读接口。
- 使用“查看帖子”进入详情前执行同一批量确认逻辑；确认失败不阻断导航，但需要保留可重试的未读状态。
- 批量成功后，主列表组状态、展开明细、当前类别缓存和全局未读汇总同步乐观更新。
- 服务端只更新当前登录用户拥有的通知，其他用户的 ID 即使被提交也不能修改。
- 输入 ID 必须为正整数、去重并限制单批数量；空数组、非法值和超限请求得到明确 400。
- 与公告弹窗共享的未读公告缓存继续按既有规则失效。

## 实施约束

- 复用现有批量已读端点，不创建逐条循环封装或新端点。
- 客户端一次用户动作最多产生一个批量已读请求。
- 乐观更新失败时回滚相关缓存或重新拉取权威状态，不允许永久显示错误的已读数。
- 重复展开已全部读取的组不再发送空请求。

## 验收标准

- [ ] 一个包含多条未读通知的互动组展开时只发送一次批量请求。
- [ ] 重复 ID 只更新一次，非法 ID 和超限批次被拒绝。
- [ ] 提交其他用户通知 ID不会修改其他用户数据。
- [ ] 成功后组未读样式、明细状态和全局未读数立即一致。
- [ ] 已全部读取的组再次展开不发送请求。
- [ ] 请求失败时通知仍可再次确认，不出现不可恢复的假已读状态。
- [ ] 查看帖子导航不会因已读请求失败被阻断。
- [ ] 公告弹窗缓存失效行为没有回归。

## 最小验证

- [ ] 路由集成测试覆盖成功、去重、非法输入、批次上限、用户隔离和数据库失败。
- [ ] 浏览器 Network 面板证明展开含多条通知的组只有一个已读请求。
- [ ] 浏览器验收成功与失败两种状态，确认乐观更新和回滚行为。

## 非目标

- 不新增“一键全部已读”。
- 不改变通知生成规则。
- 不将已读状态同步到系统级推送服务。
