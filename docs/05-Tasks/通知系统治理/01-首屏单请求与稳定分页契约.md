# 01 — 首屏单请求与稳定分页契约

**What to build：** 让用户首次进入信箱时，通过一次列表请求同时获得互动通知与未读类别汇总；列表使用小批量、稳定顺序的分页契约，为后续缓存、持续加载和互动展开提供可靠基础。

**Blocked by：** None — can start immediately

**Status：** ready-for-agent

## 交付行为

- 信箱默认请求 `interaction` 类别，首批页大小为 20。
- 通知列表响应继续返回 `list`、`hasMore`、`page`、`pageSize`，并新增按 `interaction`、`transaction`、`system` 汇总的未读数据。
- 列表和未读汇总在服务端并发获取；App 首屏不再额外请求独立未读汇总接口。
- 独立未读汇总接口继续保留，既有调用方不需要同时迁移。
- 列表排序固定为创建时间倒序、通知 ID 倒序；相同时间戳不能造成分页边界重复或遗漏。
- 目标、公告、发送者和本地化展示所需的既有响应字段保持兼容。

## 实施约束

- 复用现有通知类型与类别映射，不创建第二套分类常量。
- 不在本任务增加 Redis、数据库表或新依赖。
- 不把具体 SQL 文本当成外部契约；响应结构和可观察行为才是契约。
- 首屏请求数必须通过浏览器网络记录验证，不以代码阅读代替。

## 验收标准

- [ ] 已登录用户首次打开信箱只产生一个通知列表请求，即可渲染互动通知和更新全局未读数据。
- [ ] 默认类别为 `interaction`，默认页大小为 20。
- [ ] 响应包含三个类别的未读汇总，空类别明确返回 0。
- [ ] 同一创建时间的通知按 ID 倒序稳定排列。
- [ ] `hasMore` 使用多取一条的方式计算，但响应列表不泄漏额外记录。
- [ ] 第二页与第一页没有重复通知，也没有因相同时间戳遗漏通知。
- [ ] 独立未读汇总接口保持可用，旧调用方不发生回归。
- [ ] 未登录返回 401，非法类别或分页参数返回 400，数据库失败返回 500。

## 最小验证

- [ ] 通知路由集成测试覆盖默认请求、类别筛选、响应内汇总、稳定排序、分页边界和错误状态。
- [ ] 共享 API 测试或可运行检查确认 App 不再组合列表与汇总两个首屏请求。
- [ ] 浏览器 Network 面板保存一次冷启动记录，证明通知数据只有一个首屏请求。

## 非目标

- 不实现 Tab 视觉改造、类别缓存和加载更多 UI。
- 不实现同帖互动展开或批量已读。
- 不调整数据库索引；查询计划统一在任务 06 处理。
