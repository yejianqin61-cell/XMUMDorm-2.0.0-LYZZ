## 一、这份提案要回答什么

**设计哲学 = 产品性格 + 取舍原则。** 它不写视觉规范（那是风格体系），也不写技术方案（那是宪法）。

它只回答三个问题：

1. **这个 App 应该让人感觉"是什么"？**（性格）
2. **当设计与其它目标冲突时，谁让步？**（取舍原则）
3. **这些原则凭什么成立？**（必须能指回实测证据，而不是审美偏好）

> 之所以强调第 3 条：上一版《移动端宪法》也写了漂亮的性格描述（"苹果式舒适 + Discord 社区感 + 一点 Neo-Brutalism"），但它**没有一条能指回实测**，结果 1437 处硬编码色值照样发生。**没有证据支撑的哲学等于没有哲学。**

## 三、设计要真正解决的问题

| # | 问题 | 证据 |
|---|---|---|

> **设计哲学的价值不在于描述美，而在于给出可被脚本验证的约束。**

## 四、设计哲学的候选方向

三个方向都能回应 P1–P8，差别在**性格**与**代价**。

### 方向甲：**温暖的原生感**（推荐）

| 维度 | 内容 |
|---|---|
| **性格** | 亲和、有温度、"邻座同学"，但不幼稚；**情绪用在人格化时刻，克制用在信息密集处** |
| **视觉取向** | 圆润形状与充足留白；亮色为主基调；品牌色作为**强调与识别**而非文字载体；文字一律走**已验证的深色中性层** |
| **吉祥物用法** | **分层使用**：空态/等级/成就/引导/错误页等"人格化时刻"出场；信息流、表单、导航保持克制不出现 |
| **动效** | 有节制的物理化动效，且**每个动效都声明 reduced-motion 降级** |
| **暗色** | **暗色优先**（从第 0 天做），因为这是 App 端的独立资产，且与 Web 的亮色并不冲突 |
| **双语** | 布局按**英文长度**定尺寸；中文不填满；令牌层预留 3× 弹性 |
| **Tab** | 5 格（广场/树洞/食堂/信箱/我的）+ 发布 FAB；**图标优先**，标签短 |
| **回应 P1–P8** | P1→令牌唯一事实源 + 原型纪律；P2→按英文定尺寸；P3→品牌色只做强调，文字走深色层；P4→暗色优先；P5→首个切片必须消费组件库；P6→五格含信箱 + 孤岛收编；P7→承认与 Web 分叉；P8→每屏 a11y 验收 |
| **与品牌资产** | **一致**：调色板与吉祥物本就是柔和温暖路线，且与 Android Material 3 Expressive 的"design with emotion"方向相容 |
| **代价** | 需要在"可爱"与"克制"之间建立明确的分层纪律，否则会滑向幼稚或花哨；暗色优先意味着双主题都要在 P1 就完成 |

### 方向乙：**克制的工具感**

| 维度 | 内容 |
|---|---|
| **性格** | 高效、冷静、"校园基建"；不表达情绪 |
| **视觉取向** | 中性色为主，品牌色只用于极少数强调位；密度更高、圆角更小 |
| **吉祥物用法** | 仅出现在"关于/启动页"，界面内基本不用 |
| **代价** | ① 与品牌资产（可爱吉祥物 + 柔和调色板）**明显冲突**，等于把既有品牌资产闲置；② 与 Web 正在走的 Neo-Brutalism 同样冲突（只是方向不同）；③ 差异化弱，容易"像任何一个工具 App"；④ 对"校园社区"这一品类缺少情感连接 |
| **优势** | 一致性最容易守；无障碍与双语约束最容易满足 |

### 方向丙：**延续 Web 的分叉最小化**

| 维度 | 内容 |
|---|---|
| **性格** | 与 Web 尽量同源，降低双端维护 |
| **视觉取向** | 复用 Web 的语义令牌与视觉语言 |
| **代价** | ① **技术不可行**：Web 是 CSS 变量 + 桌面优先布局，App 是 RN + 移动端布局，令牌只能共享 Foundation 层；② **Web 自身正迁往 Neo-Brutalism**，与品牌相反；③ 旧 App 的失败恰恰来自"复刻 Web"；④ 会把 Web 的 **695 处硬编码**习惯一并带入 |
| **判定** | **不推荐**。共享应止于品牌色层与后端契约 |

### 共同前提：两端平台硬约束（对三个方向都成立）

以下由 [调研-02](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) 提供，**无论选哪个方向都必须满足**。但它们对"温暖柔和"的方向甲**额外收紧**，所以列在此处：

| 平台硬约束 | 对设计的直接含义 | 对方向甲的额外含义 |
|---|---|---|
| **Android edge-to-edge 不可退出**（target 36 起 `windowOptOutEdgeToEdgeEnforcement` 被禁用） | 每一屏都必须自己处理系统栏 insets，不存在"留一条系统栏"的偷懒空间 | 方向甲的"充足留白"**必须落在 edge-to-edge 画布之内**，留白不能靠系统栏撑出来 |
| **预测式返回默认开启，`onBackPressed`/`KEYCODE_BACK` 失效** | 返回语义必须服从系统；**自绘导航壳是禁止模式**（见 §6.10） | 同上——温暖的观感只能体现在内容层与原生容器的配置上，**不能靠自绘壳来实现** |
| **sw≥600dp 上方向/可调整性限制被忽略，且该退出口在 API 37 取消** | **"只做竖屏"这条路正在关闭**：大屏/折叠屏必须能自适应 | 方向甲若依赖"单列竖屏"的排版假设，会在大屏上失效 |
| **iOS：2026-04-28 起必须用 iOS 26 SDK 构建** | 构建链与 CI 的 SDK 下限已确定 | — |
| **iOS：`UIDesignRequiresCompatibility` 在 iOS 27+ SDK 被忽略** | **Liquid Glass 无法长期退出**；iOS 侧导航壳必须走原生容器 | 方向甲在 iOS 上的"温暖"必须与系统材质共存，**不能靠自绘绕开** |
| **无障碍硬数字：44×44pt 触控、字号默认 17pt/最小 11pt、对比度 4.5:1（≤17pt）/ 3:1（18pt 或加粗）** | 这些是**验收线**，不是建议 | 直接约束方向甲的圆角与间距令牌：可爱不等于小触控目标 |
| **标准组件自动适配 Reduce Motion / Reduce Transparency；自绘必须自己实现全部旁路** | 用原生容器能白拿一份无障碍合规 | 方向甲若大量自绘（吉祥物、动效），**无障碍旁路要自己全写** |

## 五、推荐与理由

**推荐方向甲「温暖的原生感」**，三条理由：

1. **它是唯一与既有品牌资产一致的选项。** 吉祥物与调色板已经定义了性格，App 若走克制工具感就是主动放弃品牌资产；而 3D 可爱吉祥物 + 柔和渐变 + 圆角 squircle，本身就是"温暖"的语言。
2. **它与平台趋势相容，不需要逆着规范做。** Material 3 Expressive 的官方主张即为"design with emotion"（见附录来源），与温暖性格同向；而 Web 的 Neo-Brutalism 恰恰是逆着品牌做的，App 不必跟随。
3. **它正面回应全部 P1–P8，且每条都能落成可执行约束。** 其余两个方向要么放弃品牌资产（乙），要么技术上不可行或重蹈覆辙（丙）。

**但方向甲有一个必须同时立下的纪律**，否则会失败：

> **"可爱"只能出现在人格化时刻（空态/成就/引导/错误），绝不进入信息流、表单与导航。**
> 这条纪律若不立，方向甲会从"温暖"滑向"幼稚"——而旧 App 的问题正是缺纪律。

## 六、跨调研的交叉结论

> 以下 9 条**不属于任何单份调研**——它们只有把多份文档合起来才成立。也正因如此，它们是本提案里最容易被漏掉、却最容易在实施时爆掉的部分。

### 6.1 一级 Tab 结构直接决定冷启动成本

来自 [调研-03 §4.4](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)（建议 5 格）与 [基座调研 §4.3](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)（**原生 Tab 的所有页面在导航器挂载时即 eager 渲染，且无法更改**）的交叉：

**"5 个一级 Tab"不是纯信息架构决策，而是一个启动性能决策。** 5 格意味着默认要挂载 5 个页面树。因此：

- 每个一级 Tab 的首页**必须廉价可挂载**（不做全量拉取、不挂重组件、不初始化重型 SDK）；
- 重内容延后到 `useIsFocused` / 进入可视区再加载；
- 尤其 R4 把「**信箱**」放进一级 —— 信箱首页必须设计成轻量列表，而不是一次性拉完所有分类与互动。

### 6.2 暗色不是亮色的反转，而是第二套品牌色

来自 [调研-04 §2.1](../../06-Analyze/ui-research/App设计调研-04-Web设计令牌与品牌资产盘点.md)（Web **无暗色**）× [调研-06 §三](../../06-Analyze/ui-research/App设计调研-06-无障碍与对比度实测.md)（品牌色作文字/承载白字全部不达标）的交叉：

- 暗色下**品牌色的表现会反转**：`#4da7ff` 在白底上是 2.53:1（不合格），在深底上却可能合格。因此**不能把亮色令牌取反当暗色令牌**，必须对暗色底重新解一遍对比度；
- 结论：令牌要按**主题 × 用途**二维组织，并且**每个组合都要有对比度实测值**，而不是只给一套色值。

### 6.3 英文长度 + 5 格 Tab + 图标优先，三者交叉才得出 Tab 方案

单看任一份都得不到结论：

- [调研-05](../../06-Analyze/ui-research/App设计调研-05-双语与文本弹性实测.md)：英文比中文长 **2.5×** 中位数；
- [调研-03 §4.1](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)：平台上限 3–5 格，且 5 格时官方建议「仅激活项显示文字」；
- 于是结论收敛为：**5 格必须图标优先 + 标签极短，或仅激活项显示文字**。"中文 2 字标签排得很漂亮"在英文下必然失败。

### 6.4 组件库必须一次做对，因为改基座的代价是商店发版

来自 [调研-00](../../06-Analyze/ui-research/App设计调研-00-旧App设计债实测基线.md)（旧 App 组件库引用 **0**）× [调研-03 §6.4](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)（Web 的 `FormPageLayout` **0 页使用**）× [基座调研 §6](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)（**含原生代码的 UI 基座升级必须走商店审核**）的交叉：

"组件库没人用"这件事在 Web 上只是维护债；在 App 上**后果更重**——因为一旦组件库定错，修正要经过商店审核（天级），**OTA 救不了**。所以：

- 组件库与令牌必须在**第一个纵向切片**就验证被真正消费；
- 且它们的**接口稳定性优先于功能丰富度**。

### 6.5 品牌一致性只能靠"标志 + 色彩 + 语气"，不能靠组件风格

来自 [调研-04 §3.3](../../06-Analyze/ui-research/App设计调研-04-Web设计令牌与品牌资产盘点.md) 的交叉：Web 正迁往 Neo-Brutalism（硬描边、高对比），App 走方向甲的柔和路线 —— **两端组件风格已注定分叉**。

因此"双端一致"只能落在三处：**品牌标识（`resources/icon.png` 系）、品牌调色板 Foundation 层、文案语气**。把"一致性"寄托在组件风格上是错的。

### 6.6 条款接受门禁需要一个安放位置，而它不能是注册弹窗

[基座调研 §8.3](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)：Play 要求"**发布 UGC 前**必须已接受 ToS/用户政策"（发帖前门禁）× [调研-03 §5-Q9](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)（通知形态要收敛）：这意味着**首次发布动作**需要一个合规拦截点，而它必须与"发布中心 / 树洞 FAB"的设计一起考虑，不能靠注册时弹窗糊过去。

### 6.7 账号注销入口的归位

[基座调研 §8.4](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md)（**应用内 + 网页两条都要**，且要级联删数据）× [调研-03 §4.4](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md)（"我的"承担个人事务收纳）：应用内注销应落在"我的 → 账号设置"的显著位置；网页注销入口则需要**后端提供页面**，属于"必须先做的后端工程"清单。

### 6.8 App 需要自己的一套组件，不能复用 `shared/components/`

[基座调研 §9.6](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md) 实测：`shared/components/` 含 `.jsx` + `.css`，是 **Web 专属**，不得导入 RN；可与 App 共用的只有 `shared/{api,constants,utils,config,query}`。

**这与 R4 的建议合起来才有意义**：R4 说"广场页应直接消费后端 `home-summary` 聚合"——聚合数据可以共享，但**呈现它的组件 App 必须重写**。

### 6.9 OTA 纪律要分库对待

[基座调研 §6](../../06-Analyze/tech-research/App基座调研-Expo与原生iOS混编.md) 实测：`FlashList` / `LegendList` **零原生代码**（可 OTA），而 `expo-image` / `reanimated` / `gesture-handler` / `@expo/ui` / `screens` / `safe-area-context` / `svg` **全含原生**。

因此纪律不能一刀切为"能热更"或"不能热更"，必须**按依赖逐个登记"原生依赖=有/无"**，并据此决定该次变更能否走 OTA。

### 6.10 导航壳必须交给原生容器，"自绘壳 + 贴玻璃"应被列为禁止模式

这是 [调研-02 §B6/C8](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) 最有可执行价值的结论，与 §6.1 的交叉：

Liquid Glass / M3 的材质价值**绑定在系统组件上**——滚动边缘效果、tab 滚动最小化、search tab 自动分离、sidebar 自适应、随 Reduce Transparency 自动降级。**RN 自绘只能拿到静态观感，拿不到这些行为**（第三方实现如 `@callstack/liquid-glass` 0.8.2 自陈"玻璃高度 ≥65 时文本自动配色失效"等硬限制）。

**正确取舍**：**导航壳 → 原生容器**（Tab 栏、Header、Sheet、返回手势）；**内容层 → RN 自绘 + 严格遵守各端令牌**。两级边界必须在架构上先划清。

> 两端罕见地给出一致结论：**一个产品只保留 1–2 个 hero moment**（M3 官方建议 + Apple"避免过度使用 Liquid Glass"）。

### 6.11 M3 动效物理在 RN 上没有官方实现 → 动效规范必须自己定义

[调研-02 附录 B](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) 核实：M3 motion physics 的 spring 数值**官方未公开**；官方实现对照表里 **Compose=Available、Flutter=Unavailable、React Native 根本没有条目**。调研者明确**拒绝编造常量**。

**含义**：App **不能承诺"M3 合规动效"**。动效规范必须自建（时长、曲线、弹簧参数自定），并逐条声明 reduced-motion 降级路径。

这同时解释了旧 App 的一个现象：**装了 Reanimated 却 0 引用**——因为没有动效规范，就没有"该在哪里动、动到什么程度"的依据，库自然闲置。

### 6.12 ⚠️ 对方向甲的风险提示：「玻璃永不生效」的根因是方向错误

[调研-02 §A1](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) 引 M3 官方原文：**"M3: Using color instead of shadows to communicate elevation"**，且阴影"仅在必要时使用"。即 Android 的正统是 **tonal surface 抬升，不是模糊**。

旧 App「Android 上玻璃效果从未生效」由此获得**机制级解释**：它把 iOS 向的模糊分层照搬到 Android，**方向本身就错**；而且 `expo-blur` 产出的是模糊，本来就不等于 Liquid Glass。

> **这条是对方向甲的自我风险提示**：方向甲主张"温暖柔和"，天然容易滑向"到处贴玻璃、到处加渐变"——那正是旧 App 的病。
> 因此方向甲必须同时立下**第二条纪律**：**禁止以模糊/玻璃作为视觉身份**。深度的表达应走 **分层 tonal surface + 描边/硬阴影**，而不是 blur。

### 6.13 离线不是一张提示图，而是数据层架构

[调研-01 §7.4](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md) 引 Android 官方：**离线优先意味着「本地是唯一数据源」，UI 只读本地、网络只由 repository 写入本地**；web.dev 官方亦指出「**Cache then network** 优于 Network falling back to cache」。

**这是本提案此前完全没有覆盖的一类要求。** 它对本项目的含义很具体：食堂、课表、树洞列表这类**高频且变化不快**的内容，应该"先给本地、再刷新"，而不是每次进屏都等网络。它属于**架构级设计**，必须在宪法里立条，不能靠"加载中"动画糊过去。

> 同时必须记住 R1 的诚实标注：**没有任何官方给出"App 应达到 N fps"这类性能验收线**——不要凭空写数字。

### 6.14 ⚠️ 官方导航口径已更新，R4 的五格方案需带一处核对

[调研-01 §2.1](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md) 指出 M3 官方原文已有 **"Baseline navigation bar is no longer recommended"**（基线导航栏不再被推荐）。

这与 [调研-03 §4.4](../../06-Analyze/ui-research/App设计调研-03-Dorm能力面与使用场景盘点.md) 的五格方案**不冲突**（R4 引用的是"3–5 个目的地、不超 5"这一条，仍然有效），但它意味着：**"底部 Tab 用哪一版导航栏"必须按 M3 当前推荐的那一版定，而不是按基线版**。这一项要在写风格体系时以当前 M3 官方页面为准核对一次。

### 6.15 两组官方口径冲突，应显式记录为「平台差异项」而不是取交集

[调研-01 §9/§10](../../06-Analyze/ui-research/App设计调研-01-社区内容型产品界面实证.md) 发现两处**官方之间就互相矛盾**的口径：

| 冲突 | 一方 | 另一方 |
|---|---|---|
| 应用内是否给外观开关 | Apple HIG 明确**反对**应用自建外观设置 | Discord 官方提供五档主题 + 饱和度调节 |
| Tab 栏能否承载动作 | Apple HIG 明文"tab bar 支持导航、**不提供动作**" | 国内"底部 Tab 中间放发布"极常见（**注意：该做法零官方背书，R1 明确标为最高风险项**） |

本项目已定「**双端各自最优、不求 1:1**」，因此正确处理是**把这两项写进宪法的"平台差异项"清单**，而不是取交集或强行统一。

> 顺带：R4 的 IA 方案把"发布"放在 **FAB** 而不是 Tab 中间，**恰好避开了这条零官方背书的做法**——两路调研在这里自然收敛。

## 九、待所有者拍板

**本提案层面的 4 项**：

1. **是否选定方向甲（温暖的原生感）**？若否，选乙还是另立方向？
2. **是否同时立下这两条纪律**（方向甲成立的前提）：
   - **纪律一**：可爱只出现在人格化时刻（空态/成就/引导/错误），绝不进入信息流、表单与导航；
   - **纪律二**：**禁止以模糊/玻璃作为视觉身份**——深度的表达走分层 tonal surface + 描边/硬阴影（依据见 §6.12）。
3. **暗色模式的取向**：方向甲主张「暗色优先」。若你更希望与 Web 一致（纯亮色），需明确告知。
4. **品牌一致性容忍度**：方向甲意味着 App 与 Web **视觉明确分叉**（Web 走 Neo-Brutalism）。是否接受？

**已经累积、将在风格体系/宪法阶段继续确认的 6 项**（详见设计阶段计划 §六）：字体、Tab 标签策略、语言集合与默认语言、品牌色"文字安全"档、无障碍目标等级、一级导航结构（调研-03 方案 A/B/C）。加上调研-03 §五 的 14 项范围决策。
