## 一、令牌是唯一事实源

### 1.1 三层结构

```
Foundation（原始值，不含语义）
   └─ 品牌调色板、中性色阶、字族、原始间距单位
Semantic（角色，按主题分套）
   └─ bg / text / border / accent / state × { dark, light }
Component（极少数，仅当语义层无法表达）
   └─ 例：button.height.md
```

**规则**

1. 业务代码**只允许**消费 Semantic 层；Foundation 只在 Semantic 的定义里被引用。
2. Component 层**默认不建**；出现时必须说明为何 Semantic 表达不了。
3. 两套主题（dark / light）各自**完整成套**，不允许"亮色 + 临时叠加"。

### 1.2 每个颜色令牌必须声明「可否承载文字」

这是本体系与旧做法最关键的区别：**颜色令牌不是一个色值，而是一组带用途与验证结论的约束。**

| 字段 | 含义 | 必填 |
|---|---|---|
| `value` | 色值 | ✅ |
| `usage` | `surface` / `fill` / `text` / `icon` / `border` | ✅ |
| `textSafe` | 可否用于正文文字 | ✅ |
| `contrastOn` | 若 `textSafe`，声明其验证基准背景 | ✅ |
| `contrastRatio` | 实测算得的对比度 | ✅（`textSafe=true` 时） |
| `theme` | `dark` / `light` | ✅ |

**为什么必须这么做**：实测显示品牌色的 400/500 档位**全部不达标**——白字放品牌蓝仅 **2.53:1**、警告杏 **1.76:1**、成功绿 **2.20:1**、危险红 **2.91:1**（AA 正文要求 4.5:1）。如果不逐令牌声明，这些不合规组合会以"品牌色按钮 + 白字"这种最常见的形式渗透进每一屏。

## 二、色彩

### 2.1 品牌 Foundation：**App 自建色阶，不沿用 Web**（所有者 2026-10-01 裁决）

**Web 的品牌蓝 `#4da7ff` 不能当 App 主色 —— 不是审美取舍，是它过不了本项目自己的门：**

| 组合 | 实测 | 要求 | 判定 |
|---|---|---|---|
| `#4da7ff` 作文字 on 白 | **2.53:1** | ≥4.5:1 | ❌ |
| 白字 on `#4da7ff`（CTA 填充） | **2.53:1** | ≥4.5:1 | ❌ |

它只在深色底上勉强可用（on `#12141a` 为 7.26:1），而主色的职责恰恰是**在亮色主题里也当强调色、并作为 CTA 色块承载白字**。

**色相已由所有者定案（2026-10-01）：厦大蓝 + 美团黄**，两者都从**官方品牌资产实测**得出：

| 角色 | 锚点 | 来源 | 关键实测 |
|---|---|---|---|
| **主色 · 厦大蓝** | **`#173874`** | 【实测官方资产】`www.xmu.edu.cn/images/logo2.png`（H=261.2°） | 白字 on 它 **11.33:1** ✅；它作文字 on 白 **11.33:1** ✅；**它 on 暗底仅 1.63:1** ❌ |
| **辅色 · 美团黄** | **`#ffc300`** | 【实测官方资产】`www.meituan.com/favicon.ico`（H=86.1°） | 黑字 on 它 **13.06:1** ✅；它 on 暗底 **11.45:1** ✅；白字 on 它 与 它作文字 on 白 均 **1.61:1** ❌ |

**完整色阶、逐令牌实测对比度与角色分工 → [App 设计令牌规范](App设计令牌规范.md) §三。** 本文件**不复述色值**，避免二次转述失真。

三条由实测直接推出的规则：

1. **暗色主题必须用厦大蓝的同色相提亮档**（`brand-300` / `brand-400`，对暗底 7.78 / 5.83）—— 锚点在暗底只有 1.63:1，而本项目暗色优先。
2. ⛔ **美团黄永远不能作亮色主题的文字**。它只有两个合法角色：**填充（必须配黑字）** 与 **暗色主题下的强调**。
3. ✅ **`accent-300` + 黑字 + 2px 黑描边** 天然就是 Neo-Brutalism 的 CTA 配方（§七 白名单第一类），是本项目最划算的品牌表达。

**色阶由脚本生成，不是手挑**：`node scripts/brand-ramp.js --hue <选定值> --fail`
**令牌唯一创作源是 CSS**：`tokens/design-tokens.css` → `node scripts/gen-tokens.js` → App 与 Web 同时变（宪法 2.1）。

### 2.2 `textSafe` 由实测决定，**不得按档位推断**（对 v1.0 的修正）

v1.0 曾写「品牌色 400/500 档位**一律** `textSafe = false`」。**那条是从 Web 调色板实测反推出来的，不能当通则**：

| 档位 | 暗色下（on 暗色 canvas `#12141a`） | 亮色下（on 白） |
|---|---|---|
| `brand-300` / `brand-400` | **可作文字**（**7.78** / **5.83**） | 不可（2.37 / 3.16） |
| `brand-600` / `brand-700` | 不可（2.48 / **1.63**） | **可作文字**（**7.41** / **11.33**） |
| `accent-300`（美团黄） | **可作文字 / 图标（11.45）** | 不可（1.61）→ **只能配黑字作填充** |

→ **同一个色阶，在暗色下由浅阶承担文字、在亮色下由深阶承担文字**。这就是"`textSafe` 不按档位推断"的实际样子。

**正确规则**：`textSafe` 只能由该令牌对**声明背景**（`contrastOn`）的实测对比度决定。**同一个 400 在暗色下 `textSafe=true`、在亮色下 `textSafe=false`，这是正常的。**

### 2.3 装饰色与状态色**必须各自独占色相**（新增，来自 Web 的反面证据）

[App品牌主色提案](App品牌主色提案.md) §1.3 实测出 Web 调色板的一个结构性缺陷——**它把"辅助色"和"状态色"放在了同一色相上**：

| 辅助色 | 色相 | 状态色 | 色相 | 间距 |
|---|---|---|---|---|
| 薄荷 `#73d9b3` | 167.2° | 成功 `#39c58d` | 161.9° | **5.3°** |
| 杏 `#ffb86c` | 66.6° | 警告 `#ffb547` | 73.3° | **6.7°** |
| 粉 `#ff8fb1` | 1.4° | 危险 `#f36d6d` | 22.3° | **21.1°** |

**三对全部低于 25°。** 这解释了为什么 Web 的品牌色承载不了语义——**同一批色相被同时装进了"装饰"和"状态"两个抽屉**。

**规则**：主色与每个状态色之间**色相间距 ≥25°**；辅助色不得复用状态色的色相。由 `scripts/brand-ramp.js` 的三条色相间距门强制。

**本轮的落地结果（重要：美团黄入场后原警告色不达标）**：美团黄 H=**86.1°** 与原警告 H=73.3° 只差 **12.7°** ❌。处置：**把警告色相移到 55°**。

| 对 | 间距 |
|---|---|
| 厦大蓝 261.2° ↔ 成功 161.9° / 警告 55° / 危险 22.3° | 99.3° / 153.8° / 121.2° ✅ |
| 美团黄 86.1° ↔ 警告 55° / 危险 22.3° | **31.1°** / 63.7° ✅ |
| 警告 55° ↔ 危险 22.3° | 32.7° ✅ |

→ **主色 / 辅色 / 三个状态色两两满足 25° 门，规则保持为硬规则，不需要任何"例外"。**
（备选方案是把此次冲突登记为量化例外；**已否决**——能靠移动色相解决，就不该放宽规则。）

**附加纪律**：警告**必须同时带图标与文案**，不得仅靠色块表达 —— 55° 琥珀与美团黄同处暖色区，快速扫视下需要第二重区分。

> **状态色的色相基准**（沿用 Web 现值，属最保守假设）：成功 161.9° / 警告 73.3° / 危险 22.3°。若将来重定义状态色，本表与门限需重算（提案 §五 C3）。

### 2.4 语义层（暗色优先）

**暗色先定义，亮色再派生**——因为暗色是本项目更常用的场景，且暗色下品牌色的对比度会**反转**（浅色在白底不达标，在深底可能达标），不能靠取反得到。

| 语义令牌 | 用途 | 承载文字 | 说明 |
|---|---|---|---|
| `bg.canvas` | 页面最底 | ❌ | **不用纯黑**（Material 官方口径） |
| `bg.surface` | 卡片/列表基底 | ❌ | 比 canvas 略亮一档 |
| `bg.surfaceRaised` | 浮起表面（弹层、下拉） | ❌ | 再亮一档 |
| `bg.surfaceSunken` | 内嵌区域（输入框底） | ❌ | 比 canvas 略暗 |
| `bg.brandSoft` | 品牌浅底 | ❌ | 承载 `text.onBrandSoft` |
| `text.primary` | 标题与正文 | ✅ | 对 `bg.canvas` / `bg.surface` 均须 ≥4.5:1 |
| `text.secondary` | 次要信息 | ✅ | 同上 |
| `text.muted` | 弱化/占位 | ⚠️ | **仅限大字或非关键信息**（实测 Web 的等价色仅 4.03:1） |
| `text.onBrand` | 品牌色块上的文字 | ✅ | 只允许配文字安全的深色品牌档 |
| `text.disabled` | 禁用 | ❌ | 纯装饰，不可承载需读信息 |
| `border.subtle` | 分隔线 | ❌ | |
| `border.strong` | 描边（含 Neo-Brutalism） | ❌ | |
| `accent.primary` | 强调（链接、选中态） | ⚠️ | 装饰级；作文字必须用 600/700 档 |
| `state.success/warning/danger` | 状态 | ⚠️ | 同上 |

### 2.5 暗色分层：改表面色，不是加阴影（`【已定】`）

依据 Material 官方：**"M3: Using color instead of shadows to communicate elevation"**，暗色层级由**表面色变化**表达。

- 暗色表面分档（`canvas` → `surface` → `surfaceRaised` → `surfaceSunken`），**档数固定**；
- **M2 的 overlay 机制已被 M3 的 surface container 取代，两套数值不可混用**（调研-01 §5 明确警告）；
- 暗色下**禁用高饱和色**做文字或大面积（Material 官方："optical vibrations"）；强调色在暗色下**去饱和/提亮**，且只用在关键元素。

### 2.6 禁止项

| # | 禁止 | 依据 |
|---|---|---|
| 1 | 业务代码出现 `#hex` 字面量 | 旧 v1 实测 **1437 处**；M3 色角色体系 + Apple HIG"避免硬编码色值" |
| 2 | **`textSafe` 按档位推断**（如"400/500 一律不可作文字"） | 从 Web 调色板反推的外推，不是通则；见 §2.2 |
| 3 | 装饰/辅助色复用**状态色的色相**（间距 <25°） | Web 调色板三处反面证据，见 §2.3 |
| 4 | 主色承载白字却未达 4.5:1 | Web 品牌蓝实测 2.53:1；CTA 上的白字是正文不是大字 |
| 5 | `text.muted` 用于长正文 | 实测等价色仅 4.03:1 |
| 6 | 暗色使用纯黑大底 | Material 官方口径 |
| 7 | 用**模糊/玻璃**表达层级 | Android 正统是 tonal surface；旧 App"玻璃从不生效"的根因正是照搬 iOS 模糊 |
| 8 | 语义令牌跨用途挪用（分隔线色当文字色等） | Apple HIG「Avoid redefining the semantic meanings」 |

## 三、字体与字阶

### 3.1 只用系统字体，不引入自有字体（所有者 2026-10-01 裁决，`【已定】`）

**裁决**：**字体采用原生字体，不引入新字体。** 不打包任何字体文件、不加载自定义字族。

这不只是"省事"，而是三条实测约束共同指向的唯一解：

| # | 事实 | 来源 |
|---|---|---|
| 1 | Web 的 `Source Han Serif SC`（衬线标题）在 Android 会**退化**，`PingFang SC` 在 Android **根本不存在** | [调研-04](../../06-Analyze/ui-research/App设计调研-04-Web设计令牌与品牌资产盘点.md) §1.2 |
| 2 | Android 的**字体度量在 target 35→36 之间已经变过一次**：`elegantTextHeight` 在 target 36 被忽略、「UI fonts」被停用，官方要求为阿拉伯语、泰语、卡纳达语等一批语言**调整布局** | [调研-02](../../06-Analyze/ui-research/App设计调研-02-Android与iOS平台规范.md) §C8 |
| 3 | 因此 **两端不应共用同一套"绝对 pt 值"字阶常量** | 同上 §479 |

#### 3.1.1 落地规则（每条都可被 review 直接判）

1. **禁止在 Android 上书写 `fontFamily`。**
   依据：RN 的 `ReactFontManager.createAssetTypeface`（Android）在字体名不匹配时**静默回退系统字体、不打印任何日志**，而 iOS 会打印 `Unrecognized font family '<name>'` → **在 Android 上把字体名拼错是不可见的 bug**（[RN #58750](https://github.com/facebook/react-native/issues/58750)，2026-09-29 提交、至今 open，影响 RN 0.87.1）。
2. **`system-ui` / `ui-sans-serif` / `ui-serif` / `ui-monospace` / `ui-rounded` 只在 iOS 受支持**（RN 官方 `fontFamily` 文档原文）。**不得在 Android 依赖它们**（不支持的族会静默回退，见第 1 条）。
3. **App 不使用衬线字体做标题。** Web 的衬线标题是本项目历史上唯一的"性格化排版"手段，它在 Android 不可用。→ App 的层级**完全靠字阶 + 字重 + 颜色 + 留白**表达。
4. **字阶按平台角色各自生成**：iOS 用**系统文字样式**（从而获得 Dynamic Type），Android 用 **M3 字阶角色**。**语义命名两端一致，取值分端生成。**
5. **字重只用 `normal` / `bold` + 系统确实存在的档位。** RN 官方："Not all fonts have a variant for each of the numeric values, in that case the closest one is chosen." → **不得假设每个数字档位都存在**，`500` 与 `600` 未必能区分。
6. **数字对齐用 `fontVariant: ['tabular-nums']`**，不要为此换字体（课表、排行榜、计时、价格全部需要）。
7. **系统字号放大必须支持**：`allowFontScaling` 保持开启，为关键布局设 `maxFontSizeMultiplier` 上限，**而不是关掉缩放**。

#### 3.1.2 平台字族（由系统解析，**不由我们指定**）

| 用途 | Android | iOS |
|---|---|---|
| CJK 正文/标题 | 系统 CJK（设备决定；**不写字体名**） | 系统 CJK（苹方，自动回退） |
| Latin 正文/标题 | Roboto / 系统默认（**不写字体名**） | SF Pro（不写字体名） |
| 数字与代码 | 系统等宽（确需指定时只用 `monospace`） | `ui-monospace` |

> **唯一允许出现 `fontFamily` 的情形**：① iOS 上的通用族（`ui-monospace` 等）；② Android 上的通用族 `monospace`。**除此之外一律不写。**

### 3.2 字阶

字阶令牌化，禁止 `fontSize` 字面量（旧 v1 实测 **645 处**）。字阶需覆盖：`display / title / headline / body / label / caption`，每级含 size / lineHeight / weight。

### 3.3 中英弹性（`【算得】`，**本体系最容易翻车的一条**）

实测 1504 组中英文案：**英文长度中位数是中文的 2.50×，75 分位 3.00×，90 分位 3.75×，最大 6.00×；75.9% 的文案英文 ≥ 中文 2 倍。**

规则：

1. **所有定宽元素按英文长度定尺寸**，不按中文；
2. 中文标签**不得填满**容器（填满＝给英文预留 0 弹性）；
3. 按钮、Tab、Badge 需要 **≥3× 长度弹性**或明确的截断策略；
4. 影响关键操作的文案**不允许静默截断**，应换行或缩短文案；
5. **语言切换不得引发布局跳动**——弹性必须在令牌层预留，而不是切换时重算。

## 四、间距 / 圆角 / 描边 / 阴影

| 组 | 规则 |
|---|---|
| **间距** | 以 4 为基数的等比阶（`【提案】`：4 / 8 / 12 / 16 / 24 / 32 / 48），令牌化；页面左右留白统一取一档，禁止逐屏自定 |
| **圆角** | 分档（`【提案】`：small / medium / large / full），"连续圆角"是"苹果舒适感"的主要载体；**同一语义元素在所有屏必须同档** |
| **描边** | 常规描边 1px；**Neo-Brutalism 专用 2px**（见 §七），两者不可混用于同一元素 |
| **阴影** | 亮色下极克制；**暗色下层级一律不用阴影，改表面色**（§2.5）。禁止用发光代替阴影（Material 官方：「Don't use light glows in place of dark shadows」） |
| **触控目标** | **iOS ≥44×44pt / Android ≥48×48dp**（`【已定】`：Apple HIG 44pt；Android 官方 48dp）。**取各自平台的值，不取交集**。视觉尺寸可以更小，但命中区必须补足 |

## 五、动效

### 5.1 规格必须自建（`【已定】`）

调研-02 核实：**M3 动效物理（motion physics）在 React Native 上没有官方实现**（官方实现对照表里 Compose=Available、Flutter=Unavailable、RN 无条目），且官方未公开 spring 数值。

因此：**App 不能承诺"M3 合规动效"**。动效规格由本项目自建，并**明确声明这是近似**。

### 5.2 准许的动效清单（必须逐条，不许"看情况加"）

| 场景 | 动效 | 依据 |
|---|---|---|
| 页面进退 | 平台默认转场（交给原生容器） | §6.10 导航壳走原生 |
| 列表项插入/删除 | 布局动画 | 「方向/反馈/寻路」三分类 |
| 点赞等即时反馈 | 短促缩放 | 同上 |
| 加载 → 内容 | 淡入 | 「先给东西看」 |
| 下拉刷新 | 系统手势层 | 手势交原生 |

**默认不动**：高频交互（Apple HIG 官方：「generally avoid adding motion to UI interactions that occur frequently」）。

### 5.3 强制规则

1. 每个动效都要能回答"它在表达**方向 / 反馈 / 寻路**中的哪一种"，答不上就删；
2. **每条动效都必须声明 reduced-motion 降级**（降级为淡入淡出或直接切换）；
3. 位移类可有回弹，**颜色/透明度类不得回弹**；
4. 时长随覆盖面积缩放，不用一个固定毫秒套所有转场；
5. 手势驱动动画必须在 **UI 线程**执行（Reanimated + Gesture Handler）。

> 对照基线：Web 侧 `prefers-reduced-motion` 仅覆盖 **8 处**——降级路径的缺失是既有问题，App 不能重演。

## 六、布局原型库

**8 核心 + 9 扩展 = 17 个**，覆盖全部 103 个页面（来源：调研-03 §6）。核心 8 个覆盖 **73.8%** 的页面。

| 桶 | 占比 | 说明 |
|---|---|---|
| 表单 | 20.4% | **优先参数化**（字段描述符 + 校验 + 提交语义） |
| 列表 | 17.5% | 同上 |
| 详情 | 15.5% | |
| 后台表格 | 8.7% | v1 可能不进（见调研-03 §5-Q1） |
| 静态 | 6.8% | |
| 信息流 / 仪表盘 | 各 4.9% | |
| 其余 | ≤3.9% | 榜单 / 检索 / 鉴权 / 阅读器 / 地图 / 日历 / 对话 / 翻页 / 课表 |

**纪律**

1. **每个新需求必须先声明它属于哪个原型**；不属于任何一个时，先评审"是否新增原型"，而不是先写页面；
2. 两个最大的桶（表单 + 列表，合计 **37.9%**）**优先做成参数化框架**，收益最高；
3. **万能墙（翻页）与二手私信（对话）虽各只 1 页，但交互契约特殊，必须单独立原型**，不允许塞进列表/详情降级实现；
4. **纯转发原型禁止新增**，现存 4 个纯转发页应删除。

> 现状差距（反面证据）：Web 已有 9 个模板组件，但 `ListPageLayout` 仅 5 页用、`DetailPageLayout` 1 页、**`FormPageLayout` 0 页**。"原型层名义存在、实际未落地"——App 不能重演。

**只允许出现在三类元素上**：

| # | 元素 | 允许的做法 |

| 3 | **分区标题** | 同上，通常只用描边或色块 |

## 九、四态规范（空 / 载 / 错 / 离线）

四态是**屏级交付物**，不是"顺手加一下"。

### 9.1 空态（分三类，各自动作不同）

| 类别 | 含义 | 动作 |
|---|---|---|
| 首次无数据 | 用户还没产生内容 | 引导首次动作 |
| 用户动作无结果 | 筛选/搜索无命中 | 提供放宽条件 |
| 错误管理型 | 数据不该为空却为空 | 提供修复入口 |

规则：空态**替换掉**本该显示的组件本体；空态图**不表达紧急/困惑**；**一个空态只给一个最重要动作**；同屏多个空态时 CTA 降级为 tertiary；空间有限时**只用文字不塞插画**。

### 9.2 加载

**先给东西看**（骨架/占位），不是先给空白；知道时长用确定性指示器，不知道才用不确定性；指示器**持续在动**；**不配"loading…"这种无信息量文字**；位置一致。

分页加载必须有**明确状态机**：`refresh / append / prepend × NotLoading / Loading / Error`，错误带 retry。

### 9.3 错误

说清**发生了什么 + 怎么修**；错误摘要置顶并把焦点移过去，字段级错误就近显示；**用户预期会成功的操作不弹成功提示**（失败才提示）；**预期内的删除不警告**（意外且不可逆的才警告）。

### 9.4 离线（`【已定】` 数据层要求）

Android 官方：离线优先＝**本地是唯一数据源**，UI 只读本地、网络只由 repository 写入本地；web.dev 官方：**Cache then network 优于 Network falling back to cache**。

**含义**：食堂、课表、树洞列表等高频且变化不快的内容应"先给本地、再刷新"，而不是每次进屏等网络。**这是架构级要求，写进宪法，不靠"加载中"糊过去。**

## 十二、组件层：什么用现成、什么自己写

**所有者问题（2026-10-01）**：「**组件，有没有现成的？还是说自己写好点？**」

**回答：分三层，不能整体回答。** 完整事实与依据见 [App组件层调研](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)。

### 12.1 三层与判据

| 层 | 做法 | 判据（一句话） |
|---|---|---|
| **① 平台 / 运行时原语** | **用现成** | 它承担的是**平台行为**，不是视觉决定 |
| **② 设计系统层** | **自己写** | 它是**视觉决定**或本项目独有的约束，任何库给不了 |
| **③ 完整设计系统 / UI kit** | **不作基座** | 采用即接受它的色值与字阶 |

### 12.2 第①层：用现成（**不要自己写**）

| 类别 | 采用 |
|---|---|
| 系统容器 | `react-native-screens`、原生 Tab 实现（宪法 4.3 三选一）、`expo-router` |
| 手势 / 动效 | `react-native-gesture-handler`、`react-native-reanimated` + `worklets` |
| **原生控件** | **优先 `@expo/ui`** —— 官方自述为 **primitives library**（明确否认自己是"有主见的设计套件"），三入口（`swift-ui` / `jetpack-compose` / `universal`）组件面广，并自带 **8 个 drop-in 替代**（可直接换掉 `@gorhom/bottom-sheet`、datetimepicker、masked-view、menu、pager-view、picker、segmented-control、slider）|
| 列表虚拟化 | `@shopify/flash-list` **或** `@legendapp/list`（**零原生代码，可 OTA**）—— 二者择一 |
| 图片 / 触感 / 系统图标 | `expo-image`、`expo-haptics`、`expo-symbols` |
| 安全区 / 绘图 | `react-native-safe-area-context`、`react-native-svg` |

**三条纪律**：

1. **一律 `npx expo install`**。反例（实测）：`react-native-gesture-handler` 的 npm `latest` 是 **3.3.0**，而 SDK 57 模板锁 **`~2.32.0`**，且其 peerDependencies **无版本上界** → **手装不会在安装期报错**。
2. **能换成 `@expo/ui` 官方实现的，优先换掉第三方原生依赖**（它自带 8 个 drop-in 替代，含 `@gorhom/bottom-sheet` 的兼容版）→ 直接降低宪法 11.4 的 OTA 负担。
3. **按包登记"许可证 / 是否含原生 / OTA 影响"**（宪法 3.4）。反例（实测）：`tamagui` 的 npm `license` 字段**为空**，仓库才是 MIT —— **npm 元数据不可全信**。

### 12.3 第②层：自己写（**不要买**）—— 组件清单

```
tokens/   Foundation → Semantic（每个颜色令牌带 contrastRatio / textSafe）
theme/    dark 先定义 → light 派生
ui/原子    约 12 个
ui/组合    约 20 个
原型层     8 核心 + 9 扩展（宪法 9.1）
```

**原子（约 12）**：`Surface` / `Text` / `Stack` / `Pressable` / `Icon` / `Badge` / `Divider` / `Avatar` / `Skeleton` / `Input` / `Sheet` / `Toast`

**组合（约 20）**：`Button`(CTA) / `ListItem` / `Card` / `SectionHeader` / `EmptyState` / `ErrorState` / `FormField` / `SearchField` / `TabSegment` / `Chip` / `ActionSheet` / `Dialog` / `Banner` / `ConfirmDialog` / `ProgressBar` / `PaginationFooter` / `Refreshable` / `TermsGate` / `CommentItem` / `MailboxRow`

> **数量是"提案"不是承诺**：宪法 9.1「先声明原型、不许先写页面」仍然有效 —— 新增组件必须由原型需求驱动，**不得预留**。
>
> **该估算清单按页面展开后的完整注册表见 [App 组件类型定义](App组件类型定义.md)**：**102 个组件**（原子 12 / 控件 22 / 组合 22 / 四态 6 / 覆盖层 14 / 域专用 26），每个组件都有确定的消费者（页面或本文件内其它组件），并含选择器选型表、表单字段描述符 DSL、文本底框与通知阶梯。**两份文件不是两份清单，是一份清单的两个粒度**；若两者冲突，以本宪法为准，其次以《App 组件类型定义》为准（它更细）。

### 12.4 必须自研的四条理由（每条可验证）

1. **判据是"默认渲染"，不是"脚本是否变绿"**（这条最容易被误用）：
   `design-debt-report.js` **只扫我们的 `src/`**，`node_modules` 里的硬编码色值**不会被计数、但运行时照样生效** → **"两把尺子全绿"不等于"视觉自主"**。
   **唯一有效的判据**：**装上该库、不改它的主题，渲染一个 `Button`，得到的是不是我们的 CTA？**
   实测：`react-native-paper@5.15.3` **1072 处色值 / 99 处 `fontSize` 字面量**且自带 M3 token 文件；`tamagui/themes` 1910 处；`react-native-magnus` 279 处；`react-native-elements` 148 处。
   ⚠️ **反例**：`@rneui/themed` 实测 **0 色值 0 字号**，默认 theme 仍是外来视觉 → **"字面量为 0"既不充分也不必要**。
   自研的令牌层则天然满足 2.3 条（每个颜色令牌携带实测算出的 `contrastRatio`）。
2. **方向是三种来源的特定混合，没有库实现**：`react-native-paper` 官方 README 自述 "**by default are following and respecting the Google's Material Design guidelines**" → 两端都是 M3，与宪法 5.2（iOS 不得按 M3 做）冲突；Neo-Brutalism 组件库会把白名单**扩散成全局风格**（宪法 1.1）。
3. **双端分叉是要求而不是妥协**（宪法 5.2）：导航壳、弹层形态、动效曲线、字阶取值都要分端生成 —— 而 UI kit 的核心价值恰恰是"两端统一"。
4. **宪法 9.5 的"组件库必须被消费"这道门只对自研组件库有效**：买来的库"被消费"是自动满足的，门就失去了约束力。而旧 App 的病正是"组件库写了 **0 引用**"。

### 12.5 明确不做的三件事

1. **不重造**手势、动效、列表虚拟化、物理 —— 已被第①层买掉。
2. **不引入样式引擎**（`nativewind` / `@shopify/restyle` / `react-native-unistyles` / `tamagui` 的 styling 部分）：RN 的 `StyleSheet` + 令牌层已经足够。本项目的问题从来不是"样式写得麻烦"，而是"**没有唯一的令牌来源**"——那是架构问题，不是语法问题。
3. **不引入完整 UI kit**（`react-native-paper` / `tamagui` / `react-native-ui-lib` / `@ui-kitten/components` / `react-native-magnus` / `react-native-elements` / `@rneui/themed`）。
   维护信号与发布日（含"**必须读版本自身时间戳、不得用 `time.modified`**"的取值纪律）见 [App组件层调研 §2.1 / §4.6](../../06-Analyze/tech-research/App组件层调研-现成组件库评估.md)。

### 12.6 一条被限制的能力：M3 动态取色

`@expo/ui` 的 `Material Colors` 暴露 **M3 Dynamic Colors**（由用户壁纸取色）。**本项目不把系统动态色作为令牌层的取值来源。**

理由是可验证的：**动态取色让表面 / 强调色在运行期才确定 → `contrastRatio` 无法在构建期预先算定 → 与宪法 2.3 条直接冲突。**

> 这是"每一屏都必须过对比度门"这条纪律的必然推论：**任何让颜色在运行期才确定的机制，都不能进入令牌层。**

⚠️ **但"不当作令牌来源"≠"不能用 `@expo/ui`"**。三条不冲突的用法（宪法 9.12）：

1. 给 `Host` 传 **`seedColor` = 本项目品牌主色** —— 把系统控件锚定到我们的色，而不是壁纸色；
2. 用 `colorScheme` **显式 lock** 到 `light` / `dark`，不用 `'unspecified'`；
3. 把 `@expo/ui` 原生控件当"**平台控件**"，我们自己的令牌层只管自绘组件，两者通过同一个 `seedColor` 在视觉上对齐。

**待脚手架期实测（不得当已成立）**：`seedColor` 是否在所有 M3 组件上完全覆盖动态取色；`getMaterialColors` 返回的 8 位 `#RRGGBBAA` 能否直接进入 `contrast-check.js` 的解析路径。

## 十三、组件结构纪律：杜绝嵌套与套壳（所有者 2026-10-01 裁决）

**判据（一句话）**：**删掉这个组件、把它的内容上提一层，是否丢失任何行为？** 不丢失就是壳，**必须删**（宪法 9.14）。

| # | 禁止的形状 | 反例 | 正确写法 |
|---|---|---|---|
| 1 | **透传壳** | `CardWrapper` 只做 `<Card {...props} />` | 直接用 `Card` |
| 2 | **同语义多层** | `Card > CardBody > CardContent`（3 层） | `Card > CardContent`（**≤2 层**） |
| 3 | **为复用而抽象** | 只有 **1 处**使用的"通用"组件 | **就地写**；第 2 处出现时才抽 |
| 4 | **样式壳** | `MarginBox` 只为了给子组件加 16px | 直接应用**间距令牌** |

**三项配套检查（可 review）**：
1. 一个组件文件的**唯一 `return` 是否就是另一个组件的调用**？是 → 删。
2. 同一语义单元的视觉嵌套层数是否 **≤2**？否 → 合并。
3. 该组件的引用处是否 **≥2**？否 → 上提回使用处。

> **为什么这条要写进体系**：它与「全局组件化，一改全部改」（1.4）是同一件事的两面 —— **每多一层壳，一次全局改动就要多穿一层**。旧 App 的病是"每屏自由发挥"；而它的反面（层层抽象）同样会让"一改全部改"失效：改动要么改不到底，要么改一处炸三处。

## 十四、文案纪律：杜绝说明性文字（所有者 2026-10-01 裁决）

**总原则**：**只留三类文字 —— 标识 / 动作 / 状态。** 不属于这三类的，删。

| 类别 | 含义 | 示例 |
|---|---|---|
| **标识** | 这是哪里、这是什么 | `广场` · `课程表` · `树洞` |
| **动作** | 按了会发生什么 | `发布` · `保存` · `重试` |
| **状态** | 现在怎么了 | `已发送` · `未读 3` |

**字数（宪法 10.5）**：按钮 / 标签 **≤6 汉字**（英文 ≤2 词）；标题 ≤12 汉字；正文说明 ≤30 汉字（**仅错误与合规场景允许存在**）。

| ⛔ 禁止 | 为什么 |
|---|---|
| 「这个功能是用来…」这类旁白 | 说明性文字 = 设计没讲清楚 |
| 「注意：…」「温馨提示」 | 同上；重要的事靠**设计**表达，不靠提醒 |
| `加载中…` · `请稍候` · `暂无数据` | 占位废话；空态必须给动作（§9.1） |
| 用文案弥补设计缺陷 | **改设计，不是加文案** |
| 卖萌、夸赞、感叹号堆叠 | 与「苹果的舒适感」冲突 |

**错误文案是唯一例外，且要求相反**：必须**具体**（可感知 / 可理解 / 可改正 → 宪法 10.4），**但仍须短** —— 一句话结论 + 可展开细节。

> **一句话记住**：**简洁 ≠ 含糊。** 具体指**信息量**，简洁指**字数**；冲突时以 10.4 为先。

## 十五、图标体系（两层，所有者 2026-10-01 裁决）

| 层级 | 适用 | 来源 |
|---|---|---|
| **第 1 层：品牌位 / 自绘位置** | 我们画在内容里的图标：顶栏信箱、列表与卡片语义图标、功能区、空/错状态、发布 FAB | **Lucide** |
| **第 2 层：系统控件位** | 系统容器**自己提供**图标的位置：原生 Tab 栏、原生导航栏项、原生菜单、ActionSheet、日期选择器、分享面板 | **平台原生**（iOS SF Symbols / Android Material Symbols） |

**判据**：**这个图标是我们画在内容里的，还是系统容器自己提供的？**

⛔ 禁止两层混用；⛔ 禁止 Emoji 与 Unicode 符号字符（`★ ✓ ▸`）冒充图标；⛔ 禁止为单个图标引入第二个图标库；⛔ 纯图标按钮**必须有可读标签**。

**尺寸与重量**：图标尺寸**从字阶令牌派生**，不在屏内写魔法数字；**stroke 全局统一**；**同一含义全局只有一个图标**。
【提案】具体档位与 stroke 值须真机定稿。

**图标名清单、两层归属细则与未证实项** → [App 图标方案调研](../../06-Analyze/tech-research/App图标方案-Lucide与平台图标.md)。

## 十六、绝对禁止的视觉手法（红线汇总）

| # | 禁止 | 依据 |
|---|---|---|
| 1 | **任何渐变背景**（`LinearGradient` / `MeshGradient` / CSS 渐变 / 用图片模拟） | 宪法 1.3.5 |
| 2 | **Emoji 作为图标** | 宪法 1.3.6 |
| 3 | 以**模糊 / 玻璃拟态**作为视觉身份或层级手段 | 宪法 1.3.1 |
| 4 | 用**发光**代替阴影 | Material 官方「Don't use light glows in place of dark shadows」 |
| 5 | 暗色**纯黑大底** | Material 官方口径 |
| 6 | 运行期**动态取色**进入令牌层 | 宪法 9.12 |

> 这六条的共同点：**它们都是"用观感代替结构"。** 层级、情绪与强调一律由**纯色表面 + 排版 + 间距**表达。
