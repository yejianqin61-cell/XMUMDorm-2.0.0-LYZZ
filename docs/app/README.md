# App 设计文档中心

本目录收纳 **App 客户端（React Native）** 的全部设计层文档。Web 端（`frontend/`）与后端的文档仍在 `docs/` 原有的生命周期分层里，不受影响。

**建立日期**：2026-10-02（由 `docs/` 各层归集而来，见 §五 迁移对照）｜**最近重构**：2026-10-02（新增 `research/` 层与两个跨层登记册）

---

## 一、为什么在这里

App 与 Web **双端并重、各自最优**（宪法 5.1/5.2），设计层文档也已经完全独立：旧 App 端连同其设计哲学 / 设计宪法 / 前端风格全盘作废并归档于 git tag `app-legacy-v1`，现存 App 文档是**从零重写**的一套。

因此把 App 文档集中到一个子目录，好处有三条：

1. **读写边界清晰** —— 改 App 设计不会误动 Web 文档；
2. **写作用域可切分** —— 协作纪律要求"一个模块 = 一个写作用域 = 一个负责人"，App 目录天然是一个独立作用域；
3. **分层与工作流一一对应**（constitution → product → design → task → test → research/evaluation），能直接映射到工作流。

## 二、结构与读法

### 2.1 七层

| 层 | 目录 | 回答什么 | 谁必须先读 |
|---|---|---|---|
| **宪法** | [`constitution/`](constitution/) | **不许越界**：不可协商的硬约束 | 所有人 |
| **产品** | [`product/`](product/) | **是什么**：SRS、范围、信息架构、页面清单 | PM / 设计 / 前端 |
| **设计** | [`design/`](design/) | **长什么样、怎么实现**：哲学、风格、令牌、组件、**页面骨架与布局** | 设计与前端 |
| **任务** | [`task/`](task/) | **怎么排、按什么顺序**：阶段计划与验收门；**今后的子任务 task 文档也落这里** | 所有人 |
| **测试** | [`test/`](test/) | **验成什么样**：逐屏验收、真机与安全区矩阵、脚本运行快照 | QA / 前端 |
| **调研** | [`research/`](research/) | **做决定之前**：外部事实取证、方案对比（证据在哪） | 需要复核结论时 |
| **评估** | [`evaluation/`](evaluation/) | **对已存在的东西的判定**：准入评估、专项自评、审计、复盘 | 需要判定结论时 |

**三层判据（一句话各自说清，避免互相塞东西）**：

| 目录 | 判据 |
|---|---|
| `research/` | 这份文档是**为了决定**而写的（查事实、比方案） |
| `evaluation/` | 是用来**判定某个已经存在的东西**好不好（准入、自评、审计） |
| `test/` | 是**我们跑出来的结果**（打勾、原始输出、机型、构建号） |

### 2.2 两个跨层登记册（**不是"第八层"**）

| 文件 | 是什么 | 为什么放在顶层 |
|---|---|---|
| [`TO-CONFIRM.md`](TO-CONFIRM.md) | **待所有者确认的问题**（涉及总纲与全局规范） | 它是**队列**，不属于任何一层；且必须**唯一**，其他文档只写编号引用 |
| [`TODO.md`](TODO.md) | **功能与能力待办**（等后端、等真机、等实测） | 同上；它是"我们要做的事"，与"要所有者拍板的事"必须分开 |

⛔ **不得在别处再维护第二份待确认清单或第二份待办清单** —— 两处必然不同步，同步失败会让下一个 Agent 按过期信息施工。

### 2.3 推荐阅读顺序（新成员）

`constitution/` → `product/` → `design/App页面骨架与布局规范.md` → `design/App设计哲学提案.md` → `design/App前端风格体系.md` → `task/`；**接手任何决定前先看 [`TO-CONFIRM.md`](TO-CONFIRM.md)**（那里写着哪些还没定）。

> ⚠️ **数值来源标注约定**：本目录各文档一律使用 `【已定】`（所有者裁决 / 官方规范 / 实测）、`【算得】`（由实测机械推导）、`【提案】`（**待真机或脚本复核，不得当已验证规格使用**）三种标注。**读到 `【提案】` 时不要当规格用。**

## 六、维护约定

1. **一个 App 主题 = 一个文件 = 一个负责人**；令牌、组件规范与根布局/导航壳条款由**单一所有者**维护，其他人只读。
2. **禁止并行修改** [`design/App设计令牌规范.md`](design/App设计令牌规范.md)、[`design/App组件类型定义.md`](design/App组件类型定义.md)、[`design/App页面骨架与布局规范.md`](design/App页面骨架与布局规范.md) 与 [`constitution/App设计宪法.md`](constitution/App设计宪法.md)（协作纪律见 [task/](task/)）。
3. **新增 App 文档必须落在本目录的七层之一**；若确实无法归入，先评审"是否需要新的一层"，而不是先建文件。**只有"跨层队列"才可以放顶层**（当前仅 `TO-CONFIRM.md` / `TODO.md` 两个）。
4. **待确认与待办只有一份**（§2.2 的禁令）。
5. **开发期的任何调整都要回写文档**（宪法 15.4-3）：页面结构 → `product/`；视觉 → `design/`；组件 → `design/`；范围 → `product/`。**不回写等于对下一个 Agent 说谎。**
6. **`test/` 不覆盖历史**：新一轮验收**新建文件**，不改上一轮。
