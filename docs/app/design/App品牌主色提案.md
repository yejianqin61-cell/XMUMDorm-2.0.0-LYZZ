# App 品牌主色提案

**日期**：2026-10-01　**版本**：v1.0 · **待所有者选定色相**
**上游**：[App 设计哲学提案](./App设计哲学提案.md)（方向已定）、所有者 2026-10-01 指示：**「品牌色，主色调还需要定，不能照搬 Web 的设计」**
**下游**：[App 前端风格体系](./App前端风格体系.md) §二（色彩）与 [App 设计宪法](../constitution/App设计宪法.md) 第 2 条
**性质**：本文件负责**回答"主色是什么"**。它给候选、给机械判定、给推荐，但**色相的最终选择属于所有者**。

> **本文件的核心发现（先行）**：Web 品牌蓝 `#4da7ff` **不只是"不该照搬"，而是被本项目自己的验收尺子判为不合格**——
> 作文字 on 白 **2.53:1**、承载白字 **2.53:1**，两端都够不到 4.5:1。因此"照搬 Web"不是审美问题，是**机械上过不了门**。

---

## 一、三条实测事实

### 1.1 事实一：Web 品牌蓝在主色这个岗位上两端都不达标

| 组合 | 实测对比度 | 要求 | 判定 |
|---|---|---|---|
| `#4da7ff` 作文字 on 白 | **2.53:1** | ≥4.5:1 | ❌ |
| 白字 on `#4da7ff`（作 CTA 填充） | **2.53:1** | ≥4.5:1 | ❌ |
| `#4da7ff` 作文字 on 暗色 canvas `#12141a` | 7.26:1 | ≥4.5:1 | ✅ |

**含义**：它只有在深色底上才勉强能用。而主色的职责恰恰是**在亮色主题里也当强调色、并作为 CTA 色块承载白字**。一个只能在暗底用的颜色，不能当主色。

复现：`node scripts/contrast-check.js --brand-preset`（内置预设 11 组中 8 组正文不达标）。

### 1.2 事实二：品牌标识自身的色带是 **257°–278°**（蓝紫族）

对 `resources/icon.png` 做中位切分量化（保留 alpha > 200 的像素，12 色），**一手实测输出**：

| hex | 占比 | OKLCH-L | C | H(度) |
|---|---|---|---|---|
| `#302822` | 15.3% | 0.284 | 0.016 | 58.9 |
| **`#6aa6fb`** | **12.7%** | 0.721 | 0.140 | **257.2** |
| `#12100e` | 10.7% | 0.175 | 0.005 | 67.5 |
| **`#86b1fa`** | 9.0% | 0.758 | 0.116 | **260.6** |
| `#e9d9c8` | 8.3% | 0.894 | 0.029 | 69.1 |
| **`#aeb6ed`** | 8.1% | 0.789 | 0.079 | **278.0** |
| `#f5eae0` | 7.3% | 0.943 | 0.018 | 64.9 |
| `#e9bdd6` | 6.9% | 0.844 | 0.060 | 343.4 |
| `#837677` | 6.7% | 0.578 | 0.016 | 12.3 |
| **`#7baaf2`** | 5.3% | 0.734 | 0.117 | **258.7** |
| `#d5b7d9` | 5.2% | 0.816 | 0.057 | 322.3 |
| `#c8beda` | 4.6% | 0.818 | 0.040 | 301.8 |

**读数**：标识的**有彩色部分几乎全部落在 257°–278° 的蓝紫带**（`#6aa6fb` / `#86b1fa` / `#7baaf2` / `#aeb6ed`，合计 ≈35%），中间是奶油/米色中性（≈64–69°，低彩度）与近黑描边（58.9°/67.5°，几乎无彩度）。

**这是本提案里唯一一条来自品牌资产的约束**：**主色相落在 257°–278° 区间，与品牌标识是同族的**；跳到青绿、品红等家族会让 App 与自己的图标失去色彩关联。

> 方法可复现：对 `resources/icon.png` 缩略到 ≤96px、按 alpha>200 过滤、`Image.quantize(colors=12, method=MEDIANCUT)` 取色并统计占比，再转到 OKLCH。属一次性测量，故不固化为脚本。

### 1.3 事实三：**Web 调色板把"装饰色"和"状态色"放在了同一色相上**

这是"不能照搬 Web"最硬的理由 —— 不是审美差异，是**设计系统缺陷**：

| 装饰/辅助色 | OKLCH 色相 | 状态色 | OKLCH 色相 | 间距 |
|---|---|---|---|---|
| 薄荷 `#73d9b3` | 167.2° | 成功 `#39c58d` | 161.9° | **5.3°** |
| 杏 `#ffb86c` | 66.6° | 警告 `#ffb547` | 73.3° | **6.7°** |
| 粉 `#ff8fb1` | 1.4° | 危险 `#f36d6d` | 22.3° | **21.1°** |

**三对全部低于 25°。** 即 Web 调色板里"辅助色"和"状态色"在色相上基本是同一个颜色，只靠彩度/亮度区分。

**推论（这是本提案最重要的结构判断）**：
> **Web 的品牌色之所以"承载不了语义"，根因不是它不够深，而是它把同一批色相当同时装进了"装饰"和"状态"两个抽屉。**
> 在这种调色板里，任何一个颜色都无法独占一个含义。App 若继承它，会连带继承这个缺陷。

因此本提案给出的门里，**"与三个状态色的色相间距 ≥25°"与对比度门同等重要**。

## 二、主色准入的门（共 9 条）

主色不是"挑一个好看的色值"，而是一个**必须同时满足 9 条门**的色相选择。理由写在每条上。

### 2.1 六条对比度门（暗色优先，所以 400 与 600 的职责是分开的）

| # | 门 | 门槛 | 为什么 |
|---|---|---|---|
| 1 | `400` 作文字 on 暗色 canvas | ≥4.5:1 | 暗色一等公民：强调文字/链接/选中态主要出现在暗色下 |
| 2 | `400` 作文字 on 暗色 surface | ≥4.5:1 | 卡片上的强调文字不能因底变亮而失效 |
| 3 | **白字 on `600`** | ≥4.5:1 | **CTA 填充**：Neo-Brutalism 的 CTA 是"高对比色块 + 白字"，白字是正文，必须 4.5:1 |
| 4 | `600` 作文字 on 白 | ≥4.5:1 | 亮色主题的强调文字 |
| 5 | `700` 作文字 on 白 | ≥4.5:1 | 亮色主题的链接/小号强调文字 |
| 6 | 白字 on `500`（大字/非文本） | ≥3:1 | 次级填充块（大字标签、图表） |

> **为什么门 3 是 4.5:1 而不是 3:1**：CTA 上的文字是 17pt 正文，不是大字。这条门一开，主色就被迫"深到能承载白字"，也就自动消灭了"品牌色按钮 + 白字 2.53:1"这个旧病。

### 2.2 三条色相间距门

| # | 门 | 门槛 | 为什么 |
|---|---|---|---|
| 7 | 与**成功**色相间距 | ≥25° | 状态语义必须独占色相 |
| 8 | 与**警告**色相间距 | ≥25° | 同上 |
| 9 | 与**危险**色相间距 | ≥25° | 同上；红/橙系主色会直接毁掉错误态 |

**基准说明（诚实标注）**：三条门用的状态色相仍是 **Web 现值**（成功 161.9° / 警告 73.3° / 危险 22.3°）。若 App 也重定义状态色，间距需按新值重算 —— 沿用 Web 状态色相是最保守的假设。

## 四、推荐

### 4.1 首选：**靛蓝 Indigo（H ≈ 272°）**

```
100 #ecf0fd   200 #d2dbfa   300 #aabbf6   400 #8fa4f3
500 #748aea   600 #5467c4   700 #3c4ca6
```

| 理由 | 证据 |
|---|---|
| **与品牌标识同族** | 标识有彩色带 257°–278°，272° 正落在其中；标识的浅紫 `#aeb6ed` 是 278° |
| **不是"照搬 Web 蓝"** | 与 Web 蓝相差 21.5°；更关键的是**彩度与亮度都不同**（本 400 `#8fa4f3` L=0.735 / 低彩度 vs Web 蓝 L=0.713 / C=0.155）。视觉上是更柔、更冷的"夜色靛"，而非同一个蓝 |
| **9 条门全部通过且有余量** | 白字 on 600 **5.10:1**（门 3）、400 on 暗底 **7.69:1**（门 1） |
| **与三个状态色零冲突** | 110.1° / 161.4° / 110.3°，全部远超 25° |
| **性格匹配** | 克制、偏冷、暗色下不刺眼 → 对应"苹果的舒适感"；单一强调色、暗色分层 → 对应"Discord 的社区感"；600 档 5.10:1 的高对比色块足以承担 Neo-Brutalism 的 CTA |

### 4.2 备选一：**紫罗兰 Violet（H ≈ 300°）** —— 若要"明显不同于 Web"

```
100 #f2edfd   200 #e1d5fa   300 #c8aff6   400 #b794f3
500 #a07bdd   600 #7e58b7   700 #643e9a
```

- **收益**：与 Web 蓝相距 **49.5°**，双端一眼可分；个性最强；白字 on 600 达 **5.29:1**，是全候选里 CTA 对比度最好的之一。
- **代价**：紫罗兰在移动端常被读作"创作工具 / 直播 / 游戏"，与"校园生活服务"的距离比靛蓝远；与危险红间距收窄到 82.3°（仍达标）。

### 4.3 备选二：**青蓝 Cyan-Azure（H ≈ 228°）** —— 若要求"变化最小、用户最无感"

```
100 #e1f4fd   200 #b6e5fa   300 #67ccf6   400 #40b8e6
500 #369fc7   600 #277a9a   700 #1d5f78
```

- **收益**：与现状蓝色最接近，用户迁移零认知成本；400 on 暗底 **8.08:1** 为全候选最高。
- **代价**：**"新 App 的品牌色"这件事几乎没发生**——22.5° 的偏移在多数屏幕上看不出差别。若采纳它，"不照搬 Web"只在技术上成立（色值全新、对比度达标），在感知上不成立。

### 4.4 不推荐：青绿 Teal

未过门（白字 on 500 = 2.99:1），且与成功色相同色相家族最近（34.1°）。**一个"绿色系"主色与"成功"状态天然抢语义**，在食堂/交易类界面里会被误读。

### 4.5 必须同时记录的一条宪法修正

现有宪法第 2.3 条写的是「**品牌色 400/500 档位一律 `textSafe = false`**」。**这条是从 Web 调色板实测反推出来的，不能作为通则**：

- 在本提案的色阶里，**400 在暗色下是文字安全的**（靛蓝 7.69:1 / 紫罗兰 7.49:1）；
- 而 **600 在亮色下才是文字安全的**（5.10:1 / 5.29:1）。

**正确规则**（应替换原条款）：**`textSafe` 不得由档位推断，只能由该令牌对声明背景的实测对比度决定。** 同一个 400 在暗色下 `textSafe=true`、在亮色下 `textSafe=false` 是完全正常的。原条款保留其可验证的内核（"每个颜色令牌都必须携带实测对比度"），去掉按档位一刀切的外推。

## 五、待所有者裁决

| # | 决策 | 选项 | Lead 建议 |
|---|---|---|---|
| **C1** | **主色相选哪个** | 靛蓝 272 / 紫罗兰 300 / 青蓝 228 / 其他（可给任意 0–360 的值，用脚本重跑） | **靛蓝 Indigo（H=272）**：唯一同时满足"与品牌标识同族"与"与 Web 蓝可分"的方案 |
| **C2** | **App 主色是否反向统一 Web** | ① App 先定，Web 保持现状，品牌统一单独立项（App 不阻塞）② App 定完立刻改 Web 令牌 | **①**。Web 自身正在做 RetroUI 迁移，此刻叠加改色会与在飞的改动互相干扰；且所有者已接受"App 与 Web 视觉分叉" |
| **C3** | **是否重定义状态色的色相** | 沿用 Web 现状（成功 161.9° / 警告 73.3° / 危险 22.3°）vs 一并重定 | **沿用现状**（本提案的三条间距门即基于此）；重定义会连锁改动全部状态令牌与既有素材 |

> **C1 不定，令牌层不定稿**；但 C1 **不阻塞**脚手架与组件库建设 —— 令牌层只需把 `accent.primary` 指向色阶，色相是可替换的输入。
