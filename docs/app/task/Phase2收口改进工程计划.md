## 2. The approach, requirement by requirement

### R-1 恢复真实私信会话列表链路

- **Approach**：先把已实现的跨商品会话列表部署到真实环境，再用真实令牌验证买家、卖家、空列表和无权限分支。自动化 mock 只证明页面接线，不作为线上契约证据。
- **Touches**：后端 marketplace 路由、部署配置、会话列表页面、真实契约测试。
- **Test seam**：现有 live backend contract 入口；不新增测试接缝。
- **Acceptance**：
  - [ ] 真实环境的会话列表路由不再返回 404；
  - [ ] M-11 能加载买家和卖家的会话；
  - [ ] 空列表和无权限响应均有明确业务状态；
  - [ ] live backend contract 不再跳过该路由。
- **Hard part**：部署环境可能没有同步本地新增路由，必须先确认实际运行版本。

### R-2 为私信补齐历史游标和长会话不丢消息

- **Approach**：后端提供稳定的历史游标，客户端继续使用 4 秒轮询读取增量，并把历史分页和轮询结果按同一排序规则合并去重。
- **Touches**：marketplace 消息接口、mailbox 会话状态、消息排序与分页规则。
- **Test seam**：现有 ChatScreen 业务接缝和后端契约测试；不新增底层抽象。
- **Acceptance**：
  - [ ] 超过 500 条的会话可以加载更早消息；
  - [ ] 轮询和历史分页合并后没有重复或丢失；
  - [ ] 同一时间戳的消息仍按稳定次序展示；
  - [ ] 后端游标边界、空页和末页都有测试。
- **Hard part**：历史分页与轮询可能同时返回，错误的合并顺序会产生重复或倒序。

### R-3 建立服务端条款接受真源

- **Approach**：以条款版本为单位保存用户接受记录，发布动作由服务端最终判断当前版本是否已接受。客户端只展示状态和修正动作，不再用缺失字段放行。
- **Touches**：用户协议数据、条款接受接口、发布门禁、viewer 聚合和双语错误文案。
- **Test seam**：现有发布提交门控和真实后端写入测试；不新增页面级接缝。
- **Acceptance**：
  - [ ] 未接受当前版本时服务端拒绝 UGC 发布；
  - [ ] 已接受当前版本时发布成功；
  - [ ] 条款状态缺失或版本过期时不再走放行分支；
  - [ ] 拒绝结果包含可理解、可修正的中英文提示。
- **Hard part**：客户端缓存的接受状态不能成为最终授权依据，必须覆盖旧版本和跨设备场景。

### R-4 完成 13.1 development build 设备验收

- **Approach**：先产出可安装的 SDK 57 development build，再按既有 13.1 记录执行设备批次。只有设备观察结果才能关闭触控、横屏、大屏、最大字号、返回和动效项目。
- **Touches**：development build、公共布局、页面逐屏验收、设备矩阵和缺陷总账。
- **Test seam**：现有 13.1 逐屏记录、10 条安全区清单和设备矩阵；不把静态检查改成设备通过。
- **Acceptance**：
  - [ ] 甲、乙、丙的交付页面都有对应设备记录；
  - [ ] 触控命中区、横屏、大屏、最大字号和返回手势有实测结论；
  - [ ] reduced-motion 有明确的实现或“不产生动效”证据；
  - [ ] 失败项进入唯一缺陷总账，并标明复测条件。
- **Hard part**：大屏断点不是纯验收项；设备观察确认问题后，可能需要调整公共布局并回归全部页面。

### R-5 替换隐私政策和服务条款占位正文

- **Approach**：由所有者提供正式中英文文本，应用只负责按统一静态页结构展示当前批准版本，并移除所有占位措辞。
- **Touches**：法律静态页、国际化词条、版本记录和上架材料。
- **Test seam**：现有静态页渲染测试和词条门禁；不新增法律内容解析器。
- **Acceptance**：
  - [ ] 页面不再出现“占位正文”或“待替换”；
  - [ ] 中英文正文均来自批准版本；
  - [ ] 页面链接、版本日期和上架材料一致。
- **Hard part**：正式文本是外部输入，工程只能校验完整性和展示，不替所有者决定法律措辞。

### R-6 增加私信线程归属校验

- **Approach**：进入会话前确认线程属于当前用户，后端仍是最终授权边界。非法、未知或他人线程统一进入可修正错误状态，不能执行读取或发送。
- **Touches**：mailbox 路由参数、会话列表数据、消息读写请求和错误状态。
- **Test seam**：现有 ChatScreen 测试和真实 API 权限测试；不新增导航层接缝。
- **Acceptance**：
  - [ ] 非法或未知线程不能读取或发送；
  - [ ] 他人线程不能读取或发送；
  - [ ] 深链失败不触发当前账号的鉴权清理；
  - [ ] 后端拒绝和客户端预检均有回归测试。
- **Hard part**：客户端预检只能改善体验，不能替代服务端授权；两层失败结果必须保持一致。

### R-7 按规则清偿 lint warning

- **Approach**：先生成按规则和模块分组的 warning 基线，再逐批修复 `refs`、`set-state-in-effect`、`globals` 和测试探针问题。保持规则开启，不用忽略配置制造“归零”。
- **Touches**：App 生产代码、测试代码、Expo lint 配置和 CI 报告。
- **Test seam**：现有 lint 命令和 CI；不新增 lint 包装器。
- **Acceptance**：
  - [ ] warning 数量按规则和文件可追踪；
  - [ ] 每批修复后 typecheck、测试和 rulers 仍通过；
  - [ ] warning 数量持续下降且不新增同类问题；
  - [ ] 0 error 与 warning 数量分开报告。
- **Hard part**：部分 warning 来自迁移期规则或测试探针，必须逐项判断，不能机械改写。

### R-8 让 verify 在资源边界内稳定完成

- **Approach**：先找出 Jest 未关闭的异步句柄，再限制并行 worker 和内存峰值；保留串行回退命令，确保开发机和 CI 都能拿到完整出口结果。
- **Touches**：测试生命周期、Jest 执行参数、verify 脚本和 CI 资源配置。
- **Test seam**：现有 `typecheck`、Jest、rulers 三段出口命令；不新增测试框架。
- **Acceptance**：
  - [ ] `npm run verify` 连续两次完整退出 0；
  - [ ] 默认执行不发生 Node OOM；
  - [ ] Jest 不再报告未关闭的异步操作；
  - [ ] 资源受限环境有文档化的串行回退命令。
- **Hard part**：必须先区分真实句柄泄漏和并行资源峰值，否则只调小 worker 会掩盖测试生命周期问题。

## 3. Phases

### Phase 1 — 真实私信链路恢复

**Covers**：R-1 恢复真实私信会话列表链路和 R-6 增加私信线程归属校验。

**Goal**：真实用户可以打开 M-11，会话列表不再 404；错误深链不能读取或发送他人会话。

**Tasks**

- 部署跨商品会话列表路由并确认运行环境版本
- 用买家、卖家、空列表和无权限令牌执行真实契约矩阵
- 在会话进入前增加线程归属预检和失败状态
- 让读取与发送请求复用同一归属判断
- 补非法、未知和他人线程的客户端与后端回归测试

**Proof**：真实契约测试通过，M-11 在真实环境加载会话；四类非法线程场景均不能读取或发送。

**Not here**：消息历史游标、条款接受、设备验收、法务文本和 lint 清理。

### Phase 2 — 私信消息完整性与合规门禁

**Covers**：R-2 为私信补齐历史游标和 R-3 建立服务端条款接受真源。

**Goal**：长会话可以向前翻页且消息不丢；没有接受当前条款版本的用户不能发布 UGC。

**Tasks**

- 定义消息历史游标和末页响应的后端契约
- 实现历史分页与 4 秒轮询结果的排序、合并和去重
- 用超过 500 条消息的夹具覆盖首屏、分页、空页和并发轮询
- 建立条款版本与用户接受记录的服务端读写路径
- 将发布提交门改为服务端当前版本判定
- 覆盖未接受、已接受、过期和状态缺失四种发布结果

**Proof**：长会话契约测试与发布门禁测试通过；真实测试账号能分别证明“可翻页”和“未接受不能发布”。

**Not here**：实时 WebSocket、原生推送、正式法律措辞和设备布局调整。

### Phase 3 — 设备证据与发布材料收口

**Covers**：R-4 完成 13.1 development build 设备验收和 R-5 替换法律占位正文。

**Goal**：目标页面在 development build 上有可复核的设备记录，法律页可以进入上架材料复核。

**Tasks**

- 产出 SDK 57 development build 并记录构建信息
- 按设备矩阵执行触控、返回、横屏、最大字号和 reduced-motion 验收
- 复测大屏页面并确定公共断点是否需要实现
- 将设备失败项写入唯一缺陷总账并安排回归
- 接入所有者批准的中英文隐私政策和服务条款
- 回归静态页、词条门禁和 13.1 记录索引

**Proof**：设备记录能由构建号复现；页面逐屏状态不再把未验项目标成通过；法律页无占位措辞。

**Not here**：商店提交、EAS production 发布、推送通道和未批准的新产品功能。

### Phase 4 — 工程出口稳定化

**Covers**：R-7 按规则清偿 lint warning 和 R-8 让 verify 在资源边界内稳定完成。

**Goal**：任何接手者都能在文档化资源边界内运行完整出口，并看懂剩余代码告警。

**Tasks**

- 生成 lint warning 基线并按规则、模块和责任人分组
- 修复第一批生产代码 warning，逐批保留回归证据
- 修复测试探针和未关闭异步句柄
- 调整 verify 的 worker 与资源边界并保留串行回退
- 连续运行完整 verify 两次并记录结果

**Proof**：完整 verify 连续两次退出 0；warning 数量和剩余原因有清单；typecheck、测试和 rulers 均可独立复跑。

**Not here**：为了好看而关闭 lint 规则、重写已通过的业务模块、增加新的测试框架。
