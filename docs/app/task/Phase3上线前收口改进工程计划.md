# Phase 3 上线前收口改进工程计划

文档类型：施工计划与上线差距评估  
日期：2026-10-09  
状态：待执行  
基线：Phase 2 审计、Phase 3 收口验收、Phase 5 收口小结、生产开发计划

> **结论**：当前 App 达到“业务代码接近内测候选”，尚未达到“可正式上线”。本地自动化出口已连续两次通过，但可安装构建、真实设备、商店红线、正式法务正文和部分真实后端链路仍未闭合。Phase 3 先完成证据与红线收口，再生成发布候选包；未满足验收门时，不提交商店审核。

## 3. The approach, requirement by requirement

### R-1 上线构建可安装且可回滚

- **Approach**：先准备 SDK 57 的可安装构建通道，再用同一版本号生成内部包和发布候选包。每个候选包保留构建号、提交号和回滚包。
- **Touches**：构建通道、版本管理、分发轨道和发布记录。
- **Test seam**：安装包冷启动与升级路径；不新增业务测试入口。
- **Acceptance**： [ ] 陌生设备可安装并冷启动  [ ] 构建号可在 App 内查看  [ ] 失败可回退到上一包
- **Hard part**：Expo project、Dev Client、账号权限和原生工具是外部前置。

### R-2 目标设备与关键交互通过验收

- **Approach**：使用 development build 跑既定设备矩阵，再按唯一缺陷总账修复公共布局或交互问题。静态规则只作筛选，不作设备通过证明。
- **Touches**：安全区容器、导航壳、页面骨架、设备验收记录和缺陷总账。
- **Test seam**：现有 13.1 逐屏清单与安全区矩阵。
- **Acceptance**： [ ] 关键页面完成触控、返回、横屏、大屏、最大字号和动效检查  [ ] 失败项有复现条件与责任人  [ ] 公共修复完成回归
- **Hard part**：设备、校网和校方系统访问条件可能不齐。

### R-3 真实后端主链路可用

- **Approach**：先补真实环境契约，再覆盖注册、课表、发布、私信和真实数据展示。客户端只在服务端契约稳定后收口错误态。
- **Touches**：认证、私信、发布、课表、首页摘要和真实后端契约记录。
- **Test seam**：现有 live-backend-contract 与真实账号矩阵。
- **Acceptance**： [ ] 私信列表不再返回 404  [ ] 长会话可游标翻页且不丢消息  [ ] 非法线程不能读取或发送  [ ] 注册与代表性真实数据可验证
- **Hard part**：TD-54、TD-58、TD-59 等能力仍依赖后端改动。

### R-4 UGC 发布满足商店合规红线

- **Approach**：由服务端保存条款版本、屏蔽关系和注销结果。客户端只展示服务端判定，并为拒绝提供可改正路径。
- **Touches**：条款接受、发布门禁、屏蔽、账号注销和账号数据清理。
- **Test seam**：发布入口、账号设置入口和后端授权契约。
- **Acceptance**： [ ] 未接受当前条款不能发布 UGC  [ ] 屏蔽关系同时影响内容和互动  [ ] 用户可发起注销并完成级联删除  [ ] 缺失合规字段默认拒绝
- **Hard part**：这些是商店红线，不能用客户端标记或占位接口替代。

### R-5 法务与商店材料达到提交条件

- **Approach**：所有者提供批准文本后，统一接入中文和英文页面，并建立商店提交材料的同版本引用。补齐隐私 URL、数据安全说明和账号支持信息。
- **Touches**：法律页面、国际化词条、商店元数据和合规材料。
- **Test seam**：静态页回归、链接检查和提交材料清单。
- **Acceptance**： [ ] 页面不含占位正文  [ ] 中英文文本版本一致  [ ] 商店材料引用同一版本  [ ] 法务责任人完成批准
- **Hard part**：正式文本不是工程团队可以自行编造的输入。

### R-6 工程出口可重复且告警可解释

- **Approach**：保留自然退出的完整 verify，按规则和文件清理 lint warning，并分别报告 error 与 warning。任何资源边界调整都要有回归证据。
- **Touches**：Jest 生命周期、verify 脚本、CI 和 lint 迁移债务。
- **Test seam**：`verify`、`verify:serial`、typecheck、四把 rulers 和 lint 报告。
- **Acceptance**： [ ] 完整 verify 连续两次自然退出 0  [ ] warning 数量和分类可追踪  [ ] CI 对共享代码与目标分支生效  [ ] 不用禁规则隐藏问题
- **Hard part**：309 条 warning 不是上线阻塞的单一数字，但会降低新问题可见性。

### R-7 上线运行可观察、可反馈、可降级

- **Approach**：发布包携带版本与构建号，应用提供反馈入口，后端保留错误日志，并为校方系统和关键写操作保留已批准的降级路径。
- **Touches**：反馈入口、版本信息、错误日志、发布说明和回滚流程。
- **Test seam**：内部测试安装包、反馈表和发布演练。
- **Acceptance**： [ ] 测试者可提交最小反馈  [ ] 支持人员可按构建号定位问题  [ ] 关键失败有用户可执行的替代路径  [ ] 发布失败可暂停扩散
- **Hard part**：不引入未经准入的崩溃 SDK；先用现有反馈和日志能力。

## 4. Phase 3

### Phase 3-A — 先取得可安装证据

**Covers**：R-1 上线构建可安装且可回滚、R-2 目标设备与关键交互通过验收。  
**Goal**：得到一个带构建号的可安装 development build，并完成首轮设备矩阵。

**Tasks**

- 补齐构建账号、项目标识、Dev Client 和原生工具前置
- 生成首个可安装 development build 并记录构建证据
- 用首个构建跑返回、安全区、横屏和大屏探针
- 逐屏执行关键内测页面的 13.1 验收
- 把失败项写入唯一缺陷总账并标记上线影响

**Proof**：陌生设备可安装；设备记录包含构建号、机型、系统、结果和复现信息。  
**Not here**：不在本阶段解决商店材料和新增业务功能。

### Phase 3-B — 关闭真实链路与商店红线

**Covers**：R-3 真实后端主链路可用、R-4 UGC 发布满足商店合规红线。  
**Goal**：真实账号可以完成核心读写路径，违规发布和越权访问会被服务端拒绝。

**Tasks**

- 部署并验证跨商品私信列表契约
- 增加消息历史游标并验证长会话轮询合并
- 增加线程归属校验并覆盖非法深链
- 建立条款接受版本与服务端发布门禁
- 建立屏蔽用户和账号注销的服务端闭环
- 用真实账号矩阵验证注册、课表、发布和代表性数据

**Proof**：真实环境契约测试通过；四类合规红线场景均有服务端拒绝或完成证据。  
**Not here**：不在本阶段引入实时私聊、原生推送、拼车或问答。

### Phase 3-C — 形成发布候选包

**Covers**：R-2 目标设备与关键交互通过验收、R-5 法务与商店材料达到提交条件、R-6 工程出口可重复且告警可解释。  
**Goal**：发布候选包通过自动化、设备、文案和法务四类门。

**Tasks**

- 接入批准的中英文隐私政策与服务条款正文
- 完成应用图标、启动页和版本信息核对
- 逐项修复设备缺陷并重跑受影响页面
- 按模块清偿 lint warning 并保留分类基线
- 连续两次运行完整 verify 和发布候选回归
- 生成商店隐私、数据安全和支持材料清单

**Proof**：候选包的自动化、设备、法务和材料检查均有可追溯记录；任何未通过项都阻止进入提交阶段。  
**Not here**：不把“0 warning”设为唯一上线门，也不扩展 v1.1 页面范围。

### Phase 3-D — 小范围发布与上线决策

**Covers**：R-1 上线构建可安装且可回滚、R-7 上线运行可观察、可反馈、可降级，并复核 R-3、R-4、R-5、R-6。  
**Goal**：先完成封闭测试和发布演练，再由所有者决定是否提交正式商店审核。

**Tasks**

- 发布候选包到封闭测试轨并登记测试者与安装指引
- 演练反馈、日志定位、暂停扩散和回滚
- 收集核心主链路的真实使用结果
- 复核商店红线、法务批准和构建材料版本一致
- 形成上线决策记录并明确遗留风险

**Proof**：封闭测试期间没有未分诊的 P0/P1；回滚演练成功；所有上线门都有负责人签字或证据链接。  
**Not here**：不在没有证据的情况下宣称正式上架完成。

## 5. Prerequisites and assumptions

- **Assumption A-1**：所有者可以提供 Expo/EAS 账号、构建权限和测试设备。
- **Assumption A-2**：后端团队可以部署私信、条款、屏蔽和注销所需接口。
- **Assumption A-3**：所有者可以提供批准的中英文法务文本和商店责任信息。
- **Assumption A-4**：校方系统测试允许使用测试账号和必要网络环境。

**Open questions**

- **Q-1**：开发者账号是个人还是组织？解决方式：首次封闭测试前确认；个人账号需要把 12 人 × 14 天计时纳入排期。
- **Q-2**：真实后端何时提供合规红线接口？解决方式：由后端负责人给出部署日期和契约地址。
- **Q-3**：正式法务文本由谁批准？解决方式：所有者指定责任人并提交中英文版本号。

## 6. Interfaces and handoffs

| 交付方 | 交付物 | 接收方 | 接收条件 |
|---|---|---|---|
| 构建负责人 | 可安装包、构建号、提交号 | 设备验收负责人 | 可冷启动 |
| 后端负责人 | 契约地址、真实账号矩阵、部署记录 | App 负责人 | 读写路径可复现 |
| 法务责任人 | 中英文批准文本与版本号 | 发布负责人 | 页面和商店材料同版本 |
| 验收负责人 | 设备矩阵与缺陷结论 | 所有者 | 每项有结果或阻塞原因 |
| 发布负责人 | 候选包、发布说明、回滚包 | 所有者 | DoIT 与上线门齐全 |

## 7. Rollback

- **Phase 3-A**：构建失败时保留当前代码和串行验证出口，不把未验证包分发给测试者。
- **Phase 3-B**：后端契约失败时关闭受影响入口，保留只读或手工粘贴降级路径，并记录为发布阻塞。
- **Phase 3-C**：设备或法务门失败时不生成发布候选，回退到上一份内部包继续验证。
- **Phase 3-D**：封闭测试出现 P0/P1 时暂停扩散，撤回候选包，恢复上一包并发布已知问题说明。

## 8. Not doing

- 不把 Phase 3 变成 v1.1 功能开发。
- 不用 mock、静态扫描或占位法务文本替代真实上线证据。
- 不用关闭 lint 规则、Jest `--forceExit` 或伪造设备记录来制造绿灯。
- 不在没有所有者上线决策和完整材料时提交正式商店审核。
