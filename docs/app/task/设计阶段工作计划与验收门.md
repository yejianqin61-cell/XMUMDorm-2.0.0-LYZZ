## 二、为什么必须先立宪、后写码

旧 App v1 的失败已被实测证实为**约束缺失**，而非技术选型错误。实测数据（见 [`../../06-Analyze/ui-research/App设计调研-00-旧App设计债实测基线.md`](../research/App设计调研-00-旧App设计债实测基线.md)）：

| 指标 | 旧 App v1 实测 |
|---|---|
| 硬编码色值 `#hex` | **1437 处 / 79 个文件** |
| `fontSize` 字面量 | **645 处** |
| 引用自有 UI 组件 | **0 次**（组件库写了 7 个，一屏未用） |
| `src/theme/` 令牌体系 | **不存在**（只有一个 469 B 的局部文件） |
| 暗色/外观 API | **0 次** |
| Reanimated / gesture-handler | 已安装，**0 引用** |

**推论**：旧 App 的问题不是"用了 Web 写法"，而是**每一屏都在自由发挥**。因此本阶段的成功判据不是"设计文档写得多漂亮"，而是**产出的约束能否被脚本验证**。

## 四、协作纪律（写入宪法候选条款）

1. **一个模块 = 一个写作用域 = 一个负责人**；令牌与原型组件由单一所有者维护，其他人只读。
2. **禁止并行修改** `tokens`、根布局、导航壳、原型组件。
3. **首个纵向切片必须先消费组件库与令牌**，通过后才允许模块铺开（旧 App 的组件库 0 引用就是这样发生的）。
4. **每完成一个模块立即过验收**，不留"最后统一验"。
5. **不得据已删除的旧文档写任何 App 代码**——旧设计材料只作历史参考，归档于 `app-legacy-v1`。

### 5.4 ⚠️ 阻塞级风险（必须在脚手架首周验证，不能等功能做完）

| 风险 | 内容 | 处置 |
|---|---|---|
| **R1：Android 上返回键可能直接退出 App** | target API 36 + Android 16 设备上，系统不再派发 `onBackPressed` / `KEYCODE_BACK`。RN 0.81 官方博客称 `BackHandler` 照常工作，但社区在 `react-native-screens` Discussion #2540 实测相反：RN 收不到事件 → 系统判定退出 Activity → **App 直接关闭**。上游 issue `expo/expo#39092` **至今 open**（标签指向 React Native Screens）。逃生舱 `android:enableOnBackInvokedCallback="false"`（官方支持、社区验证有效），**代价是没有系统返回预览动画 = 本机感有损** | **脚手架第一周做真机 spike**，结论决定导航架构；可能是 ADR。**在结论出来前，不锁返回栈的实现方案** |
| **R2：原生 Tab 栏在 SDK 57 上没有稳定入口** | 宪法第 4.3 条要求导航壳交给原生容器，但 **expo-router 的原生 Tab 在 SDK 54–57 只有 `unstable-native-tabs`**，稳定路径 `expo-router/native-tabs` 要等 SDK 58。而排期（§7.2）建议锁 SDK 57。**⚠️ 2026-10-02 追加要求**：第 5 格是**动作型 Tab**（点了**不切页**，而是打开发布中心）→ 需验证原生容器能否承载"非目的地格位" | 三选一，首周定案，见 §7.2；**禁止因此退回自绘 Tab 栏**（宪法 4.3）。**若做不到动作型格位，退路是"四格 + 发布 FAB"并请所有者重新裁决**（宪法 4.9.9） |
| **R7：安全区与屏幕适配（2026-10-02 新增，所有者点名）** | Android target 36 起 **edge-to-edge 不可退出**（宪法 5.3），每屏都必须处理 insets；漏一处的典型后果：内容被挖孔切掉、最后一行被手势条压住、底部双倍留白（Tab 栏自带安全区又被我们叠加一次）、键盘弹出后输入框不可见 | 宪法**第 17 条**（八条铁律）+ [骨架规范 §6](../design/App页面骨架与布局规范.md) 的 **≥8 机型矩阵**与 **10 条验收清单**；首周与 R1/R2 合并做真机验证（[TODO](../TODO.md) TD-32） |

> R1/R2/R7 **都没有纯 JS 解法**——属"必须先验证"的架构级未知项。R1 直接冲击「**五格**导航 + 各 Tab 返回栈 + 顶栏信箱」的设计。

## 七、排期与日历约束（所有者 2026-10-01 给定）

**所有者口径**：**没有硬性上限，但尽量在 1 个月内**（以 2026-10-01 起算 ≈ **2026-11-01**）。

### 7.1 唯一不可压缩的那一段：Play 封闭测试

Play 对 **2023-11-13 之后创建的个人开发者账号**要求：上架前必须完成 **≥12 名测试者连续 opted-in ≥14 天**的封闭测试，随后生产权限审核**最长 7 天**。**组织账号豁免。**

**倒推（个人账号情形）**：

| 环节 | 最短耗时 | 最晚必须开始 |
|---|---|---|
| 封闭测试轨构建可安装、≥12 名测试者全部 opted-in | — | **2026-10-11** |
| 连续 14 天 | 14 天 | → 最早 2026-10-25 满足 |
| 生产权限审核 | 最长 7 天 | → 最早 **2026-11-01** 上架 |

**结论**：个人账号情形下，1 个月目标**刚好卡满、零缓冲**。因此：

1. **第一个"能装到别人手机上的纵向切片"必须在 10 天内成立** —— 不是"一个月后有个完整 App"；
2. 封闭测试的 14 天与审核窗口**必须与其他开发并行**，不能排在开发之后；
3. **若为组织账号，这一整段不存在**，1 个月目标宽松得多。
4. → **账号类型从"越早定越省时间"升级为"决定 1 个月目标是否可行"**，是当前第一优先级的非设计决策。

### 7.2 由 1 个月目标倒推的 SDK 线：**建议锁 SDK 57**

Lead 早前的建议（等 SDK 58 稳定后从 58 起步，可免一次原生重建）**在 1 个月口径下不再成立**：

| 理由 | 事实 |
|---|---|
| 等待成本占预算的 25%~45% | SDK 58 GA 预计 **2026-10-06 ~ 10-13**（Beta 起于 2026-09-15，官方称 3–4 周）；今天已是 10-01 |
| 现有版本矩阵**全部是对 SDK 57 实测出来的** | expo 57.0.26 / RN 0.86.3 / React 19.2.3 / gesture-handler `~2.32.0` / expo-router 57.0.24 / `@expo/ui` 57.0.21 …… 换 58 等于让这套核对**作废重做** |
| 58 同时吃进三处迁移面 | ① expo-router 核心重构（官方原文 "remove a large portion of the forked react-navigation API surface"）② iOS 27 scene lifecycle ③ RN Strict TypeScript API |

**建议**：**锁 SDK 57 起步**，把 SDK 58 升级列为**独立、非阻塞**的后续任务。

### 7.3 随之必须处置的：原生 Tab 栏在 SDK 57 上怎么实现（**R2，首周定案**）

宪法第 4.3 条要求 Tab 栏交给原生容器，且**明令禁止"自绘导航壳 + 贴玻璃"**。但 SDK 57 上 expo-router 的原生 Tab 只有 `unstable-` 入口。三条路：

| 方案 | 内容 | 代价 |
|---|---|---|
| **(a) `expo-router/unstable-native-tabs`（建议）** | 一方官方；导入路径在 SDK 58 稳定后预计改名为 `expo-router/native-tabs`（属**改名级迁移**） | API 带 `unstable-` 前缀，意味着**跨 SDK 可能破坏**；但 SDK 57 线内由 `expo-router@57.0.x` 锁死 |
| (b) `react-native-bottom-tabs@1.4.0` | 第三方（MIT，2026-07-09 更新，实测）；真正的 `UITabBarController` / Android `BottomNavigationView` | 引入一个第三方**原生依赖** → 升级需重建，须登记"原生依赖=有/OTA 影响" |
| (c) 等 SDK 58 用稳定原生 Tab | 官方稳定路径 | **与 1 个月目标直接冲突**（见 §7.2） |

**处置**：脚手架**首周**在真机上验证 (a)，与 R1（返回键）spike 合并做；若 (a) 有阻塞问题则切 (b)。**任何情况下都不允许退回自绘 Tab 栏。**

**本次组件层调研补充的相关事实（2026-10-01 一手）**：

- `@expo/ui/jetpack-compose` **已有 `NavigationBar` 组件**（官方描述："NavigationBar component for Material 3 bottom navigation"）→ **但它是"一个组件"，不是带独立返回栈的导航容器**，**不能替代** §4.3 要求的 Tab 导航器。可作为 (a)/(b) 的前置观感验证手段。
- `react-native-bottom-tabs@1.4.0`（MIT，最后发布 2026-07-09，实测）→ 方案 (b) 的具体载体。
- `@expo/ui` 的 **8 个 drop-in 替代**里包含兼容 `@gorhom/bottom-sheet` 的实现 → **采用 (a)/(b) 时，底部弹层等控件应优先换成官方实现**，减少第三方原生依赖（宪法 9.10／11.4）。

### 7.4 排期骨架（4 周 + 缓冲）

| 周 | 目标 | 出口门 |
|---|---|---|
| **W1** 10-01~10-07 | 宪法获批 → 脚手架 + 令牌层 + 核心组件；**真机 spike 四合一：R1 返回键 + R2 原生 Tab 与动作型格位 + R3 校方系统内嵌与会话 + R7 安全区机型矩阵** | 首个纵向切片在真机跑通，且**真正消费令牌与组件库**（宪法 9.5）；**安全区 10 条清单在该切片上先过一遍** |
| **W2** 10-08~10-14 | 第一个完整纵向切片（广场 + 详情 + 发布）；**若为个人账号，本周必须把封闭测试轨构建发出去** | 封闭测试轨可安装、≥12 名测试者开始 opted-in |
| **W3** 10-15~10-21 | 其余一级 Tab 与高频模块铺开 | 每模块过宪法第 13 条逐屏验收 |
