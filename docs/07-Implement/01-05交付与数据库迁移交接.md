## 二、组长执行步骤

### 1. 先确认适用的原库基线

支持范围限定为 MySQL 8.0.16 及以上的 8.0 系列；实测 8.0.46。
不宣称支持 MySQL 5.7、MariaDB 或 MySQL 8.4；这些环境会被执行器拒绝。
最低版本与有效 CHECK 有关，依据 [MySQL CHECK 文档](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)。

原库必须是已经运行现有 XMUMDorm 的业务库，至少具备：

- users 的原有登录、角色、状态、资料和等级字段；主键为有符号 INT。
- 树洞 posts、图片、点赞、comments、广告排除表；posts 已有 title、content_origin、repost_source。
- notifications 的 type 为 VARCHAR(50)，extra 为 JSON，原 post_id 仍指向树洞，不能改为校园帖外键。
- 食堂 regions、shops、product_categories、products、图片、点评及点评图片、product_favorites。
- tags、post_tag_map、tag_visibility；必要字段及类型由只读预检逐项核对。

上述旧业务模块不是本次新快讯功能的全量重建对象；缺失时预检停止，不能运行 migrate:all 或 init-db.sql 猜测补齐。
可能相关的旧定义来自 001、002、007、011、013、030、047、062、070、076；应按实际缺项审核单独补丁，不能整目录重放。
本次涉及的表须为 InnoDB、utf8mb4_unicode_ci；旧库如有其他排序规则，需要先审核兼容方案，执行器不会自动转换。
存在触发器时停止并另行审核。开启 FK/UNIQUE 检查、显式 timestamp 默认值和 STRICT_TRANS_TABLES 或 STRICT_ALL_TABLES。

组长仍需提供或确认：目标数据库名、实例 UUID、实际版本、字符集/排序规则、相关 SHOW CREATE TABLE、既有迁移记录、目录稳定 ID 和备份恢复可用性。
只提供脱敏结构与汇总输出即可，不要发送密码、连接串、用户行、哈希或数据库数据备份到聊天。
本轮没有读取组长原库、下载生产数据或连接线上数据库。

### 3. 备份、暂停写入、迁移前检查

先在组长原库的独立恢复副本执行完整流程，验证旧数据及业务后，再排目标库窗口。
数据库和原图片/附件目录、对象存储都要有可恢复备份，核对备份可读并在独立库演练恢复。
备份保留在受控私有位置，不能进 Git。数据库备份不包含磁盘图片或对象存储对象。

如采用 MySQL 客户端备份，先用 mysql_config_editor 配置私有 login-path；密码在交互提示输入，不放命令参数。
以下 DATABASE_NAME 由组长替换，并与已核对身份一致；命令只供组长在目标环境执行：

```powershell
mysql_config_editor set --login-path=xmumdorm-migration --host=TARGET_HOST --port=3306 --user=MIGRATION_USER --password
mysqldump --login-path=xmumdorm-migration --single-transaction --routines --events --triggers --hex-blob --no-tablespaces --set-gtid-purged=OFF --result-file=.local/delivery/backup-before.sql DATABASE_NAME
```

成功判据：备份命令退出 0、文件可读、独立恢复验证通过；权限/例程/GTID 等错误必须由 DBA 解决后重新备份。
single-transaction 对 InnoDB 数据提供一致性，不保护并发 DDL；备份和迁移窗口禁止其他结构变更。

正式迁移前暂停应用写入、任务、通知 worker 和可能写同库的其他实例。
建议备份前即进入维护窗口，确保恢复点与迁移前数据一致。
原因：ALTER 和加索引会拿元数据锁；逐对象迁移期间新旧代码可能看到不完整结构，汇总数比对也要求无并发写入。

```powershell
node scripts/delivery-01-05/migrate.cjs pre .local/delivery/target.json > .local/delivery/before.json
if ($LASTEXITCODE -ne 0) { throw 'STOP: precheck failed' }
```

预检只读，输出身份、各步骤 pending/ready、新旧账本汇总和必要表行数；不要将输出解释为原库副本已经验收。
成功判据：退出 0、身份正确、所有已有对象兼容。pending 表示待新增，不表示错误。
BASELINE、INCOMPATIBLE、UUID、STRICT、LEDGER 等错误均必须停止；保留脱敏输出，核对实际定义后补独立修复方案。

### 4. 执行与迁移后检查

```powershell
node scripts/delivery-01-05/migrate.cjs apply .local/delivery/target.json
if ($LASTEXITCODE -ne 0) { throw 'STOP: migration failed' }
node scripts/delivery-01-05/migrate.cjs post .local/delivery/target.json > .local/delivery/after.json
if ($LASTEXITCODE -ne 0) { throw 'STOP: postcheck failed' }
node scripts/delivery-01-05/compare-checks.cjs .local/delivery/before.json .local/delivery/after.json
if ($LASTEXITCODE -ne 0) { throw 'STOP: row-count comparison failed' }
```

执行器使用数据库命名锁防止同一入口并发迁移；每个对象先写 started，成功且定义验证通过后才记 applied。
SQL 错误、未知警告、定义冲突、记录更新异常立即退出，不继续执行后续语句。
只接受实测的整数显示宽度弃用提示 1681 的完整固定消息；其他警告均停止并保留 started，交由 DBA 核对。
控制台不打印原始驱动 SQL 错误，避免泄露数据；不能为看见原始错误就把含数据的日志发到聊天。

成功判据：post 退出 0，verifiedSteps=46，所有账本 applied，38 条审核目录逐值一致，compare-checks 通过。
旧业务表数量应保持，目录最多只增加缺失的 10+28 行；新表为空是正常状态，不需要导入演示数据。
行数相同不能证明字段值相同。独立副本仍应使用受控数据比对验证关键旧字段；本轮测试的指纹校验只针对合成测试数据。
pre/post 也可单独重复运行进行只读检查；不要用健康接口代替结构验证。

### 6. 失败、重试与恢复

任一步失败即保持维护窗口，先保存退出码及脱敏 pre 输出。不要删除账本、改 SQL 哈希、禁用 FK 检查或手工标记 applied。
迁移在 DDL 发出前失败：started 保留，修复连接/锁/权限等原因后以相同代码重新执行 apply。
DDL 已成功但进程在记账前中断：重新执行会核对目标对象，定义兼容才补 applied，不重复执行已完成 DDL。
对象部分存在且不兼容：停止，依据 SHOW CREATE 和同哈希步骤核对；需要单独修复迁移，不能强制跳过。
账本 applied 但实际结构不符合：停止并视为漂移；SQL 文件哈希变化也停止，不自动重写历史。

目录 INSERT 与验证在一个事务中，失败全部回滚本次目录新增；已完成的结构步骤保留，下次补剩余目录。
目录冲突应核对原 ID/编码/中英文名，不覆盖目标原记录。网络断线导致 COMMIT 结果未知时，用 post 核对，再重跑 apply。
工具会逐条精确匹配并只插缺失记录，因此不会凭“上次断线”重复造目录。

MySQL CREATE/ALTER 会隐式提交，不能靠外包一个事务整体撤销。
单条 DDL 的原子性不等于整组迁移原子性，依据 [MySQL 隐式提交文档](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)。
本次没有默认 down SQL，也没有清表、删用户、重置密码或缩短正文的流程。

| 恢复方式 | 能恢复什么 | 限制 |
| --- | --- | --- |
| 回退代码 | 恢复上个应用版本 | 不撤销新表、新列和迁移记录；须验旧代码兼容，先停新 worker |
| 回退结构 | DBA 独立审批的反向 DDL | 删除新增表/列会丢新数据，MEDIUMTEXT 缩回 TEXT 可能失败；默认不执行 |
| 恢复备份 | 恢复某个时间点的数据与结构 | 丢失备份后新增业务；还须恢复匹配的文件/对象，先在独立库验证再切换 |

### 7. 组长用原有数据验收

1. 原账号正常登录，资料、旧帖子、原密码和条款状态保留；停用/封禁账号仍受限。
2. 学院列表与专业联动正确，保存并刷新仍为选定身份；未映射旧文本仍可见，不被自动改学院。
3. 旧组织校园帖可按原入口阅读，旧评论/点赞保留；审核归类后才进入新快讯列表。
4. 管理员创建草稿、发布、修改、撤回、隐藏/恢复，版本与审计对应；学生不能进入管理写接口。
5. 学生信息流与详情一致，点赞可取消，评论/回复目标正确，同一请求重试不重复发评论，删除后保留线程语义。
6. 我的帖子、点评与收藏分栏只返回本人数据，食堂收藏与快讯收藏分开；撤回或删除快讯后不可从收藏和通知读正文。
7. 给学院发布新快讯，仅合格冻结收件人得到通知；信箱读取/已读正常，pending 可投递并去重，失败保留重试记录。
8. 分享链接在新会话、刷新和登录后保留路径、查询、锚点；外站回跳被拒绝。
9. 原树洞普通发布、食堂标签入口、管理员公告、三图/三标签及原创声明仍正常；验证目标的真实上传和资源回读。

失败必须保留维护窗口并定位，不能因构建成功而跳过数据或业务验收。
