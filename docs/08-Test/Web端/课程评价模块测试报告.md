## 补充：Web 端「只显示 20 条」分页缺陷与修复（2026-09-26）

### 症状

线上 `course_reviews` 有 **412 条**未删除（2026-09-26 批量导入 407 条），
但 `/about/freshman-guide/course-review` 页面只显示 **20 条**，且没有任何「下一页 / 加载更多」入口。

### 排查数据（远程库 + 线上接口实测）

| 检查项 | 结果 |
|---|---|
| `SELECT COUNT(*) FROM course_reviews` | 413（`deleted_at IS NULL` 412，软删 1） |
| `created_by` 分布 | **1 → 407 条**，14 → 5 条 |
| `GET /api/handbook/course-reviews?page=1&pageSize=20` | `listCount=20`、`hasMore=true` |
| `…&page=2&pageSize=20` | `listCount=20`、`hasMore=true` |
| `…&page=21&pageSize=20` | `listCount=12`、`hasMore=false`（20×20+12 = **412**） |
| 线上页面 `.handbook-mini-card` 数量 | **20**（修复前） |

**结论：后端分页完全正常，缺陷在前端。**

### 根因

`frontend/src/pages/Handbook/CourseReviewPage.jsx` 写死了第一页：

```jsx
queryFn: () => listCourseReviews({ q, tags, page: 1, pageSize: 20 }),   // ❌ 永远第 1 页
select: (d) => d || { list: [], hasMore: false },                        // ❌ hasMore 直接丢弃
const list = query.data?.list || [];                                     // ❌ 只渲染第一页
```

既没有 `useInfiniteQuery`，也没有加载更多 UI → 列表被**永久硬顶在 pageSize 条**，
库里多少条都只能看到 20 条。`HandbookMe.jsx`（我的课程点评 / 我的收藏）同样的问题，
而 user 1 名下正好有 407 条。

### 修复

- 两个页面改为 `useInfiniteQuery` + `initialPageParam: 1` + 由 `hasMore` 驱动的 `getNextPageParam`；
- 新增纯逻辑模块 `shared/utils/infiniteList.js`（`flattenPages` / `nextPageParamFrom`）；
- 列表底部新增「加载更多 / Load more」按钮（复用 `HandbookHome` 既有的 `.handbook-loadmore` 样式），
  `hasNextPage` 为假时自动收起；筛选条件变化 → `queryKey` 变化 → 分页自动重置。

### 验证（本地 dev + 远程生产库，1440×900）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 公开课程评价列表首屏 | 20 条，无更多入口 | 20 条 + 「加载更多」 |
| 连续点击「加载更多」（20 次） | 不存在该入口 | **412 条**，最后一条 `/course-review/1`（库里最旧一条），按钮消失 |
| 我的课程点评（user 1，407 条） | 20 条，无更多入口 | 20 次点击 → **407 条**，按钮消失 |
| 切标签 GE → 加载 2 页 → 切回「全部」 | — | 20 → 60 → **20**（正确重置，不残留 60） |

新增单测 `__tests__/frontend/courseReviewPagination.test.js`（17 例）：分页纯逻辑、
「412 条 = 20×20+12」的真实场景还原、两个页面必须用无限查询的结构契约、
以及后端 pageSize 上限 30（说明前端**必须**翻页，调大 pageSize 不是解法）。

### 规约

1. **凡是响应里带 `hasMore` 的列表接口，前端一律 `useInfiniteQuery` + `nextPageParamFrom`，
   禁止写死 `page: 1`。** 写死第一页 = 列表永久硬顶，且不会报错，只能靠肉眼发现。
2. 判断「数据没显示全」的顺序：先数库（总数 / 软删 / 分组），再直接打接口的 `page=1,2,…最后页`
   验证 `hasMore` 边界，最后才怀疑前端——本次三步都做了，边界值 `20×20+12=412` 与库内 412 完全吻合。
3. 分页接口的 `pageSize` 上限（本次 30）是硬约束：**大列表只能翻页，不能靠调大 pageSize 治本。**
