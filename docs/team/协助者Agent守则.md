# 协助者 Agent 守则

**适用**：在本仓库里协助开发的 AI Agent（含被人类协助者临时唤起的 Agent）。
**日期**：2026-10-02　**版本**：v1.0　**上位规则**：[团队协作契约](团队协作契约.md)（人写的规则，Agent 同样受约束）；本守则只补"机器执行者"特有的那部分。

> **一句话结论**：协助者的成败判据**不是"改了多少"**，而是 **"别人能不能安全地接着改"**。
> 由此推出三条硬结果：**① 只写分配给你的路径 ② 每条结论给得出证据 ③ 没做完就说没做完。**

## 一、开工前必须按顺序读这四个

| 顺序 | 读什么 | 为什么 |
|---|---|---|
| 1 | `CLAUDE.md` | 全局事实与命令入口（模块数、测试数、尺子） |
| 2 | `docs/README.md` | 文档在哪一层 |
| 3 | **本任务涉及的那一层**（App 相关 → `docs/app/README.md`） | 不读就写 = 必然与既有约束冲突 |
| 4 | **`docs/app/TO-CONFIRM.md`** | **那里写着"哪些还没定"** —— 没定的事不许当已定来实现 |

## 二、六条铁律

| # | 铁律 | 违反的后果 |
|---|---|---|
| **1** | **一个模块 = 一个写作用域 = 一个负责人**。只写分配给你的路径，不顺手改别人的文件 | 并发写同一文件 → 覆盖别人的未提交改动 |
| **2** | **每条结论都要指得出证据**：文件 + 行号、命令 + 原始输出、或官方来源 URL | 无法复核的结论 = 制造返工 |
| **3** | **没做完就说没做完**。禁止把"我打算这么做"写成"已完成" | 下一个 Agent 会基于幻觉继续 |
| **4** | **改了代码就回写文档**；改了文档就修链接 | 文档与代码不一致 = 对下一个 Agent 说谎 |
| **5** | **不碰密钥**：不读、不打印、不提交 `.env`、token、keystore、`create-app-review-account.js` | 泄露不可逆（契约 §7：先轮换，再处理历史） |
| **6** | **不确定就停下问**，把问题写进登记册，而不是猜 | 猜出来的规格会在实现期炸 |

## 三、写作用域纪律

1. **改文件前先读**；被拒绝（`FS_STALE_VERSION` 之类）说明**有别人刚改过** → **重新读、把改动重做到新内容上**，⛔ 不要用覆盖写把别人的改动抹掉。
2. **并发场景（本仓库发生过）**：同一目录可能同时有另一个 Agent 在写。三条动作 —— ① 开工时声明自己**只碰哪些路径**；② 收工前**再看一遍 diff**，确认没有混进别人的改动；③ 发现不属于自己的改动**原样保留**，不要"顺手修一下"。
3. **提交时用显式路径**，永远不要 `git add .`（见 [Git 协作手册](Git协作手册.md)）。
4. **不提交**任何属于别人未完成工作的文件（哪怕它在 `git status` 里很碍眼）。
5. **开工前先同步、push 前先查远程**（两条都是硬检查）：
   - 开工前：`git fetch origin` + `git merge origin/main`（在他人分支上则 `git pull --no-rebase`）。**未同步就开始改 = 在旧代码上干活**，冲突会成倍放大。
   - 提交/push 前：`git fetch origin` 后 `git log --oneline HEAD..origin/<你的分支>` **必须为空**，否则先合并再推。
   - **发现别人改动了同一文件**：重新读文件、把自己的改动**重做到新内容上**；⛔ 不许覆盖写、不许 `push --force`。完整处置（含"被别人覆盖了怎么救"）见 [Git 协作手册 §六](Git协作手册.md)。

## 四、Git 禁令（Agent 专属，比契约更严）

⛔ **以下命令一律不得执行**，即使"看起来能解决问题"：

| 禁止 | 原因 |
|---|---|
| `git push` 到 `main` / 任何非本人分支 | 契约 §2：只通过 PR |
| **未经人类明确要求，执行任何 `git push`** | 推送是人类的动作；Agent 只提交到本地分支 |
| **push 前不 `fetch` 检查远程** | 会把别人的新提交顶掉或造成分叉 |
| `git push --force` / `--force-with-lease` | 会覆盖别人的提交 |
| `git reset --hard` / `git checkout -- .` / `git clean -fd` | 会删掉别人的未提交改动 |
| 对别人的分支 `rebase` / `merge` | 分支归属他人 |
| 删除分支 / 删除 tag | 历史与归档（如 `app-legacy-v1` 是唯一归档） |
| `git add .` | 会把 `.env`、临时文件一起提交 |
| 提交任何密钥、`uploads/`、`node_modules/` | 契约 §7 |

**需要"撤销"时**：先跑 `git status` + `git log --oneline -5`，把现状贴给人类，**由人类决定撤销方式**。

## 五、验证门槛（"我认为没问题"不算验证）

| 你改了什么 | 至少跑什么 |
|---|---|
| 任何 JS 代码 | `npm test`（期望 **46 套件 / 668 用例全绿**）+ 你新增/修改行为的针对性验证 |
| 数据库迁移 | 迁移脚本可重复执行（第二次应全为"跳过"），并在 PR 里写明回滚影响 |
| 文档（本仓库大量工作） | 链接自检（相对链接不得新增失效）+ 与代码事实逐条核对（**引用行号**） |
| App 设计文档 | 四把尺子：`design-debt-report` / `contrast-check` / `brand-ramp` / `gen-tokens` |
| 报"修好了"之前 | **贴原始输出或退出码**；非零退出必须解释清楚 |

⚠️ **脚本全绿 ≠ 结论正确**：例如 `design-debt-report.js` 只扫我们的 `src/`，`node_modules` 里的硬编码色值不会被计数但运行时照样生效。**别把"门过了"当成"事对了"。**

## 六、汇报格式（固定五段，缺一段视为没汇报）

```text
1. 我做了什么          —— 逐文件/逐命令，一句话一条
2. 证据               —— 命令 + 原始输出 / 退出码 / 文件:行号
3. 我没做什么 / 没验证什么  —— 明确列出（这一段最容易被省略，也最值钱）
4. 风险与不确定        —— 标 【已定】/【算得】/【提案】 中的哪一档
5. 需要人类定的        —— 一条一个问题，带选项与我的建议
```

⛔ **禁止**："已完成，请查看"（没有 2 与 3）；把估算写成实测；把 `【提案】` 写成既定规格。

## 七、什么情况下必须停下来问（四类触发条件）

1. **规格没定**：该问题在 `TO-CONFIRM.md` 里还没关闭 → 登记后停手，不要"先按我理解的做"。
2. **要动约束**：需要违反宪法、契约、或某份规范才能完成 → **停下，说明代价**，由人类裁决。
3. **要动破坏性操作**：删数据、改 schema 不可回滚、动生产环境、改签名/密钥 → 一律先问。
4. **事实矛盾**：两份文档互相冲突，或代码与文档冲突 → 报冲突，**不要自己选一个当真相**（宪法口径：以宪法为准；不确定时问）。

## 八、完成定义（DoD）

一个任务只有**同时**满足下列六条才算完成：

- [ ] 改动落在批准的写作用域内
- [ ] 相关测试/校验已跑，**并贴出结果**
- [ ] 受影响文档已回写（含链接）
- [ ] 没有提交任何密钥/临时文件/他人未完成的工作
- [ ] 未验证项与风险已明确列出
- [ ] 需要人类定的问题已进登记册（一条一个问题）
