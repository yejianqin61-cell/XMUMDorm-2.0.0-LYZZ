# 移动端页面清单与结构盘点（重写输入 v1）

> **用途**：全盘重写 `mobile/` 的施工输入。先定清「有哪些页面、长什么样、去哪」，再动手写 UI。
> **权威来源**：`frontend/src/routes/layoutRoutes.jsx`（路由表）+ `frontend/src/App.jsx`（顶层路由）+ `frontend/src/pages/`（103 个页面文件）
> **对照来源**：`mobile/src/screens/`（69 屏，即将废弃，仅用于核对功能是否遗漏）、`routes/*.js`（后端能力边界）
> **盘点日期**：2026-09-29
> **统计**：Web 端 **≈111 条路由**，其中 Layout 内 95 条、顶层 5 条、管理后台 11 条

> ⚠️ 仓库里还有 `frontend-app/` 目录（另一份前端源码），本次**不**作为依据，避免两套路由混淆。建议后续确认其去留。

## 一、一级导航（受 Android 原生 Tab ≤ 5 的硬约束）

Web 端一级为 5 个 Tab + 一个独立「发布中心」。移动端**保持 5 个**，发布改为全局 FAB（不占 Tab）：

| # | Tab | Web 一级路由 | 建议路由组 | 备注 |
|---|---|---|---|---|
| 1 | 广场 | `/about` | `(tabs)/square` | 聚合入口：热搜 / 校园 / 社团 / 二手 / 跑腿 / 新生指南 / 学习资料 |
| 2 | 树洞 | `/treehole` | `(tabs)/treehole` | 匿名；含万能墙 `/confession` 是否合并待定（§5-Q3） |
| 3 | 食堂 | `/eat` | `(tabs)/canteen` | 含商家端（是否进移动端见 §5-Q2） |
| 4 | 信箱 | `/mailbox` | `(tabs)/mailbox` | 通知中心 |
| 5 | 我的 | `/myzone` | `(tabs)/me` | 含日程类、设置、管理后台入口 |
| — | 发布 | `/publish` | FAB → 模态 | 发帖 / 发布二手 / 跑腿 / 评价 / 上传资料 |

**信息架构要点**：Web 端把 6 大子模块全挂在 `/about/*` 下（历史原因），移动端**不要照抄**这个层级——应按「广场 → 子模块」再进详情，共 3 层封顶。

## 二、布局原型库（12 种，先定原型再套页面）

重写时**只允许使用下列原型**；页面若有新需求，先扩原型库，不允许各页自己长样式（这是旧版 1144 处硬编码色值的成因）。

| 原型 | 定义 | 关键结构 | 适用 |
|---|---|---|---|
| **P1 信息流** | 单列卡片流，下拉刷新 + 触底加载 | 顶栏 + 筛选条 + 卡片列表 + 加载/空态 | 广场、校园、树洞 |
| **P2 瀑布流** | 双列错落网格 | 顶栏 + `FlashList numColumns={2} masonry` | 树洞图墙、二手列表 |
| **P3 详情** | 单实体详情 + 评论区 + 底部操作条 | 滚动内容 + 评论列表 + 固定底栏 | 帖子/商品/活动/菜品详情 |
| **P4 发布表单** | 字段表单 + 图片上传 + 提交校验 | 表单域 + 上传器 + 底部主 CTA | 发帖、发布二手/跑腿、评价 |
| **P5 列表+分类** | 左侧或顶部分类 + 右侧列表 | 分段控件 + 列表 | 新生指南、餐厅/商家、菜品类目 |
| **P6 搜索** | 搜索框 + 历史/热词 + 结果列表 | 搜索头 + 结果复用 P1 | 帖子搜索、食堂搜索 |
| **P7 榜单** | 排名列表（带名次/徽标） | 名次 + 条目 + 数值 | 食堂榜单、等级榜 |
| **P8 会话/聊天** | 消息气泡流 + 输入框 | 气泡列表（反向）+ 输入条 | 二手私信 |
| **P9 工具/日程** | 结构化工具页（表格/日历） | 自定义栅格 + 操作区 | 课表、待办、日记、假期 |
| **P10 设置/资料** | 分组行列表 | 分组 + 行 + 开关/箭头 | 设置、资料编辑入口、关于 |
| **P11 管理台** | 数据概览 + 审核列表 + 详情操作 | 概览卡 + 列表 + 操作弹层 | 管理员后台、组织管理、商家管理 |
| **P12 图文静态页** | 长文/协议/说明 | 标题 + 正文块 | 隐私政策、服务条款、算法说明、免责声明 |

## 四、盘点结论（三条，直接影响重写）

1. **一级 Tab 已有现成答案**：Web 的 5 个一级正好等于 Android 原生 Tab 上限 5。不需要重新设计信息架构，**只需把 `/about/*` 的 6 层深挂载压平**。
2. **原型收敛度很高**：111 条路由基本落在 12 种原型里，**P1/P3/P4 三种覆盖了约 60%**。这意味着「先把 P1/P3/P4 三个原型做扎实，再铺页面」是最高杠杆的路径，也与宪法「原语先行」一致。
3. **移动端特有的是 4 类，Web 端无法照搬，必须单独设计**：
   - **P8 聊天**（二手私信，Web 用轮询）
   - **P9 日程/工具**（课表、待办、日记；Web 是宽屏表格）
   - **权限与门槛**（登录墙、管理员/商家角色可见性）
   - **原生能力**（推送、相册、分享、触感反馈——Web 端完全没有）

## 五、待确认项（需项目所有者裁决，重写开工前定）

| # | 问题 | 影响 |
|---|---|---|
| **Q1** | **商家端（6 路由）+ 管理后台（11 路由）是否进移动端 v1？** 旧移动端做过（11 个后台屏），但它们占 17/111 ≈ 15% 的工作量，且是低频功能 | 直接决定工期与 Tab 结构 |
| **Q2** | 万能墙 `/confession` 与树洞 `/treehole` 是否合并为一个 Tab？两者都是匿名 | 影响一级 IA |
| **Q3** | `/about/map`（校园地图）与 `/eat/map`（区域地图）是否进 v1？Web 是 CSS 动效密集型，移动端需重做 | 地图能力需额外依赖（`expo-maps` 为 ALPHA） |
| **Q4** | 广告位 `/advertisement/:id` 是否保留 | 低优先，可延后 |
| **Q5** | 假期 `/myzone/holidays` 是否属于 v1 | 低优先 |
| **Q6** | `frontend-app/` 目录的去留 | 避免两套前端路由继续分叉 |

> **建议的默认答案**：v1 全量做（所有者已明确"全部做完才上架"），但 **P11 管理台放到最后一批**，且先用最小可用版（列表 + 处置动作），不做数据可视化仪表盘。
