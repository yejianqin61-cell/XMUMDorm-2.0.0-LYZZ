# 微信公众号推文排版模板与编辑器调研

> 调研日期：2026-09-26
> 调研对象：给 XMUMDorm（React + Express 学生社区项目）写公众号招募推文时，可用的排版方案——在线排版编辑器、Markdown → 公众号工具、自写 HTML/CSS 模板 + 内联化三条路线。
> 调研范围：只研究「排版产出物怎么进公众号后台」这一段。不研究公众号注册/认证/涨粉运营、不研究封面图与配图设计、不研究自动发布到草稿箱的 API 工程实现（只把配额与限制记录下来）。

---

## 1. 结论先行（推荐路径）

**首选：自部署 `doocs/md`（Docker 一条命令），配「公众号图床」，主题用内置的「简洁」或自写一份自定义主题 CSS。**

理由（每一条都能指回下面的来源与数据）：

1. **图片这一关它默认就能一并解决，而在线编辑器往往要靠「授权公众号」才能做到。** 微信公众号正文里的图片 URL 必须来自微信自己的接口（[官方新增草稿 API](https://developers.weixin.qq.com/doc/subscription/api/draftbox/draftmanage/api_draft_add)明确写「外部图片 url 将被过滤」；[官方上传永久素材 API](https://developers.weixin.qq.com/doc/subscription/api/material/permanent/api_addmaterial)明确写「腾讯系域名外使用，图片将被屏蔽」）。`doocs/md` 的图床列表第 8 项就是「公众号」，填 `appID` / `appsecret` / 代理域名即可把 Markdown 里的本地图片自动上传进微信素材链路（[README 图床表](https://github.com/doocs/md#支持的图床服务)）。在线编辑器这边，走「同步」路线（如 135 的 `[保存同步]`、96 的「同步公众号」）也需要**管理员扫码把公众号授权给第三方**，走「复制」路线则是纯前端复制、图片由你自己的浏览器发起，两条路各有代价——而 `doocs/md` 这条路是你自己的机器直连微信接口，**不需要把公众号授权给任何第三方**。
2. **它免费且许可宽松。** License 是 WTFPL（Do What The F*ck You Want To Public License），可自由使用与修改（[gh repo view 结果](#7-一手来源清单)）。
3. **它还在维护。** 最近一次提交 2026-09-24，13,374 star，TypeScript 单体仓库（[GitHub](https://github.com/doocs/md)）。对比之下 `mdnice` 最近提交停在 2023-10-06、`lyricat/wechat-format` 上游已声明停止维护。
4. **它是给程序员用的。** 主题是一份可读的 CSS（`packages/shared/src/configs/theme-css/*.css`），用 CSS 变量驱动，你可以直接 `git clone` 改成 Dorm 的品牌色，改动可版本管理——这正好匹配「需要能反复复用的模板」这个诉求。
5. **不用赌第三方站点会不会倒。** Docker 自部署，`docker run -d -p 8080:80 doocs/md:latest` 就完事。

**次选（如果只想 30 分钟内发出去）**：直接用在线版 https://md.doocs.org ，主题选「简洁」，发完再说。

**不推荐**：为这件事现学秀米/135 的模板库。老牌编辑器吐出的 DOM 是大量嵌套 `<section>` + 内联样式（**第 3.13 节**给出了三类证据：微信官方机制、厂商自述、第三方旁证），后期改不动；而且微信官方[编辑器插件开发规范](https://developers.weixin.qq.com/doc/subscription/guide/product/plugin_spec.html) 明确写了「同一标签名、同一内联样式、仅包含单个子节点的连续嵌套链路**不应超过 10 层**，超出此限制时，**编辑器会自动精简冗余的嵌套层级**」——嵌套越深，被编辑器自作主张改动的风险越大。更关键的是微信开放社区里有一条**官方回复**：「用了第三方插件无论预览、发表，双端表现不一致**找第三方插件客服**」——平台明确不为这条链路的一致性负责（[来源](https://developers.weixin.qq.com/community/develop/doc/0000c070a586c8a892154412161800)）。

> 如果你的目标只是「今天发一篇」，第 3.14 节的排序是：**壹伴（唯一官方支持「导入 HTML」+ Markdown）> 135编辑器（免费可用 + 一键排版吃 Markdown 语法）> 易点编辑器（免费额度最透明）**。但请注意，**这三家没有一家的会员价格被官方公示到可核实**（见 8.3）。

## 2. 微信官方的硬限制（决定一切的前提）

### 2.0 先说清楚：官方到底有没有一份权威文档

**有，但只有一份，而且它不是「HTML 标签白名单」。** 官方在 2026 年仍在更新的是一份面向编辑器插件开发者的规范：

- [微信公众平台编辑器插件开发规范](https://developers.weixin.qq.com/doc/subscription/guide/product/plugin_spec.html)（对应服务号版 [同页](https://developers.weixin.qq.com/doc/service/guide/product/plugin_spec.html)）
- 官方还提供了该规范的**官方实现与测试用例仓库**：[wechatjs/verify-article-structure-spec](https://github.com/wechatjs/verify-article-structure-spec)（MIT，12 star，最近提交 2026-09-10），CLI 基于 puppeteer（注意：**未发布到 npm，需 clone 后自己跑**，见 6. 路径 A 第 6 步的更正）

**官方至今没有一份「公众号正文支持哪些 HTML 标签 / 哪些 CSS 属性会被丢弃」的完整白名单文档。** 微信开放社区里反复有人问这个问题（例如 [「公众号新建草稿箱接口,推送的 html 数据行内 style 样式丢失怎么解决?」](https://developers.weixin.qq.com/community/develop/doc/000484ae0f42a870a97f98d125b400)、[「调用新建草稿的 API，传入的 content 是 html, 为何样式会乱？」](https://developers.weixin.qq.com/community/develop/doc/00046c6febcd282048a0492116b800)），这两个都是「置顶精选热门」帖，都没有官方给出完整清单。所以：

> **本节把「官方文档明确写了」与「开发者社区实测共识」严格分栏标注。凡标「社区共识」的，都不代表微信承诺过，只是多方独立来源一致。**

### 2.1 【官方明确写了】正文内容的硬配额

来自[新增草稿 API `content` 字段说明](https://developers.weixin.qq.com/doc/subscription/api/draftbox/draftmanage/api_draft_add)（[更新草稿](https://developers.weixin.qq.com/doc/subscription/api/draftbox/draftmanage/api_draft_update.html)同）：

| 项目 | 官方原文 |
| --- | --- |
| 标签支持 | 「支持 HTML 标签」 |
| 正文字符数 | 「必须少于 2 万字符」 |
| 正文字节数 | 「小于 1M」（同页另一处写「大小不可超过 2kb」，两处自相矛盾，以前者为准需自行验证） |
| 脚本 | 「此处会去除 JS」 |
| 图片 | 「涉及图片 url 必须来源『上传图文消息内的图片获取 URL』接口获取。**外部图片 url 将被过滤**」 |
| 标题 | 「总长度不超过 32 个字」 |
| 作者 | 「总长度不超过 16 个字」 |
| 摘要 | 「总长度不超过 120 个字」，未填则默认抓正文前 54 字 |
| 图片消息 | 「仅支持纯文本和部分特殊功能标签如商品，商品个数不可超过 50 个」 |

来自[上传永久素材 API](https://developers.weixin.qq.com/doc/subscription/api/material/permanent/api_addmaterial)：

| 项目 | 官方原文 |
| --- | --- |
| 素材 URL 可用范围 | 「永久图片素材新增后，将带有 URL 返回给开发者，开发者可以在**腾讯系域名内使用（腾讯系域名外使用，图片将被屏蔽）**」 |
| 素材库配额 | 「图文消息素材、图片素材上限为 **100000**，其他类型为 **1000**」 |
| 正文外链图片 | 「图文消息的具体内容中，微信后台将**过滤外部的图片链接**，图片 url 需通过上传图文消息图片接口上传图片获取」 |
| 正文图片上传接口限制 | 「上传图文消息图片接口所上传的图片，**不占用**公众号的素材库中图片数量的 100000 个的限制，图片**仅支持 jpg/png 格式，大小必须在 1MB 以下**」 |
| 站内链接 | 「图文消息支持正文中**插入自己账号和其他公众号/服务号已群发文章链接**的能力」 |

### 2.2 【官方明确写了】结构规则：违反会被编辑器自动删除/精简

来自[编辑器插件开发规范 · 第 2 节「文章结构类」](https://developers.weixin.qq.com/doc/subscription/guide/product/plugin_spec.html)：

- **嵌套层级限制**：「排版中，同一标签名、同一内联样式、仅包含单个子节点的连续嵌套链路不应超过 **10 层**。超出此限制时，编辑器会**自动精简**冗余的嵌套层级。图片、视频、SVG 等媒体标签不受此限制。」
- **`<span leaf>` 节点规范**：行内容器，内部**只能**包含行内元素（`span, strong, img` 等）或文本，**严禁包裹块级元素**（`section, div, p`）。
- **`<section nodeleaf>` 节点规范**：只能包裹官方指定的特定组件或 `img`。
- 总则：「不符合规则的结构会被编辑器自动删除。」

> 这三条对「从秀米/135 复制过来的模板」是致命的：那些模板恰好是深层嵌套 `<section>`。

### 2.3 【官方明确写了】CSS 属性「使用规范」（注意：是规范，不是白名单）

官方这一节列的是「不当使用会破坏编辑器或最终呈现」的项，**不是「其余都会保留」的白名单**。原文列出的违规项：

| 属性 | 官方指出的错误场景 | 影响 |
| --- | --- | --- |
| `opacity` | 把 `img` 的 `opacity` 设为 0，把带背景图的 SVG 叠在同一位置 | 发布后无法在后台修改图片（编辑器改不了 SVG 背景图） |
| `caret-color` | 输入光标设为完全透明 | 编辑器中看不到光标位置 |
| `line-height` | 容器行高小于字号，多行文字重叠 | 移动端行与行重叠。**豁免**：图片无缝拼接、实际只渲染成单行文字 |
| `width` | 设置**固定宽度**，未随屏幕自适应 | 三类问题：居中布局不一致、内容溢出被截断、不同屏幕下宽度差异大 |
| `height: 0` | 容器高度设 0 | 编辑器里能看见（外层有最小高度），**移动端文字完全不可见**。豁免：SVG 内部元素、SVG 交互容器、内部无文字 |
| `height` 固定值 | 父容器固定高度 < 子元素实际内容高度 | 内容被裁剪。设置滚动属性的容器豁免 |
| `text-align` | 用 `start` / `end` 值 | 不同终端兼容性差异，出现居中/居左不一致 |
| `pre` 标签 | 用 `<pre>` 包裹普通段落文本 | `<pre>` 默认 `white-space: pre`，移动端窄屏水平截断。官方推荐改用 `<section>` 或 `<p>` |
| SVG `animate` 的 `begin` | 只设 `touchstart` | PC 端不触发，需写成 `begin="touchstart; click"` |
| `!important` | 任何场景 | 「无论何种场景，平台均**不建议**创作者在排版时使用 `!important`」，会使平台公共样式失效，且 Dark Mode 算法也需用 `!important` 覆盖 |

官方同时给出了三个**豁免属性**（这是全网少有人提到的、非常实用的一手信息）：

- **`data-ignore-width`**：加在节点上，跳过该节点及整棵子树的 width 相关检测。适用：横向滚动容器、`overflow:hidden` 视觉裁剪、第三方固定尺寸组件、SVG 交互布局。
- **`data-ignore-dm`**：值写要忽略的规则名（`low-contrast` 跳过对比度过低检测；`text-bg-gradient` 跳过渐变背景检测），**仅对该节点生效**。
- **`data-no-dark`**：指定当前节点跳过 Dark Mode 算法转换，**仅当前节点**，后代仍会被转换。

以及一条实用性极高的建议：**「建议给 `<img>` 添加 `data-w` 属性」**，值为图片原始像素宽度（如 1080×800 的图 `data-w="1080"`）。官方检测引擎在图片加载超时时按 `img.style.width` → `data-w` → `width` 属性兜底；都没有时会塞 1×1 透明 SVG 兜底。

### 2.4 【官方明确写了】字体与 Dark Mode

- **字体**：「**核心原则：不建议设置任何字体族（`font-family`）**。」公众号已设定优化过的默认字体栈；自定义会让创作端与阅读端（iOS/Android）视觉不一致，iOS 17+ 部分版本会因字体映射差异出现明显字号/字距变化。
- **Dark Mode 颜色**：算法「尽可能保留原文信息」，仅当对比度不足或亮度过高时调整。**「如非必要，文字背景尽量不要使用渐变」**——算法会先把渐变 mix 成纯色再转换，格子背景这类渐变装饰在 Dark Mode 下会直接消失。纯背景（上方无文字）的渐变不受影响。
- **Dark Mode 结构**：「严禁使用绝对定位或变形等手段破坏视觉与结构顺序的一致性」（算法按深度优先遍历）。
- **背景图补色**：`background-image` 上方文字在 Dark Mode 保留 Light Mode 原色，算法对背景图引入「补色」机制。

### 2.5 【官方明确写了】外链 `<a>`、`<script>`、`<iframe>`、`<video>`

| 项 | 结论 | 来源性质 |
| --- | --- | --- |
| `<script>` | 「此处会去除 JS」（新增草稿 API 原文） | **官方** |
| 外链 `<a href>` | 旧接口[「上传图文消息素材」](https://developers.weixin.qq.com/doc/subscription/api/notify/message/api_uploadnewsmsg.html)原文：「具备**微信支付权限**的公众号，可以使用 `a` 标签，其他公众号不能使用。」同时明确「图文消息支持正文中插入自己账号和其他公众号/服务号已群发文章链接的能力」 | **官方**（但注意这是已标记为「该能力已更新为草稿箱」的旧接口，草稿箱接口未重复该限制——实际后台行为以编辑器为准） |
| `<iframe>` | 「公众号文章是不允许嵌入 iframe 页面的，也不允许图片资源引用外链」——[微信开放社区官方回复](https://developers.weixin.qq.com/community/minihome/doc/000804f9e2c020f007aab3bd65ac00)（2020-07-09） | **官方社区回复**，非正式文档 |
| `<video>` / `<audio>` | 官方规范中出现 `视频` 作为「不受嵌套限制的媒体标签」，并提到 `<svg>`/`<video>`；社区一致认为应使用微信自家的 `mpvoice` / `mpvideo` 组件标签而非原生 `<video>`。官方未给出原生 `<video>` 的明确支持声明 | **混杂**：规范侧面提及为官方；`mpvoice`/`mpvideo` 属社区共识 |
| 外链打开 | 微信对非微信域名外链有安全提示与[《微信外部链接内容管理规范》](https://weixin.qq.com/agreement/weixin_external_links_content_management_specification)约束 | **官方** |

### 2.6 【社区共识】`<style>` / `class` / `id` / 外部 CSS —— 微信官方从未正式声明，但多方实测一致

官方 API 文档只说「会去除 JS」「外部图片 url 将被过滤」，**从未说过 CSS 会被怎么处理**。以下是开发者社区、开源工具源码与实测文章的一致结论（**不属于官方承诺**）：

| 项 | 社区一致结论 | 佐证来源 |
| --- | --- | --- |
| `<style>` 标签 | **被剥离**，其中的 CSS 规则全部不生效 | [wewrite/references/wechat-constraints.md](https://github.com/oaker-io/wewrite/blob/main/references/wechat-constraints.md)、[axtonliu 的 HTML/CSS 支持概览](https://www.axtonliu.ai/newsletters/ai-2/posts/wechat-article-html-css-support)、[min-skill/wechat-html-constraints.md](https://github.com/limin112/min-skill/blob/main/skills/wechat-publish-template/references/wechat-html-constraints.md) |
| 外部 CSS / `@import` / `@font-face` | 不允许 | 同上 |
| `class` 属性 | 保留也会被剥；即使保留也无对应规则 | 同上 |
| `id` 选择器 | 无意义（无样式表可用） | 同上 |
| `@media` 媒体查询 | 无效（没有地方写规则） | axtonliu、min-skill |
| `::before` / `::after` 伪元素 | 不可用 | min-skill、wewrite |
| `position: absolute / fixed` | 部分会被剥；官方规范也从 Dark Mode 结构角度明确反对绝对定位 | min-skill、官方规范 4.2.2 |
| `float` | 社区称被剥或慎用 | axtonliu、codechina |
| `transform` / `animation` / `transition` | 被过滤 | min-skill |
| `background-image: url(外链)` | 外部图片链接会被过滤 | 官方（图片规则）+ 社区 |
| `display: flex` | **新版编辑器部分支持**，旧版不支持 | min-skill（保留 flex）、wewrite（建议改用 `section` + 样式化) |
| `data-*` 自定义属性 | 除 `data-src`（图片）外一般会被剥；但 `data-w` / `data-ignore-width` / `data-ignore-dm` / `data-no-dark` 是官方认可的 | 官方规范 + 社区 |
| `<form>` / `<input>` / `<button>` | 功能上不可用 | min-skill |
| 内联事件（`onclick` 等） | 被剥除 | axtonliu |
| 内联 `style` 属性 | **这是公众号唯一稳定支持的样式方式** | 所有来源一致，且官方规范通篇以 `style="..."` 举例 |

### 2.7 【社区共识】图片防盗链与 `referrerpolicy`

**官方已经写明**：「腾讯系域名外使用，图片将被屏蔽」。社区把它讲清了机制：

- `mmbiz.qpic.cn` 判断请求头 `Referer`。非微信域名 → 返回一张「此图片来自微信公众平台，未经允许不可引用」的占位图。（[Admirable Pro 的分析](https://admirable.pro/wechat-platform-referer/)、[腾讯云开发者社区](https://cloud.tencent.com/developer/article/1093600)）
- **绕过办法一（不彻底）**：页面/文档加 `<meta name="referrer" content="never">` 或 `content="no-referrer"`，让浏览器不发送 Referer。**PC 端有效，iOS App 端实测仍为空白**（[腾讯云社区原文](https://cloud.tencent.com/developer/article/1093600)、[CrazyMing](https://blog.crazyming.com/note/2694/)）。
- **绕过办法二（自建中转）**：服务端代理转发并把请求头 `Referer` 改写为空/微信域名（[hopkinson/wxpic](https://github.com/hopkinson/wxpic) 是现成示例）。有法律与稳定性风险，且**对公众号正文本身没有意义**。
- **正确做法**：图片上传进微信自己的链路。要么走公众号后台素材库，要么调「上传图文消息图片」接口（jpg/png，<1MB），要么用编辑器自带的「公众号图床」功能。**这就是为什么 1. 节的推荐把「能自动上传到公众号」当作第一判据。**

### 2.8 正文容器宽度与推荐排版值

**「677px」这个数字有一个官方出处**：官方[编辑器插件开发规范](https://developers.weixin.qq.com/doc/subscription/guide/product/plugin_spec.html) 在解释 width 问题时原文写道「在 375px 屏幕上撑满甚至溢出，**在 677px 屏幕上只占 74%**」。即 677px 是官方语境下的编辑器/宽屏容器宽度。

但**官方对 width 的规范方向是「不要写固定宽度」**（见 2.3）。所以正确写法是：

```html
<section style="max-width:677px;width:100%;margin:0 auto;padding:0 16px;">
```

而不是 `width:677px`。这一段是本次调研对社区通行做法（大量文章直接教人写死 677px）**做出的修正**，依据是官方 width 违规规则。

### 2.9 【社区共识，官方未核实】正文字数与图片数量上限

- 有第三方文章称：**正文上限 50000 字，图片最多 500 张**（[中华网转载的运营规则文](https://m.tech.china.com/digi/articles/20250409/202504091658585.html)，2025-04）。**这份数字无法在微信官方文档中核实**，与官方 API 的「2 万字符」也不在一个口径（后台编辑器 vs 接口）。请以实际编辑器为准。
- 有社区帖反映「正文总大小不超过 10M 字节」的限制（[微信开放社区](https://developers.weixin.qq.com/community/develop/doc/000e886d5f83f8199a2d9890b5b400)），**同样无官方文档佐证**。

### 2.10 一句话总结第 2 节

> **公众号正文 = 一张只能写内联 `style` 的静态 HTML 页面。没有 CSS 文件、没有类选择器、没有脚本、没有 iframe、没有外部图片。** 所有排版方案最终都要产出「扁平结构 + 全内联样式 + 微信素材库图片 URL」的 HTML。谁帮你把这三件事做掉，谁就是好工具。

- **缺点**：**免费额度与价格完全未查到**（官网不公示价目，只有 token 计费口径）；API 有 **2 分钟/次**的频率限制且 `markdown` 入参上限 5000 字，**对长文不友好**；官网存在大量 `/geo/article/...` 的 SEO 内容（自述「排版外包 80–150 元/篇」「用有一云省 90%」），**营销色彩重，其自述数据不可作中立依据**（[官网 SEO 内容](https://www.uecloud.com/geo/article/xVj1)）；第三方（壹伴自有域名，**竞品口径**）称「有一云 AI 写东西还行，就是**排版不太灵活**」（[来源](https://yiban.io/geo/31049)，竞品倾向，不可作中立事实）；产品定位在 AI 营销而非排版，是否长期维护排版能力未知。

### 3.13 「嵌套 `section`」与「复制后空行」到底是什么性质的问题

**先把一个容易搞错的事说清楚**：本次调研**没有找到针对单家编辑器的、点名式的、中立的社区评测**（知乎 / CSDN / V2EX 未命中具体点名帖）。能拿到的证据是三类，可信度依次递减。

**（第一类）微信官方的通用机制——这一类是硬证据**

1. **嵌套层级限制（官方硬性规则）**：官方规范明确「同一标签名、同一内联样式、仅包含单个子节点的连续嵌套链路**不应超过 10 层**。超出此限制时，**编辑器会自动精简冗余的嵌套层级**」，并给出 10 层 `<section>` 嵌套的示例（第 11 层会被删除）（[plugin_spec.html §2.1](https://developers.weixin.qq.com/doc/subscription/guide/product/plugin_spec.html)，见本文 2.2）。
   → **推论（推测，已标注）**：第三方编辑器普遍用「多层 `<section>` 包裹 + 全内联 style」实现样式，一旦超过官方 10 层阈值就被**后台自动精简**，用户在编辑器里看到的和最终发布出去的可能不一致。**这不是某家的 bug，是平台规则。**
2. **复制到公众号出现大量空行——微信官方社区置顶帖**：[《公众号代码块导致文章末尾空行？》](https://developers.weixin.qq.com/community/develop/doc/0000c070a586c8a892154412161800) 用户报告「**手机端文章末尾有大量空行留白**，电脑端草稿箱编辑无问题，**代码块越多文章末尾空行越多**」。**官方回复：「不用第三方插件是否有问题呢？……用了第三方插件无论预览、发表，双端表现不一致找第三方插件客服。」**
   → 这是本次调研里**最有分量的一手材料**：它等于官方明确表态——「第三方编辑器 → 公众号」这条链路的双端不一致，责任在插件侧，微信不管。
3. **复制后格式全丢——微信官方社区置顶帖**：[《从网页复制内容到公众号保存后格式发生混乱该怎么办？》](https://developers.weixin.qq.com/community/develop/doc/0006c0e7ba85501fa36295c6a66000) 用户用 Typora 编写、导出 HTML 后复制进公众号编辑器，「**点击『保存草稿』之后，格式全部丢失，变成了没有格式的文本**」。
   → **注意这条针对的是「自己写 HTML 再复制」这条路（也就是本文方案 C）**。它说明方案 C 的核心风险真实存在且有官方社区记录：**编辑器里的预览 ≠ 保存后的结果**。
4. **内联样式是平台硬约束**：公众号编辑器不支持外链 / 内嵌 CSS，必须把样式内联到每个元素的 `style` 属性（常规解法就是 `juice`）；同时不支持 CSS 变量 `var()`、`::before` / `::after` 伪元素（[社区技术文章](https://cloud.tencent.com/developer/article/2436347)、[EvoAI-li/md-to-weixin](https://github.com/EvoAI-li/md-to-weixin)）。这是「满屏内联样式」的根因。

**（第二类）厂商自己承认的问题——可信度较高，因为是自曝**

5. **秀米官方自认复制会错乱**：官方渠道教程原文「**粘贴的时候不要粘贴到其他模板组件的结构里，否则很容易出现格式错乱的问题……如果无论怎么粘贴都还是出现格式错乱，那就别勉强了，改用同步或全文复制**」（[秀米官方向导文](https://www.sohu.com/a/441419608_330573)）。秀米另出 Chrome 插件，自述解决「**复制粘贴引起的格式丢失，例如特定 SVG 功能**」。
6. **键盘喵官方自认复制有阴影**：官方帮助中心专文《为什么文章复制到公众号会有阴影》（[来源](https://www.jianpanmiao.com/help/info/id/7086.html)）。
7. **135 官方自认「复制」能力有限**：官方帮助写「使用 [复制] 功能的限制较多……如果文章中含有 SVG 效果则需要使用 [保存同步] 功能」，而同步需管理员扫码授权公众号（[来源](https://www.135editor.com/essences/9490.html)）。

**（第三类）第三方实测文章——可信度最低，仅作旁证**

8. **「空格 → `&nbsp;`」机理分析**：公众号编辑器底层是富文本 iframe，**会把空格自动转义成 `&nbsp;`**；当 HTML 里有多层 `<span>` 嵌套且经过代码美化器缩进后，系统会把缩进空格识别为用户输入的空格，「文字里就插入了许多莫名其妙的『空格』，主要分布在段落结束、空行，以及原本预留了空格的地方」，「每次删都浪费快半个小时」（[艾瑞克的博客](https://www.zengjianpeng.com/2020/11/16/编辑器那些无中生有的-空格/)）。
9. **「改不动」的真实工作流**：有运营团队记录了从秀米复制到后台后，想**加一个空行**或**删一个模板**都只能开浏览器开发者工具**手动改 HTML**，因为「模板之后没有小光标不好直接 ENTER 空行」「有的模板的复杂性，直接用删除键是删不干净甚至会出现排版混乱的情况」（[CSDN 运营技术文档](https://blog.csdn.net/verse_armour/article/details/131405177)）。
10. **代码冗余对比（第三方）**：「秀米偏好 `<section>` + `data-*`；135 习惯用嵌套 `<section>` + 类名控制样式」；「微信编辑器里那些带底色的卡片、复杂的图文混排模板，**背后的代码嵌套能有十几层**。复制到其他编辑器，90% 会崩」（[TrueSight](https://tsight.io/articles/18118138)、[前沿AIGC资讯](http://www.aishici8.com/ai/ement.html)、[代码聚汇网](https://codechina.net/article/weixin_29007135/203089)）。
11. **「段落间距忽大忽小」**：编辑器里敲回车「有时会生成 `<p>` 标签，有时又是 `<section>` 标签，甚至混合使用」，不同解析规则导致间距不一致；该文给的规避建议是「复制前先在公众号后台清除格式，或先粘到记事本做中间跳板」——**这些额外步骤本身就是证据**（[前沿AIGC资讯](http://www.aishici8.com/ai/ement.html)）。
12. **通用错乱机理（社区问答，非官方）**：多因从 Word / 网页复制带入 `mso-` 等冗余私有样式、以及 HTML / 可视化模式来回切换导致嵌套错误与闭合缺失；建议「纯文本粘贴」「清空格式」，避免定稿后再切 HTML 模式（[CSDN 问答](https://ask.csdn.net/questions/9074683)）。

> **合起来看**：这两类缺点**不是某家的个案，是「第三方编辑器 → 公众号」这条链路的平台级结构问题**。根源正是本文 2.5 / 2.6 那两条——**`<style>` 和选择器不可用，所以一切样式只能内联；内联就得靠嵌套 `section` 承载；嵌套一深就撞官方的 10 层自动精简**。这个结论直接支撑第 1 节的推荐：与其在海量模板里挑一个「没那么脏」的，不如拿一份干净的 CSS 自己控制嵌套层数。

### 3.14 结论：哪几个最适合「技术项目 + 极简科技感 + 免费」

**先说结论：这 11 个工具里，没有一个以「极简科技感 + Markdown 优先 + 完全免费」为核心定位。** 它们清一色是「模板素材库 + 会员订阅」的营销/运营向工具，模板库规模越大，免费版被锁的部分越多。**更麻烦的是：本次调研中，11 家全部没有可指回 URL 的一手「风格分类」数据**，所以「偏商务 / 偏学生 / 偏极简 / 偏节日营销」这类标签，本文**不为任何一家编造**——只有 135（官网设政企/教育专栏，偏政企教育）与 965/365（办公向）能间接推断。下面是「最接近」的排序，不是「完美匹配」。

**第一梯队（值得一试，但仍需你自己砍掉装饰）**

1. **壹伴**（https://yiban.io/ ）——**名单内最贴合技术项目的一家**。
   - 官方 12.4.0（2026-09-22）更新日志明确列出「**Markdown 排版**」，是名单内**唯一有官方 Markdown 声明的产品**；
   - 更关键的是官方更新日志含「**导入 HTML**」——对技术项目是决定性优势：你可以自己写极简内联样式 HTML（**完全掌控 `section` 层数 ≤10、无冗余嵌套**），再整段导入，绕开模板库的营销风样式；
   - **插件形态直接嵌入公众号后台**，天然规避「复制粘贴导致格式丢失 / 空行 / 夜间模式看不见字」这条最常见的痛点（微信官方在社区贴里把双端不一致直接甩给第三方插件）。
   - **风险**：**官方会员价格未查到**（只有第三方矛盾数字）；免费版具体边界无官方口径；官方 SEO 文**自曝**「智能排版后格式整齐了，但**样式太固定**。想改点细节，还得自己手动调」「排版样式少，不灵活」（[来源](https://yiban.io/geo/31049)，官方 SEO 内容，营销倾向）。
2. **135编辑器**（https://www.135editor.com/ ）——**免费可用的「经典排版」，且一键排版吃 Markdown 语法**。
   - 官方明示「**经典排版（核心产品，可免费体验）**」，免费层有实质功能，不是纯试用；
   - [官方公告](https://www.135editor.com/essences/4127.html)确认**一键排版支持 MarkDown 语法**（用 `#` 识别标题），意味着可以把 Markdown 结构喂进去做骨架；
   - 官方宣称 **10W+ 模板**，可「精细调参自定义字体」「SVG 动效」，配合「清空全文格式」能压到极简风。
   - **风险**：**文档导入要付费**（官方帮助明示）；VIP 素材占比高；高级 / 超级会员价格未查到；模板整体偏政企 / 营销，**极简科技感需要自己清格式重排，不是开箱即得**。
3. **易点编辑器**（https://www.wxeditor.com/ ）——**免费额度透明度最高的一家，适合零成本试**。
   - 官方免费「基础版」**不限次导入 Word / Excel**，可存 10 篇文章、绑 1 个公众号、图片 100 张/月，**完全免费无试用期**；升级门槛低（专业版 ~8–10 元/月）。
   - **风险**：**Markdown 支持未查到**；免费版只存 10 篇、免费样式与 VIP 样式分离；模板规模与风格未查到，谈不上极简科技感。

**第二梯队（可用但不推荐作为技术极简首选）**

4. **小墨鹰（原小蚂蚁）**（https://www.xmyeditor.com/ ）：官方 **25W+ 素材**规模最大，但免费用户**只能用「无 V 标」SVG 动效且不可商用**、使用素材**扣鹰币**、按 V 标分级锁会员（官方帮助明示）；**Markdown 支持只有厂商 SEO 内容声称、官方帮助中心未见**；重量级模板库与「极简」取向相反；更名时间两处来源还差一年。
5. **365编辑器**（https://www.365editor.com/ ）：价格低（终身 ¥269），但官方 FAQ 明确「**精选模板不属于会员素材/模板范围，需单独付费购买**」——**付费后还要再买**；免费版素材受限；**Markdown 未查到**。
6. **96微信编辑器**（https://96weixin.com/ ）：价格透明（330元/年、499元终身），但免费版只给 **200 张图/月、绑 1 个公众号、图片只存半年、素材不可商用**；**Markdown 未查到**。
7. **秀米**（https://xiumi.us/ ）：免费可排版，官方价格也清楚（等级会员 10元/30天、模板会员 20元/30天），但「会员模板」锁会员、独立链接**带秀米广告**、**无 Markdown**、**官方自己承认复制易错乱**、结构化编辑学习成本高。**技术极简不推荐。**
8. **有一云**（https://www.uecloud.com/ ）：定位「AI 写作 + AI 排版 + 全网分发」，不是精细排版工具；**价格官网不公示（未查到）**；SEO 内容占比高、营销味重。**唯一亮点是公开了 OpenAPI**（`/post/markdown/create` + 同步到公众号草稿箱），**适合作为「以后自动化发布」的备选调研对象，不适合作为第一篇推文的工具**。

**第三梯队（无法推荐）**

9. **键盘喵**（https://www.jianpanmiao.com/ ）：免费版**几乎不可用**（**15 张图/月、云存 3 个、无 Word 导入、无 VIP 素材**）；官方帮助专文解答「**为什么文章复制到公众号会有阴影**」，直接命中本调研关心的复制异常问题。**最不适合免费使用。**
10. **新榜编辑器**：**该独立排版编辑器已不可考**，`edit.newrank.cn` 域名现已指向「小豆芽」多平台分发工具。**无法作为候选评估。**
11. **老曹编辑器**：**官网未查到**（多个候选域名 DNS 不可解析，多引擎检索无产品命中）。**无法评估，建议从候选名单中移除或向需求方核对准确名称。**

**额外发现（不在原定 11 个名单内，但是本次检索中反复出现的「真·Markdown → 公众号」路线，供第 4/6 节参考）**：`EvoAI-li/md-to-weixin`（`marked` + `highlight.js` + **`juice` 内联 CSS** + DOMPurify，**主题含「科技蓝」**）、[mpediter.com/formatter](https://mpediter.com/formatter)、[markdown.com.cn/wechat](https://markdown.com.cn/wechat/)、[Layweout](https://layweout.vercel.app/)（Markdown / HTML / 富文本 → 公众号）。**这些 URL 均出现在检索结果中，但我未逐一打开核实其现状**，仅作为线索列出。

**最终判断**：对 Dorm 来说，在线编辑器只适合作为「路径 B 的应急替补」。**真正匹配「技术项目 + 极简科技感 + 免费 + 可复用」的，是第 4 节的 `doocs/md`（或 WeMD）——因为极简科技感这件事，对程序员来说最省力的做法不是在海量模板里挑一个「没那么脏」的，而是拿一份干净的 CSS、自己控制嵌套层数去改。**

逐项说明：

- **`juice`（[Automattic/juice](https://github.com/Automattic/juice)，MIT）**：本路线的事实标准。解析 HTML + 收集 `<style>` 里的 CSS 规则，按选择器匹配写回每个元素的 `style=""`。它是公众号场景被引用最多的库——`mdnice` 的 `package.json` 里就写着 `"juice": "^5.2.0"`（[源码](https://github.com/mdnice/markdown-nice/blob/master/package.json)），社区一批公众号排版工具/Agent Skill 的依赖表里也都是它。
  **必须注意的坑（来自 juice README 的 options 表）**：
  - `removeStyleTags` 默认 `true`（内联后删原 `<style>`）——**这是你要的**；
  - 但 `preserveMediaQueries` 默认 **`true`**，它是「以保留的 `<style>` 标签形式」保留 `@media`——**对公众号来说这段 `<style>` 会被剥掉，媒体查询等于白写，却在你产物里留了个隐患**；
  - 同理 `preserveFontFaces` / `preserveKeyFrames` / `preservePseudos` 默认都是 `true`，**都要关**；
  - `preserveImportant` 默认 `false`——**别开**，官方规范明确不建议 `!important`（2.3）；
  - `resolveCSSVariables` 默认 `true`（把 CSS 变量解成字面值，对公众号是好事）；`inlinePseudoElements` 默认 `false`（公众号不支持 `::before/::after`，开了反而塞 `<span>` 污染 DOM）。
- **`inline-css`（[jonkemp/inline-css](https://github.com/jonkemp/inline-css)，MIT）**：能力与 juice 基本同构（选项里同样有 `removeStyleTags` / `preserveMediaQueries`），卖点是基于 cheerio 且支持 `options.url` 直接拉外链 CSS。但更新节奏明显落后（2024-12 vs juice 2026-09），生态与 issue 响应弱一档。**新项目没有理由选它。**
- **`premailer`（[peterbe/premailer](https://github.com/peterbe/premailer)，BSD-3-Clause）**：老牌 Python 方案，但**默认分支最后一次 commit 是 2021-08-02**，实质停更 5 年。依赖 `lxml`/`cssselect`/`cssutils`，对新 CSS（嵌套、`@layer`、CSS 变量）支持弱；且基于 lxml 会重排 HTML，对已经手工调好的公众号 `section` 结构有意外改动风险。
  - 注意：PyPI `info.license` 字段填的是 `"Python"`（历史填错），classifier 写 PSF License，但**仓库 LICENSE 是 BSD-3-Clause，以仓库为准**。
  - 周下载量 1,054,953 看起来很高，但 pypistats 含 CI/镜像流量且它被大量项目当**传递依赖**，**不能理解为有 100 万人在做邮件**。
- **`css-inline`（[Stranger6667/css-inline](https://github.com/Stranger6667/css-inline)，MIT）**：本组唯一「现代、活跃」的实现，Rust 核心 + Python/Node binding。Python binding 已到 0.21.3（2026-09-14，Development Status `4 - Beta`），支持 Python 3.10–3.14。它是 premailer 作者参与推动的替代品。
  - **坑 1**：它同样会**保留带 `@media` 的 `<style>`**。README 原文：`Such tags will be kept in the resulting HTML even if the keep_style_tags option is explicitly set to false`。
  - **坑 2**：**Node binding 停在 0.11.2（2023-12-09）**，比 Python binding 落后 2.5 年。Node 项目用它等于拿一个两年前的 binding。
- **`inline-style-parser`**：**不是同类工具**。它只把单个 `style="..."` 字符串解析成 AST，不做选择器匹配、不读 `<style>`。它解决「读」内联样式，不解决「写」。在公众号工具链里只能当**后处理校验器**（检查产物里有没有 `!important` / `position` / `@media`）。列在这里是为了避免被 npm 下载量误导——它 5,322 万的周下载量来自 `react-markdown` 等一大批包的传递依赖。

> **推荐**：Node/JS 路线用 **`juice`**；Python 路线用 **`css-inline`**（不要用停更的 premailer）。无论哪个，**必须把 `preserve*` 系列全关，然后断言产物里 `<style>` 数量为 0**，否则会在公众号编辑器里静默失效。

#### 5.2.2 MJML：实测产物在这个场景会坏

- [mjmlio/mjml](https://github.com/mjmlio/mjml)：**18,249 ★**，MIT，npm `mjml@5.4.1`（2026-09-10），**周下载量 2,132,577**，仍在活跃维护（`pushedAt` 2026-09-25）。5.x 于 2026-04-16 发布，4.18.0 仍在维护。

**实测证据**：用 `npx mjml@5.4.1` 编译一个「两列、每列只有两个词」的最小模板，产物指标：

| 指标 | 实测值 |
| --- | --- |
| 产物字节数 | **9,440 bytes** |
| `<style` 块数量 | **5** |
| `@media` 出现 | **2 处** |
| `!important` 出现 | **3 处** |
| `<div>` / `<table>` / `<section>` 数量 | **6 / 5 / 0** |
| `class=` 属性 / `role="presentation"` | **5 / 5** |
| IE/mso 条件注释 `<!--[if` | **9** |
| 内联 `style="` 属性 | 17 |

关键片段（原文）：

```html
<style type="text/css">
  @media only screen and (min-width:480px) {
    .mj-column-per-50 { width: 50% !important; }
  }
</style>
...
<div class="mj-column-per-50 mj-outlook-group-fix"
     style="font-size:0px;text-align:left;direction:ltr;display:inline-block;vertical-align:top;width:100%;">
```

**这就是全部答案**：MJML 的多列布局，**内联写的是 `width:100%`**，靠 head 里 `<style>` 的 `@media (min-width:480px) { width:50% !important }` 才覆盖成并排。

于是：

1. **媒体查询被剥 → 多列塌成「上下两段」，不是「并排压缩」。** MJML 维护者在 [issue #1778](https://github.com/mjmlio/mjml/issues/1778) 的官方回答原文就是：「Mjml is mobile first so if a mail client doesn't support media queries, it will fallback to mobile version.」同类还有 [issue #919](https://github.com/mjmlio/mjml/issues/919)（`!important` 被剥后列被堆叠）、[#717](https://github.com/mjmlio/mjml/issues/717)、[#844](https://github.com/mjmlio/mjml/issues/844)。套到公众号：`<style>` 被剥 → `@media` 消失 → 内联已是 `width:100%` → **双栏变双段**。对「左图右文」「双栏信息卡」「往期文章两栏卡」这类版式是**直接变成另一个版式**。
2. **`!important` 撞官方规范。** 官方规范 4.5.2 明确不建议使用 `!important`。即便某个版本的编辑器没剥 `<style>`，`!important` 这条路也站在官方规范对立面。
3. **`<div>` + `class` + `role="presentation"` 对不上公众号 DOM。** 实测产物 `<section>` = 0 个、`<div>` = 6 个；而官方规范描述的是 `span[leaf]` / `section[nodeleaf]` 体系，没把 `div` 当容器（2.2）。社区实测亦称新版编辑器底层白名单里没有 `div`，被 `div` 包裹的卡片背景/圆角会被整段吞掉（[CSDN/Agent 技术社区](https://agent.csdn.net/6a812035662f9a54cb9d46d5.html)）。MJML 处理 `mj-style` 的实现里，`inline="inline"` 模式仍显式传 **`removeStyleTags: false`**（[GitCode 博客引 mjml-core 源码](https://blog.gitcode.com/9f5b29643877c56d6347a66293e37f8b.html)）——即**即使切到 inline 模式，产物里仍然有 `<style>`**。
4. **9 条 `<!--[if mso]>` 条件注释、`role="presentation"`、`mso-*` 属性在公众号全是零收益的死重量**（公众号只跑微信在 iOS/Android 上的渲染引擎）。而一个两列两个词的模板就已经 **9,440 bytes**——真实招募推文用 MJML 出产物，体积会是手写内联 HTML 的数倍。

#### 5.2.3 Maizzle：比 MJML 更差（Tailwind 是明确的失败因子）

- [maizzle/framework](https://github.com/maizzle/framework)：**1,614 ★**，MIT，npm `@maizzle/framework@6.1.7`（2026-09-16），周下载量 **82,603**，活跃。
  ⚠️ **别看错仓库**：[maizzle/maizzle](https://github.com/maizzle/maizzle) 有 2,862 ★，但那是站点仓库且 **licenseInfo 为 null**，不能拿它的 star 当框架热度。
- 它的本体是 **Tailwind CSS + PostHTML**（npm description 原文：`Maizzle is a framework that helps you quickly build HTML emails with Tailwind CSS.`），构建期用 **Juice** 做内联。
- **有一手失败案例**：腾讯云开发者社区一篇 2026-07 的文章里，作者原文写「我最终放弃了 HTML-Anything。因为它生成的内容复制到微信公众号时，格式会大批量丢失。**原因是他用了 Tailwind CSS，而微信公众号编辑器不支持。**」，最终改成「让 AI 用 mdnice 的思路，生成内联样式的 HTML 文件」才稳定（[原文](https://developer.cloud.tencent.com/article/2701529)）。
- Maizzle 文档确认：Tailwind 的 `dark:` / `ios:` 变体会编译成 `@media (prefers-color-scheme: dark)` / `@supports` 块，**这些 at-rule 只能留在 `<style>` 里，无法内联**（[Inline CSS transformer](https://maizzle.com/docs/transformers/inline-css)、[Tailwind CSS](https://maizzle.com/docs/tailwindcss)）。
- **它是三个坑一起踩**：Tailwind 类名不被识别 + at-rule 留在 `<style>` 被剥 + 产物含邮件式 `<div>`/`<table>` 结构。
- **唯一可复用的是它的 transformer 清单思路**（[overview](https://maizzle.com/docs/transformers/overview)）：`Safe Selectors`（把 `.foo > .bar` 这类邮件客户端不安全选择器重写成安全形式）与 `Six-digit HEX` 这两步对公众号**有借鉴价值的后处理步骤**。

#### 5.2.5 为什么 Cerberus / email-blueprints 这类「混合内联 + head style」模板到公众号会退化

Cerberus 的 `cerberus-hybrid.html` 实测：文件 **40,273 bytes**；`<head>` 里一大段 `<style>`（以 CSS Reset 开头，**带 `!important`**）后接 **4 个 `@media` 块**（320–374px / 375–413px / ≥414px / max-width 480px）；body 里**内联 `style="` 属性 101 处**。

这就是所谓 **hybrid（混合）范式**：**关键排版用内联写死（保证 Gmail 这类剥 `<style>` 的客户端不崩），再叠加 head 里的 `@media` 做小屏微调**。

退化原因三条：

1. **`@media` 那一层全丢，且退化是静默的。** Cerberus hybrid 的价值恰恰在「内联是兜底、`@media` 是优化」。公众号剥 `<style>` 后只剩兜底那层——配色/字号/间距的移动端微调消失，**更麻烦的是 `display:none` 的「仅桌面/仅移动」区块会全部显形**（比如「在浏览器中查看」、preheader 预header 文本、只为桌面准备的备用列）。它不报错，只是「看起来还能看，但不是设计稿的样子」。
2. **`!important` 撞官方规范。** Cerberus 的 reset 用 `!important`，MJML 的列宽也用 `!important`；官方规范 4.5.2 明确不建议。
3. **邮件专属的 `<table>` 嵌套 + `role="presentation"` + mso 兼容层是纯负重。** 公众号**确实支持 `<table>`**（公众号自己的卡片单元格就是 table），但那是公众号自己的 table 语义，不是邮件的 table-as-layout 语义。深嵌套 table 还会踩官方 2.1「单子节点连续嵌套不超过 10 层，超出会自动精简」。`mailchimp/email-blueprints`（7,024 ★，2019 年，**无 License**）更是「桌面优先 + table 布局 + head style」的老范式，除结构参考外几乎无可复用。

> 一句话：**Cerberus / email-blueprints 的「知识点」值得抄（如何用内联 + table 做出不依赖 `<style>` 也能读的骨架），但它们的「产物」不能直接喂给公众号——因为公众号只吃「内联那一半」，而它们的设计价值有相当一部分在「`<style>` 那一半」。**

### 5.3 成本与收益：什么情况下值得

#### 收益（真实可得）

1. **把「排版」变成「编译」**：一次性投入后，每篇推文的排版边际成本 ≈ 0。
2. **视觉一致性**：招募推文是重复性内容（岗位/项目/时间/报名方式），天然适合模板化。
3. **可校验、可回归——这是纯手工排版给不了的东西**。成熟的公众号工具都在做**确定性校验**：`md2html` 的 `validator.ts`（检查禁用标签/CSS）、`wechat-skill` 的双关卡 lint（「源头干净 → 产物必然干净」）。更关键的是**官方就提供了校验器**：[wechatjs/verify-article-structure-spec](https://github.com/wechatjs/verify-article-structure-spec)（MIT，puppeteer CLI，退出码 0/1/2；**但它未发布到 npm，要 clone 后自建，且输出需人工判断——见第六节更正**）。对「反复发、格式固定」的场景，把公众号红线写成断言脚本是一次投入长期生效。
4. **模板进 git**：改样式走 PR + review，比在公众号后台点样式可审计得多。

#### 成本（真实会发生的）

| 成本项 | 量级与依据 |
| --- | --- |
| 一次性搭建 | 内联化本身**半天以内**（juice 核心是 5 行代码）；**真正的成本在「公众号兼容后处理」**——`div`→`section`、渐变降级实色、图片 `max-width:100%`、代码块转 span 染色、外链转脚注、图片重新上传，社区工具普遍把这部分写成几百行管道 + 校验脚本 |
| 持续踩坑成本 | 公众号编辑器行为**不公开、会静默变化**。官方社区有「排版样式莫名错乱」的置顶帖（用户反馈「用了六年的样式块最近一个月出问题」），**这是一条没有 SLA 的依赖** |
| 产物体积 | 内联后 HTML 体积约为 Markdown 源的 **5–10 倍**（[365工具箱](https://www.toolbox365.cn/tutorials/markdown-to-wechat-typesetting-traps/)）；MJML 实测 2 列 2 词 = 9,440 bytes |
| 图片仍要手工 | 无论工具多好，**图片必须在公众号编辑器里逐张重新上传**（外链图会被防盗链拦/裁切）。招募推文通常带二维码/宣传图，这部分**自动化不掉** |
| 引入 MJML/Maizzle 的额外风险 | 还要额外承担「框架产物适配公众号」的适配层，而**没有任何先例可抄**（5.2.4 零实践证据） |

#### 判断

- **可行且被验证的是窄路**：「Markdown / 手写 HTML + juice 内联 + 确定性校验」。所有能找到的公众号排版开源工具都在窄路上。
- **MJML/Maizzle：思路能、框架不能。** 核心矛盾是 MJML 的响应式列 = `<style>` 里的 `@media` + `!important`，而公众号恰好把这两样都砍掉。
- **最小可行路径（如果要走）**：
  1. 手写一份**单文件、全内联、`section` 优先、无 `@media`、无 `!important`、无 `div`** 的招募推文 HTML 模板；
  2. 模板里用占位符（`{{title}}` / `{{deadline}}` / `{{qr}}`），用任意模板引擎填充；
  3. `juice(html, { removeStyleTags: true, preserveMediaQueries: false, preserveFontFaces: false, preserveKeyFrames: false, preservePseudos: false })`；
  4. 用官方 `wechatjs/verify-article-structure-spec` 的 CLI 做发布前门禁（需先 clone 自建，见第 6 步更正；建议人工过一遍输出，它有已知误报）；
  5. 再加几条自己的断言：产物里 `<style>` 数 = 0、`@media` 数 = 0、`!important` 数 = 0、`<div>` 数 = 0、所有 `<img>` 带 `max-width:100%;height:auto`。
- **何时值得**：项目**每季度 ≥ 3–4 篇格式高度相似的推文**，且作者本来就写代码。
- **何时不值得**：一年发不到 5 篇、或每篇版式都不同——直接用现成工具更省事，把时间花在内容上。

> **对 Dorm 的落点**：Dorm 的目标是「招募用户 / 招募共同开发者」，属于「格式高度相似的重复推文」，且作者是程序员。但从零做路径 C 的投入产出比不如直接用 `doocs/md`（它已经把内联化 + 主题 + 图片上传这三件事做完了）。**建议：第一篇用 doocs/md；等发到第 4–5 篇、模板结构稳定后，再把 doocs/md 的输出固化成一份仓库内的 HTML 模板 + juice 脚本。**

## 6. 对 Dorm 的实操建议

前提约束（来自任务）：作者是程序员；要免费或低价；想要极简/科技感；需要能反复复用的模板；要发的是招募类推文（用户 + 共同开发者）。

### 路径 A（首选）：doocs/md Docker 自部署 + 自写一份 Dorm 主题 CSS + 公众号图床

**用什么**：`doocs/md`（WTFPL，13,374★，2026-09-24 仍在更新）
**用哪个主题**：以内置 **`simple`（简洁）** 为基线改造；也可以试 **WeMD 的「数据蓝图」/「清晰指南」** 找配色灵感
**费用**：0 元（Docker 在你自己的机器上跑；公众号图床只要你有一个公众号的 appID/appsecret，也是免费接口）

**步骤**：

1. 起服务：
   ```sh
   docker run -d -p 8080:80 --name dorm-md doocs/md:latest
   ```
   打开 http://localhost:8080 。
2. 配公众号图床：进「图床设置 → 公众号」，填 `appID`、`appsecret`、`代理域名`。教程在 https://md-pages.doocs.org/tutorial 。**这一步是整个方案的地基**——不配它，图片外链会被微信过滤掉（见 2.1）。
3. 建模板仓库：在你自己的机器上另开一个目录（**不要放进 Dorm 主仓库**，避免污染工程），把这三样东西存起来并 git 管理：
   - `dorm-theme.css`：从 [`packages/shared/src/configs/theme-css/simple.css`](https://github.com/doocs/md/blob/main/packages/shared/src/configs/theme-css/simple.css) 复制出来改；
   - `recruit-template.md`：招募推文的骨架（开头一句话说清「XMUMDorm 是什么 / 招什么人」→ 项目截图 → 技术栈 → 你想要什么样的贡献者 → 怎么联系）；
   - `CHANGELOG.md`：记下每次发文的主题改动。
4. 改主题时要遵守的硬约束（来自本文第 2 节）：
   - 只写**内联样式级别的东西**，别用 `@media`、伪元素、`position: absolute`、`float`、`animation`（2.6）；
   - 容器写 `max-width:677px;width:100%`，**不要写死 `width:677px`**（2.3 / 2.8，官方 width 规范）；
   - 不要设 `font-family`（2.4，官方明确不建议）；
   - 不要用 `!important`（2.3，官方明确不建议）；
   - 嵌套别超过 10 层（2.2，官方会「自动精简」，你会失去控制权）；
   - 正文 15px / 行高 1.75 / 字距 1px（2.8）；
   - Dark Mode 下别用渐变做文字背景（2.4）。
5. 写稿 → 预览 → 复制 → 粘贴进公众号后台。
6. 想验证样式有没有踩官方规范，可以拿官方的校验 CLI 跑一遍：[wechatjs/verify-article-structure-spec](https://github.com/wechatjs/verify-article-structure-spec)（MIT，基于 puppeteer，退出码 0/1/2）。**这是全网唯一由微信官方提供的 HTML 校验器**，用它比任何社区文章都靠谱。

   > **更正（2026-09-26 实测）**：它**没有发布到 npm**，所以「`npx` 一下就能接 CI」是不成立的。
   > `cli/package.json` 虽然写了 `"private": false` 和 `bin`（包名 `@tencent/verify-article-structure`），
   > 但在 npmjs 和腾讯镜像 `mirrors.tencent.com/npm` 上**都是 404**——从未真正发布。
   > 要用只能 clone 仓库进 `cli/` 目录自己装：
   >
   > ```bash
   > git clone --depth 1 https://github.com/wechatjs/verify-article-structure-spec.git
   > cd verify-article-structure-spec/cli
   > PUPPETEER_SKIP_DOWNLOAD=true npm install
   > PUPPETEER_EXECUTABLE_PATH="/path/to/chrome" npx tsx src/index.ts ./article.html --json
   > ```
   >
   > 本仓的 `marketing/wechat/dorm-wechat-template.html` 已经用它跑过：抓到 1 条真违规
   > （顶部品牌条用渐变做文字背景）并已修掉；剩 1 条 `line-height` 报警经逐帧测量确认是
   > **校验器自身的 bug**（把 `<strong>` 的文字算了两遍导致行数虚高），详见
   > `docs/07-Implement/公众号推文模板与微信号统一.md`。也就是说：**这个校验器值得跑，
   > 但它的输出需要人来判断，不能当 CI 的硬门禁。**

**为什么推荐它**：唯一同时满足「免费 + 图片这关能过 + 可版本管理 + 作者自己能读源码改 + 不怕第三方站点倒闭 + 还在维护」的方案。缺的只有一个「现成的科技风主题」，而这对程序员来说是最容易自己补的一环。

### 路径 B（打底/应急）：在线版 doocs/md，「简洁」主题，图片先手动传

**用什么**：https://md.doocs.org （免部署）
**用哪个主题**：内置「简洁」（`simple`）
**费用**：0 元
**步骤**：写 Markdown → 选「简洁」→ 用编辑器面板微调主题色为 Dorm 主色 → 复制 → 粘贴进公众号后台。图片先在公众号后台素材库手动上传，再把 `mmbiz.qpic.cn` 链接回填进 Markdown。
**什么时候用**：想今天就把第一篇招募推文发出去；或者本地 Docker 环境没配好。
**代价**：图片要手动倒腾，稿件一多就烦；主题调整能力受在线版面板限制。

### 路径 C（长期进阶，只在有明确需求时做）：自建 HTML 模板 + `juice` 内联化，纳入 Dorm 仓库

**用什么**：`juice`（mdnice 用的就是它）+ Node 脚本
**步骤**：写一个 `templates/recruit.html` + `templates/recruit.css` → 用 `juice` 把 CSS 内联成 `style` 属性 → 用 Markdown 渲染器把稿件正文塞进 `<section>` 占位符 → 输出一段可直接粘贴的 HTML。
**什么时候值得**：你已经写第 5 篇以上招募推文、模板结构稳定、并且希望「推文排版能进 CI」时。**第一篇推文就做这个是过度工程。**
**代价**：要自己处理图片上传到公众号、自己保证不踩 2.x 的全部地雷、自己维护主题。

> **一个更省事的变体（本次调研新增）**：如果你不想装 Node 工具链，但已经会写 HTML，**壹伴（https://yiban.io/ ）的「导入 HTML」功能可以让你把自己写好的极简内联 HTML 直接塞进公众号后台**（依据：壹伴官方 12.4.0 更新日志，见 3.5）。这等于把路径 C 的「产出 HTML」和「进后台」两步合并成一步。但**它仍然不能进 git、不能进 CI**，并且你依然要自己保证 `section` 层数 ≤10、无 `!important`、无 `@media`（第 2 节）。

### 最终推荐

> **走路径 A：`doocs/md` Docker 自部署 + 自己改一份基于 `simple` 的 Dorm 主题 + 配置公众号图床。**
>
> 先用路径 B 发第一篇试水，同一天内把路径 A 搭好。路径 C 留到「每月都要发推文」以后再考虑。

#### 补充：仓库里已经有一套「零依赖」模板（2026-09-26 同日交付）

本调研与 `marketing/wechat/` 下的推文模板是**并行产出**的，这里补上交叉引用，避免两份文档各说各话。

交付物是 `marketing/wechat/dorm-wechat-template.html`：**纯手改 HTML + 一键复制**，
不装 Docker、不配图床、不写 `juice`、不需要 Node 工具链，双击打开就能改、能复制。

它**不是**上面说的路径 C。路径 C 指的是「`juice` 内联化 + 构建脚本」那条工程化路线；
这套模板是手写内联样式，没有构建步骤。准确地说它是路径 A / B 之外的**第四个选项**：

| | 路径 A（doocs/md） | 仓库模板 |
| --- | --- | --- |
| 上手成本 | 装 Docker + 配 appID/appsecret | **零** |
| 写稿方式 | Markdown | 直接改 HTML |
| 图片 | 配好图床后**自动**上传进微信素材链路 | **手动**传素材库 |
| 改样式 | 改一份 CSS，可版本管理 | 手动全局替换色值 |
| 适合 | 长期、高频发文 | **发第一篇 / 低频发文** |

**所以建议是互补的**：想马上把第一篇招募推文发出去，直接用仓库模板；
等「每月都要发」了再上路径 A。两条路都遵守第 2 节的硬约束——仓库模板已按官方规范
逐条自查（零 `class`、无 `!important`、无 `font-family`、容器用 `max-width:677px`、
嵌套最深处 4 层、`<img>` 带 `data-w`），并有 13 例测试守着这些约束不被改回去。
