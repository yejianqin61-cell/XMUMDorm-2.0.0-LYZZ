# 双语与文本弹性实测

**日期**：2026-09-30
**性质**：新 App 设计的前置事实输入（Lead 亲自实测）
**为什么是移动端第一等约束**：校区在马来西亚、**英文授课**、社群以中文为主——双语不是可选项。而**中英文的文本长度差 2.5 倍**，直接决定按钮、Tab、徽章、表单能否放得下。移动端屏幕比 Web 小得多，这条约束在 App 上比在 Web 上更致命。

---

## 一、结论先行

| 结论 | 证据 |
|---|---|
| 双语是硬需求 | 校区在马来西亚、英文授课；Web 侧 177/257 个文件含中文、并已实现中英切换 |
| **中英文本长度比中位数 2.50×** | 1,504 组中英字面量实测 |
| **75.9% 的文案，英文长度 ≥ 中文的 2 倍** | 同上 |
| 极端案例达 **6.00×** | 「保存」→「Save changes」；「互动」→「Interaction」 |
| Web 的双语机制**不可继承** | 1,701 处内联三元 `isZh ? '中文' : 'English'`，**0 处 `t('key')` 字典调用** |
| 旧 App 的"双语"**是空壳** | 139 个文件里仅 **5 个**有语言分支、**4 个**真正双语；69 个屏里 62 个含中文 |
| 双语覆盖率两边都不完整 | Web：101/177 含中文文件有分支（约 57%）；旧 App：4/89（约 4.5%） |

## 二、实测方法

```powershell
# 中英字面量对与长度比（Web）
$jsx = Get-ChildItem frontend/src -Recurse -File -Include *.jsx,*.js
foreach ($f in $jsx) {
  $t = Get-Content $f.FullName -Raw
  [regex]::Matches($t, "isZh\s*\?\s*'((?:[^'\\]|\\.)*)'\s*:\s*'((?:[^'\\]|\\.)*)'")
}
# 旧 App 对照需先从 tag 导出：git archive --format=tar -o "$env:TEMP\v1.tar" app-legacy-v1 mobile
# 注意：统计 t('key') 必须用词边界 (?<![\w.])t\(\s*['"] ，
#       否则 split(' / format(' 会被误判 —— 实测宽松口径虚报 369 次，严格口径为 0。
```

## 三、Web 的双语机制（不可继承）

| 指标 | 实测 |
|---|---|
| 语言上下文 | `frontend/src/context/LanguageContext.jsx`（1,065 B），暴露 `lang` / `isZh` / `setLang` |
| 语言集合 | **仅 `zh` 与 `en`** |
| 默认语言 | `zh`（`isZh = lang !== 'en'`） |
| 持久化 | `localStorage['dorm-lang']` |
| **内联三元 `isZh ? '中文' : 'English'`** | **1,701 处** |
| 引用 i18n / 字典模块 | 10 处 |
| **`t('key')` 字典调用** | **0 处** |
| i18n 目录内容 | 仅 `canteenAreaRanking.js`、`canteenStrings.js`（食堂专用） |
| 含中文文件 / 含 `isZh` 分支文件 / 两者都有 | 177 / 103 / **101**（257 个文件） |

**判定**：Web 没有词条层。文案散落在 1,701 个三元表达式里，**无法审计完整性、无法统一长度、无法新增语言**。覆盖率约 57%（101/177），即近一半含中文的文件没有英文对应。

### 内联三元最集中的文件

| 文件 | `isZh ?` 处数 |
|---|---|
| `i18n/canteenStrings.js` | 80 |
| `pages/Schedule.jsx` | 78 |
| `pages/Clubs/ClubProfile.jsx` | 54 |
| `pages/Admin/AdminDashboard.jsx` | 50 |
| `pages/Handbook/HandbookArticleDetail.jsx` | 47 |

## 四、旧 App v1 的双语：空壳

| 指标 | 实测 |
|---|---|
| 生产代码文件 | 139 |
| 含中文字符的文件 | **89** |
| 含任意语言分支（`isZh ?` / `lang === '…'`）的文件 | **5** |
| **两者都有（真正做了双语）的文件** | **4** |
| 屏文件 | 69，其中含中文 **62** |
| `isZh ?` 出现次数 | 39 |
| `lang === 'zh'` / `lang === 'en'` | 各 1 |
| **`t('key')` 调用** | **0** |
| 字典常量（`copy` / `STRINGS` / `MESSAGES` 等） | 0 |

`LanguageContext.tsx`（849 B）**存在**，暴露 `lang` / `setLang` / `toggleLang`，但**几乎没有代码使用它**。

**判定**：旧 App 实质上是**纯中文应用**，"双语"只是建了一个 Provider 就当作完成了——**与"装了 Reanimated 却 0 引用""写了 7 个 UI 组件却 0 引用"是同一种病：把"建了基础设施"当成了"完成了功能"。**

## 五、核心量化：中英文本长度比

样本：Web 侧可解析的中英字面量对 **1,519 组**（有效 1,504 组，双方长度均 ≥ 2）。

| 分位 | 英文/中文 长度比 |
|---|---|
| **中位数** | **2.50×** |
| 75 分位 | 3.00× |
| 90 分位 | 3.75× |
| 95 分位 | 4.00× |
| 最大 | **6.00×** |
| **比值 ≥ 2.0× 的占比** | **75.9%** |

### 极端案例（英文膨胀最严重）

| 中文 | 英文 | 比值 |
|---|---|---|
| 保存（2 字） | `Save changes`（12） | **6.00×** |
| 广告帖（3 字） | `Advertisement post`（18） | **6.00×** |
| 验证码（3 字） | `Verification code`（17） | 5.67× |
| 互动（2 字） | `Interaction`（11） | 5.50× |

> 这些都是**按钮、标签、字段名**——恰好是移动端空间最紧张的位置。

## 六、对 App 设计的硬含义

以下每条都可直接转成宪法条款或验收项：

1. **布局必须以英文长度为准，不能以中文为准。**
   以中文定尺寸的按钮/分段控件，切到英文必然溢出或截断。中位数 2.5×、90 分位 3.75× 是设计余量的依据。

2. **中文不该"填满"，英文必须"放得下"。**
   常见的错误做法是照中文排版让中文占满宽度——那等于给英文预留 0 弹性。设计必须按**最长语言**定尺寸。

3. **必须建立集中词条层（key-based），禁止内联三元。**
   Web 的 1,701 处内联三元是反面教材：无法审计、无法统一长度、无法新增语言。旧 App 更糟——根本没有。
   验收方式：`isZh ?` 式内联三元计数必须为 0，`t('key')` 覆盖率必须为 100%（可用脚本测，见 [`scripts/design-debt-report.js`](../../../scripts/design-debt-report.js) 的同类思路）。

4. **语言切换不得引发布局跳动。**
   若切换语言导致按钮换行、Tab 变高、卡片重排，那是"按当前语言排版"的直接后果。必须在令牌层预留弹性，而不是切换时重算。

5. **Tab 与徽章是重灾区，需要专门策略。**
   中文 Tab 常见 2 字（"广场""树洞"），英文对应 `Square`/`Tree Hole`（更长且可能两词）。可选策略：图标优先 + 短标签、英文用缩写、或两端各自定义标签而非直译。**这一项必须由设计哲学先定调**。

6. **字体：中英混排需要显式策略。**
   Web 用 `Source Han Serif SC`（衬线标题）+ `PingFang SC`（正文）。**`PingFang SC` 在 Android 不存在**，且衬线标题在 Android 会退化。App 必须为中日韩字符与拉丁字符分别指定字族，并各自验证。

7. **双语覆盖率必须可测。**
   Web 57%、旧 App 4.5% 都是不合格的。App 应有一个可运行的检查：所有面向用户的字符串都必须有 zh 与 en 两个词条。

## 七、需要所有者拍板

1. **语言集合**：仅 `zh` + `en`，还是要预留马来语（`ms`）？预留与否决定词条层与字体的设计余地。
2. **默认语言**：Web 默认 `zh`。App 是否默认跟随系统语言（更符合平台习惯），还是同 Web 默认中文？
3. **Tab 标签策略**：中文短标签 + 英文较长时的处理方式（图标优先 / 缩写 / 各语言独立文案）——这属于设计哲学范畴。
4. **是否需要"中英混排"的正式规范**（同一界面内中英并存，如课程名、地名）——XMUM 场景下很常见。

---

## 八、本文件的边界

- 本文只测量**现状与文本长度**，**不提出 App 的设计主张**；主张在《设计哲学提案》中给出。
- 「中英长度比」的样本来自 **Web 的文案**；App 会有自己的文案，**分位数可能不同，但量级不会变**（这是语言特性决定的）。App 文案定稿后应重跑同一测量。
