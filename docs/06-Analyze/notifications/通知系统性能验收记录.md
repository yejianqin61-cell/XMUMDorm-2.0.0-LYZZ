# 通知系统性能验收记录

**测试日期：** 2026-08-16

**对应任务：** `06 - 查询计划、条件索引与性能验收`

**基线提交：** `26fdf7b`

**优化后提交：** `e96de87`

**测试结论：** 请求收束和批量已读目标达成；冷请求中位数未达到降低 40% 的门槛，已确认瓶颈为 Railway 数据库网络往返，未虚构收益，也未增加缺少收益证据的索引。

## 1. 测试条件

- 本地启动基线与优化后 Node.js API，二者连接同一 Railway MySQL 数据库。
- 使用通知数量最多的账号作为匿名固定样本，不记录用户 ID、账号信息、Token 或通知正文。
- 数据库共有 699 条通知，涉及 126 个用户；样本账号有 57 条通知，单帖互动最大样本为 6 条。
- 基线模拟变更前 App 行为：并发请求通知列表与未读汇总，列表页大小为 50。
- 优化后模拟当前 App 行为：请求互动通知列表一次，响应同时包含未读汇总，页大小为 20。
- 每组先执行 2 次预热但不计入结果，随后执行 10 次独立 HTTP 请求；每次关闭 HTTP 连接并发送 `Cache-Control: no-cache`。
- 本测试排除了客户端与应用服务缓存命中，但 Railway 托管环境不允许清空 MySQL Buffer Pool，因此“冷请求”指 HTTP 与应用缓存边界，不宣称数据库页缓存绝对冷启动。
- 两组测试在同一台 Windows 11 电脑、同一网络、相邻时间窗口内完成。

## 2. API 基线结果

| 指标 | 基线 `26fdf7b` | 优化后 `e96de87` | 变化 |
|---|---:|---:|---:|
| 首次打开通知请求数 | 2 | 1 | -50% |
| 首批页大小 | 50 | 20 | -60% |
| Median | 368.8 ms | 391.2 ms | +6.1% |
| P95 | 799.4 ms | 676.0 ms | -15.4% |

基线 10 次原始样本（ms）：

```text
368.2, 427.9, 369.4, 371.2, 352.5, 367.3, 369.6, 367.5, 346.3, 799.4
```

优化后 10 次原始样本（ms）：

```text
353.6, 671.3, 349.1, 348.5, 353.5, 416.1, 371.2, 676.0, 411.2, 420.5
```

### 门槛判断

- 首次通知请求数从 2 降为 1：通过。
- 同组 N 条未读由 N 次更新降为 1 次批量更新：已由批量已读路由与客户端回归测试证明通过。
- Median 至少降低 40%：未通过。
- P95 未因互动展开能力明显恶化：通过，当前样本下降 15.4%。

Median 未改善的原因可复现：变更前 App 已使用 `Promise.all` 并发请求列表和未读汇总；变更后只是把两条远程 SQL 移到同一个 API 内并发执行。两种实现都受约 350 ms 的 Railway 单次往返下限约束，因此减少一个 HTTP 请求降低了请求数量和高位波动，却不会把并发链路的中位耗时相加后再减半。继续调整本地 UI、增加 Redis 或盲加索引都不能可信地制造 40% 收益。

## 3. 查询计划

下表记录最大通知样本账号在当前生产结构上的 `EXPLAIN`。`rows` 为优化器估算扫描行数，不是实际返回内容。

| 查询 | 基线计划 | 优化后计划 | 判断 |
|---|---|---|---|
| 互动列表 | `idx_user_id`, `ref`, rows 57, filesort | `idx_user_id`, `ref`, rows 57, filesort | 按用户限制在 57 行，没有全表扫描 |
| 事务列表 | `idx_notifications_user_type_read_created_at`, `range`, rows 6, filesort | 同基线 | 复合索引覆盖用户与类型过滤 |
| 系统列表 | `idx_notifications_user_type_read_created_at`, `range`, rows 6, filesort | 同基线 | 复合索引覆盖用户与类型过滤 |
| 未读汇总 | 变更前后查询相同 | `idx_notifications_user_type_read_created_at`, `ref`, rows 57, `Using where; Using index` | 覆盖索引，无回表扫描正文 |
| 单帖互动展开 | 基线功能不存在 | `post_id + idx_user_id` index merge, rows 1, filesort | 样本最多 6 条，扫描规模与结果规模相称 |
| 批量已读 | 变更前后更新形状相同 | `PRIMARY`, `range`, rows 2, `Using where` | 主键定位并由 `user_id` 二次约束 |

列表查询因 `type IN (...)` 后再按 `created_at, id` 排序而出现 filesort，但最大账号只扫描 57 行，事务和系统列表只扫描 6 行。现有数据不支持为了消除这种小规模内存排序新增 `(user_id, created_at, id)` 索引；该索引会增加所有通知写入和批量公告写入成本，而且不一定优于当前类型过滤索引。

## 4. 索引决策

本次不新增索引，不产生迁移文件，理由如下：

1. 六类查询均使用主键、单列用户/帖子索引或既有复合索引，没有全表扫描。
2. 最大用户扫描 57 行，单帖互动估算扫描 1 行，和当前生产数据规模相称。
3. API 中位耗时接近所有查询共有的远程网络下限，现有证据不能把约 350 ms 归因于 filesort。
4. 新索引无法证明可达到 40% 门槛，却会确定增加通知写入成本。

若未来单用户通知量增长到数千条，应重新采集 `EXPLAIN ANALYZE`、扫描行数和写入耗时，再评估面向真实查询形状的最小索引；不得依据本次小数据样本提前创建。

## 5. 可复现瓶颈与后续边界

当前未达 40% 的瓶颈不是功能缺陷：列表完整性、稳定分页、三分类、同帖展开和批量已读均已保留。若业务仍要求把中位耗时压到 220 ms 以下，需要改变部署或数据访问边界，例如让 API 与数据库位于更低延迟的同区域网络，并在同样方法下重新采样。Redis、消息队列和缩短历史可见范围不属于本轮方案，也不应用来掩盖基线未达标。
